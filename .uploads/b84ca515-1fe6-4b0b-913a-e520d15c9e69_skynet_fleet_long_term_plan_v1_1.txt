天网（Skynet Fleet）长期发展计划书
V1.1｜网络理解、可靠自动化与能力融合
整理日期：2026-11-03

一、项目宗旨与长期目标

宗旨：借天下融入己身，融万物之能，以解万物之题。
目标：网络随处可到，网络随处可用，网络随处可查，网络随处可解。

天网不是单一的爬虫、注册工具、浏览器自动化工具或模型调度器，而是逐步建设一套开放、可扩展、跨设备、跨模型、跨服务的通用智能基础设施：发现外部资源，理解可用能力，按权限调用工具，协同执行任务，观察执行结果，并将经过验证的经验沉淀为可复用能力。

本文件是长期战略和实施路线，不代表要推翻现有架构。实施前必须对照现有仓库、项目总纲、代码和测试，区分已实现、部分实现、缺失和未验证能力；优先复用已有实现，避免重复造轮子。

二、关键认知更新：从局部逆向到端到端系统理解

过去常见路径：
发现网站 → 逆向分析 → 找端口或接口 → 尝试请求 → 遇到登录态 → 尝试处理登录 → 失败后重试或人工操作。

这条路径能发现局部线索，但端口只是通信入口，API 路径不等于接口契约，登录成功不等于拥有所有权限，请求发出不等于业务成功，页面显示成功也不一定代表服务端状态已改变。

新的工作模型：
明确目标 → 选择合法访问方式 → 观察通信与执行状态 → 理解认证、授权、会话和业务规则 → 验证最终结果 → 根据证据诊断失败 → 记录可复现结论 → 将有效方案沉淀为能力。

必须区分：
1. 网络连接成功 ≠ 应用请求成功。
2. HTTP 请求成功 ≠ 业务操作成功。
3. 身份认证成功 ≠ 获得全部权限。
4. 浏览器点击成功 ≠ 服务端接受操作。
5. 没收到结果 ≠ 操作一定失败；也可能是“结果未知”。
6. 重试不等于诊断。对有副作用的操作，必须先查询状态或确认是否可安全重试。

三、项目定位与差异化方向

定位：开放式、可扩展、跨设备的通用智能基础设施。

核心方向：
1. 大规模接入外部能力：网站、API、开源项目、模型、论文、数据、协议、软件、设备和服务。
2. 统一能力注册与组合：能力可被发现、描述、授权、调用、验证和复用。
3. 跨设备协作：协调 Windows、Android、Linux、服务器和云端环境。
4. 基于证据的自主扩展：发现能力缺口，研究外部实现，生成适配器，在受控环境验证后再注册。
5. 从“能执行”走向“能解释”：不只发出指令，还能观察执行链路、识别失败位置并给出可验证的修复建议。

四、总体架构：八个逻辑层

1. 网络与运行基础层：操作系统、进程、文件、DNS、IP、TCP/UDP、TLS、权限、设备身份与通信。
2. 统一能力接入层：能力注册表、适配器、工具描述、输入输出契约、版本、依赖、权限要求和健康状态。
3. 资源获取与检索层：代码仓库、论文、技术文档、协议、模型、数据集、软件包、工程讨论和公开服务目录；保留来源、时间、许可证与原始证据。
4. 知识关联与能力图谱层：建立项目—依赖、论文—实现、协议—客户端、模型—推理框架、服务—授权方式、设备—执行器等关系。
5. 任务理解与智能编排层：拆解目标，选择模型和工具，处理依赖、并行、超时、重试、状态持久化、暂停与恢复。
6. 跨设备与分布式协作层：设备注册、在线状态、能力清单、任务分发、消息确认、结果回传、远程执行和故障恢复。
7. 实验、评估与能力转化层：在受控环境验证功能、性能、可靠性、依赖、许可证、安全边界和端到端结果。
8. 持续发现与受控自我改进层：识别缺口，生成研究问题，寻找资源，测试方案，按权限审批后注册能力，并用真实任务反馈持续评估。

五、网络知识地图

网络并非单一的“逆向层”，而是多个交叉领域：

1. 网络基础与寻址：IP、子网、路由、NAT、DNS、端口、IPv4/IPv6。
2. 链路与接入：以太网、Wi-Fi、MAC、ARP、交换机和网卡。
3. 传输层：TCP、UDP、QUIC、连接状态、重传、拥塞控制和超时。
4. 应用协议：HTTP/1.1、HTTP/2、HTTP/3、WebSocket、REST、RPC、gRPC。
5. 加密与信任：TLS、证书、PKI、密钥管理、OAuth 2.0、OpenID Connect、Token、Cookie 和会话管理。
6. 抓包与协议分析：Wireshark、TShark、tcpdump、PCAP、流重组、时序分析和请求响应关联。
7. 浏览器与应用运行时：DOM、JavaScript、浏览器开发者工具、自动化框架和事件机制。
8. 网络安全：防火墙、访问控制、WAF、威胁建模、安全日志、漏洞分析与授权测试。
9. 分布式系统：代理、隧道、负载均衡、服务发现、消息队列、P2P、边缘计算和服务网格。
10. 网络编程与可靠自动化：Socket、异步 I/O、协议解析、状态机、限流、重试、幂等性和可观测性。

原则：抓包是观察入口，不是网络知识的全部；逆向是研究方法之一，不是服务接入的默认方式。优先查阅官方文档与受支持接口，再按实际需求选择协议分析、浏览器自动化或其他方式。

六、网络观测与协议理解能力层

目标不是只保存抓包文件，而是将通信证据转成可诊断、可复用的信息。

建议模块：
1. 采集器：从获准的网卡、浏览器开发者工具、应用日志、测试代理和任务执行器采集数据。
2. 协议解析器：解析时间戳、端点、协议、请求方法、响应状态、延迟和错误类型；明确标记加密内容的可见性边界。
3. 会话与任务关联器：按任务 ID、时间、连接、请求关联标识和应用日志，将请求、重定向与执行步骤串联。
4. 状态机与结果验证器：区分已发起、已发送、已接收、处理中、成功、失败、结果未知、暂停和需要人工确认。
5. 故障诊断器：依据证据区分 DNS/连接失败、TLS 错误、HTTP 错误、授权/会话问题、业务校验失败、页面脚本异常、权限拦截、超时和结果判断错误。证据不足时明确标注未知，不臆造原因。
6. 知识库：保存官方文档、接口契约、已验证错误模式、修复方法、适用条件与失败记录。
7. 能力适配层：根据任务在官方 API、SDK、CLI、受支持的协议客户端、浏览器 DOM 自动化和桌面视觉操作之间选择方式。

七、统一自动化架构

1. 目标理解：理解最终结果，而不是只执行点击脚本。
2. 访问方式选择：优先官方 API、SDK、CLI 和受支持协议；没有合适接口时再考虑浏览器或桌面自动化。
3. 环境与权限检查：确认授权、程序权限、依赖、网络可达性和执行环境。
4. 状态化执行：每一步都有输入、预期结果、超时策略和状态记录。
5. 结果验证：用服务端状态、响应数据、文件或测试结果确认任务是否完成。
6. 失败诊断：根据日志与通信证据定位问题层次，不盲目重试。
7. 安全恢复：可安全重试时再重试；结果未知或操作有副作用时，先查询状态或请求人工确认。
8. 经验沉淀：将已验证的解决办法、适用范围和限制登记到能力库。

八、身份认证、授权与会话管理

不要把“登录态”视为单一障碍，也不要混淆认证、授权和业务风险：
- 认证：确认用户或客户端是谁。
- 授权：确定可以执行哪些操作。
- 会话：管理 Cookie、Token、过期、刷新、撤销与安全保存。
- 业务规则：判断请求是否满足服务端条件。
- 风险验证：平台可能要求额外验证，不能假设一次成功后永远成功。
- 结果确认：验证账号、资源或业务状态是否真正改变。

接入原则：
1. 优先官方 API、OAuth/OIDC、SDK 和平台支持的授权方式。
2. 不把浏览器会话凭证当成可任意复制、共享的通用令牌。
3. 不在日志、抓包文件或模型提示中暴露密码、Cookie、Token、验证码和密钥。
4. 对身份验证及平台要求的人工确认，按官方流程处理。
5. 不把绕过访问控制、伪造身份或规避安全机制作为通用自动化目标。
6. 每个能力记录权限要求、凭证保管方式、撤销路径与风险等级。

九、双电脑与多智能体协作

跨设备任务必须有明确的通信协议与执行状态，而不是让两个 AI 不断猜测对方进度。

每个任务至少记录：task_id、唯一执行标识、目标设备、所需权限、输入参数、预期结果、消息发送/接收/确认状态、开始时间、截止时间、重试次数、执行日志、错误分类和结果证据。

重点验证：
1. 设备离线或断网时能否恢复。
2. 重复消息是否会导致有副作用的操作被重复执行。
3. 执行器是否遵循最小权限原则。
4. Windows 安全、UAC、防火墙或应用权限阻止操作时，系统能否明确报告原因。
5. AI 未收到结果时，是否先查询任务状态，而不是直接重复执行。
6. 任务能否暂停、续跑、取消和审计。

十、资源发现与能力扩展

资源获取、价值判断和工程验证分开处理：
A. 多源获取：发现代码仓库、论文、文档、协议、模型、数据集与服务，保存来源和时间。
B. 关联发现：不只按关键词或星标筛选，还建立跨领域关系，发现低热度候选。
C. 缺口识别：从任务失败、用户需求和工具限制中提出研究问题。
D. 受控实验：检查许可证、依赖、维护情况和风险，再在隔离环境测试。
E. 能力注册：记录用途、调用方式、输入输出、权限、依赖、版本、验证结果、成本和失败模式。
F. 持续复评：系统能力或任务需求变化时，重新评估此前低优先级资源。

十一、核心闭环

观察外部世界
→ 获取资源与通信证据
→ 保存来源和原始证据
→ 建立索引、关系和能力图谱
→ 识别任务与能力缺口
→ 选择访问方式并制定方案
→ 在授权和受控环境中执行
→ 观察状态、通信与业务结果
→ 诊断失败或验证成功
→ 将有效方案注册为能力
→ 通过真实任务反馈继续改进。

失败不只是重试信号，也是发现能力缺口和学习新知识的输入。

十二、实施路线图

阶段 0：现有项目盘点
- 对照仓库、项目总纲、代码和测试，形成“已实现 / 部分实现 / 缺失 / 未验证”能力映射表。

阶段 1：建立可观测性
- 为现有任务链增加统一任务 ID、结构化日志、时间戳和明确状态。
- 区分成功、失败、结果未知和等待人工确认。
- 选一个无风险任务复现正常流程与可控失败。

阶段 2：抓包与协议分析
- 在自有设备和获准环境使用 Wireshark 与浏览器 Network 面板。
- 学会区分 DNS、连接、TLS、HTTP、应用状态和业务结果。
- 将通信记录与执行日志按时间及任务关联。

阶段 3：网络诊断原型
- 先支持结构化日志和浏览器请求记录，再按需要增加 PCAP 元数据解析。
- 为常见错误提供证据、置信度和下一步建议；第一版不追求支持所有协议。

阶段 4：统一服务接入与会话管理
- 建立能力描述、访问方式、授权要求、错误模型和结果验证契约。
- 优先接入官方 API、SDK 与公开服务。
- 明确凭证安全、权限范围和人工确认机制。

阶段 5：跨设备可靠执行
- 统一消息协议、任务状态、确认机制、幂等性、超时、恢复和审计。
- 在两台电脑上受控测试断网、权限拒绝、超时和结果丢失。

阶段 6：多源发现与能力转化
- 将资源发现系统与真实任务的能力缺口关联。
- 通过隔离实验，把外部资源转成已验证适配器。

阶段 7：持续扩展与受控自我改进
- 自动发现候选能力、生成适配器草案、运行测试并生成证据报告。
- 对高风险权限、外部写入和生产变更保留人工审批。

十三、首批验证任务

任务 A：双电脑消息传递
A 发送任务，B 确认接收并执行一个无副作用动作，再返回结果。模拟正常、超时、断网和重复消息，验证系统能否区分失败与结果未知。

任务 B：自有测试网站诊断
访问自建页面，记录请求、响应、重定向、应用日志和最终状态。制造一个可控参数错误或权限错误，检查诊断是否准确。

任务 C：API 与浏览器方式对照
对同一项允许执行的读取任务，比较官方 API 与浏览器方式的耗时、稳定性、日志完整度和维护成本，形成访问方式选择规则。

任务 D：从故障转为能力
将可复现故障记录为：现象、证据、原因、修复、适用条件和回归测试；验证下次遇到相同问题时能否复用。

十四、评价指标

不以抓包数量、仓库数量、工具数量或重试次数作为主要成绩。建议追踪：
- 端到端任务成功率；
- 失败原因可定位率；
- 结果未知状态的识别准确率；
- 平均诊断时间与平均恢复时间；
- 重复执行造成的副作用；
- 新接入能力验证通过率；
- 能力跨任务复用率；
- 低热度资源有效发现率；
- 每项有效能力新增的时间与算力成本；
- 凭证泄漏、越权与未授权操作事件。

十五、安全与工程原则

1. 先观察和理解，再改变行为。
2. 优先使用正式接口和支持的访问路径。
3. 在自有或获准环境中测试。
4. 最小权限，凭证加密保存，日志脱敏。
5. 不把绕过身份验证或访问控制作为通用目标。
6. 有副作用的操作考虑幂等性、状态查询与人工确认。
7. 自动诊断区分事实、推测与未知。
8. 新适配器先隔离测试，再审批注册。
9. 保存失败结果，避免重复踩坑。
10. 长期架构决策以仓库事实和可复现实验为依据。

十六、当前优先级

第一：让现有执行链可观测、可复现，区分失败与结果未知。
第二：学习并应用抓包、HTTP、TLS、会话、授权和跨层故障诊断。
第三：把网络诊断与能力注册、任务调度和跨设备协作连接起来。
第四：根据真实任务缺口扩展资源发现、协议支持和外部能力融合。
第五：逐步建立受控的自主研究、适配器生成、测试与注册闭环。

这些优先级不代表暂停资源发现或能力融合，而是让扩展有证据、有接口、有验证，减少系统对盲目尝试的依赖。

十七、终局判断

当天网能够发现外部资源，理解其公开能力和访问条件，选择合适的 API、协议客户端或界面自动化方式，跨设备执行并记录完整状态，通过通信证据和应用日志解释失败，将验证过的解决办法注册为可复用能力，并在安全、授权和人工监督边界内持续扩展，它就开始具备通用智能基础设施的特征。

最终方向：
网络随处可到，网络随处可用，网络随处可查，网络随处可解。

借天下融入己身。以证据理解系统，以能力解决问题，以反馈推动进化。
