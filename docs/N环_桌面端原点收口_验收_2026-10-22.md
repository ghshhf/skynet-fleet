## 三、改了什么（两处，均最小改动）

### 3.1 `ui/app.css`：新增 `--accent-solid`，修 dark 主题实心按钮对比度

**问题**：`#vvSend`（语音视图发送按钮）白字 `#ffffff` on `#5b8def` = **3.23**，需 4.5。

**根因不是单个按钮，是一类用法**：全站「实心 accent 底 + 白字」共 4 处，都直接吃 `--accent`。
- light：`--accent:#2f6bd8` + 白字 = **4.98** ✅（本来就达标）
- dark：`--accent:#5b8def` + 白字 = **3.23** ❌（同一变量既要当文字色、又要当按钮底色，两个场景对亮度的要求相反）

axe 当时只报 1 处，是因为另外 3 处（`.cbtn.send` / `.badge.ask` / `.apprrow .hbtn.yes`）此刻未渲染——**只修报错的那一个，等消息发出来、审批弹窗弹出时会再冒红**。

**改法**：把「实心底色」从 `--accent` 里拆出来，独立成 `--accent-solid`：

| 主题 | `--accent`（文字/边框/描边用） | `--accent-solid`（承载白字用） | 与白字对比度 |
|---|---|---|---|
| light | `#2f6bd8` | `#2f6bd8`（不变） | 4.98 |
| dark | `#5b8def`（不变） | `#3b6fd4`（压暗） | **4.76** |

`#3b6fd4` 是逐档算出来的：`#4a7de0`=3.96 不够、`#3b6fd4`=4.76 过线且色相最接近原色（视觉偏移最小），留 0.26 余量防色值微调。

替换的 4 处：`.cbtn.send`、`.badge.ask`、`.apprrow .hbtn.yes`、`.vv-send`。
**主色 `--accent` 一个字节没动**——按钮以外的地方（链接、选中态、进度条）视觉零变化。

**同根因的另外两批（axe 没报，但真不达标）**：

修完 `#vvSend` 后，用一次性脚本把全站「文字色 vs 实际底色」逐元素算了一遍（含 axe 会跳过的隐藏元素）。查出 axe 漏报的真问题——它们此刻没渲染，但一旦出现就不达标：

| 元素 | 原值 | 现改 |
|---|---|---|
| `.badge.se`「副作用」 | `--warn` #c98a00 + 白字 = **2.95**（dark 2.28） | `--warn-solid` #8a5d00 = **5.76** |
| `.badge.deny`「破坏性」 | `--danger` #d8453c + 白字 = **4.34** | `--danger-solid` #c0332a = **5.60** |
| `.badge.ok` | `--ok` #1f9d55 + 白字 = **3.49** | `--ok-solid` #147a41 = **5.40** |
| `#apprFlag`「N 项在等审批」 | `--warn` 文字 on 浅底 = **2.66** | `--warn` 加深 = **5.76** |
| `.cbtn.mic.on` / `.voicebar .mic` / `.vv-mic.rec` / `.tb-win i.close:hover` | `--danger` + 白字 = 4.34 | `--danger-solid` = 5.60 |
| `.sb-foot .ava` `#personaAva` | `--accent` + 白字 = 3.23（dark） | `--accent-solid` = 4.76 |

做法与 accent 同构：`--warn/--danger/--ok` **保留作文字色**（深色主题下还调亮了：#e0b44c / #f0756c / #4ec97f，深底上 8.60 / 5.95 / 7.95），另立 `--warn-solid/--danger-solid/--ok-solid` 专供「背景 + 白字」。

复扫后剩余不达标项：**0 条真实文本**（只剩 4 条误报，见 §七）。

### 3.2 `tools/uicheck/clickaudit.js`：修「覆盖率假低」

**症状**：死链 0，但覆盖率只有 **81%**，工具自己警告「未测到的不能算没问题」。19 个跳过里 14 个是同一句「元素已不在 DOM」。

**根因（实测定位，不是猜）**：`.tab`（专家/技能/连接器/声音）本身是要被测的元素，点它会 `loadAssetTab()` 把 `#tabBody` **整个换掉**——卡片墙连同 16 个「切换到这张」一起消失。而该相位的 `restore` 只切 `.view` 的 class、**从不复位 tab**，于是点过 tab 之后，该相位剩下的卡片按钮全部查不到，记成「不在 DOM」。

一次性探测脚本实测证据：直接点「切换到这张」后 DOM 完全不变（16 个按钮原位、视图仍是 viewAssets、遮罩 0），所以问题不在按钮本身，而在**相位内 tab 状态漂移**。

**改法（三处）**：
1. 相位 `setup`：进入时强制把 tab 复位到「专家」（`data-tab="cards"`），相位初始态确定，本轮测什么不再取决于上一轮留在哪；
2. 相位 `restore`：仅在 tab 真被切走时点回来（未切则不重渲染，标记仍保住）；
3. 命不中元素时**不再直接判死**：回相位初始态 + 轮询重枚举（最多 6 秒），按「签名 + 同签名序号」把元素找回并**重建整批标记**；确实找不回才记「不在 DOM」并注明已重试。

**效果**：有反应 113 → **130**，跳过 23 → **7**，覆盖率 81% → **92%**。

> 为什么轮询而不是固定等：`useCard` 会先把 `ASSET_CACHE.cards` 置空再重新拉接口。固定等 300ms 时枚举到的是空壳（实测重枚举只剩 12 个、目标 0 个），等 900ms 也不够。轮询到目标签名出现为止才是对的判据。
