## 0. 结论先行（9 条）

1. 🔴 **原结论 13 被推翻：有两个站真的能程序化拉卡。**
   - **`aicharactercards.com`**：公开 JSON API，`GET /api/cards/{id}/download` 直接返回**真 PNG 卡文件**（实测 968KB、457KB）。
   - **`character-tavern.com`**：下载的 JSON 是**标准 `chara_card_v2`**，PNG 是**标准 `chara_card_v3`**。
   ⇒ 「卡库浏览器」这个原结论要重开。但**「卡库」和「拉取器」是两件事**（见结论 5）。
2. 🔴 **但真拉到卡之后，本仓读不懂其中一类。**
   `aicharactercards` 的卡 **`spec = "aicc_card"`**（私有 schema），
   字段名是 `general_description` / `appearance` / `background_history`，**不是** `description` / `personality`。
   本仓 `load_card()` 走「V1 顶层平铺」分支 ⇒ 静默降级 ⇒ `build_system()` 只吐出 **47 字**的「你现在扮演『她』」。
   **卡内容全部丢失，而且不报错。** 这是本仓现存最典型的「静默失败」。
3. 🔴 **修法很便宜**：那套私有 schema 与 SillyTavern 字段**语义一一对应**，
   加一个 30 行的**适配器**就能接。实测它的 `world.worldbook_entries[]` **完全是标准 SillyTavern 世界书格式**
   （`keys`/`secondary_keys`/`selective`/`insertion_order`/`constant`/`enabled`/`use_regex`/`position` 全齐），
   ⇒ **只有外壳不同，内核通用**。
4. 🔴 **`ClawHub` 不是角色卡站，是技能/插件市场。** 实测 `GET /api/v1/skills?limit=3` 返回
   `{ownerHandle, slug, displayName, summary, tags, stats:{downloads,installs,stars}}`。
   ⇒ 主人的转述把它归入「角色卡分享平台」有误。**但这个发现对本仓价值更大**（见结论 8）。
5. 🔴 **「卡库」与「拉取器」必须分开做。**
   - **拉取器**（`card.fetch` 能力）：只做「给定一个 ID/URL → 下载 → 落盘 → 体检 → 报告」。
     **零界面、零依赖、纯函数**，完全符合本仓路线。**这个该做。**
   - **卡库浏览器**（可视化商店）：要标签筛选、要预览、要几万张卡的列表 ⇒ 要索引、要缓存、要分页、要 UI。
     **这是社区红海，且本仓是个人使用 ⇒ 不做。**
6. **「图片 CDN」≠「卡文件 CDN」。** 实测 `character-tavern` 的图片桶
   `ct-cards.storage.character-tavern.com/{作者}/{卡名}.png` 可以无鉴权直下，
   🔴 **但下到的是纯图片，没有 tEXt 卡块**——本仓 `load_card()` 报「PNG 里没有角色卡块」。
   真正的卡数据在服务端 DB，只能走它的导出功能。**⇒ 「能下到 PNG」不等于「能下到卡」。**
7. **下载有冷却。** `aicharactercards` 的 `/download` 对同一张卡有 **30 分钟**冷却
   （第二次请求返回 `{"error":"Duplicate download","message":"You already downloaded this card recently. Please wait 30 minutes."}`）。
   ⇒ 真要做拉取器，**必须缓存 + 限速**，否则主人多点两下就报错。
8. 🔴 **ClawHub 的技能市场形态，正是本仓 `fleet/skills.py` 的天然上游。**
   本仓的技能装在 `skills/` 与 `~/.workbuddy/skills/`，认 `SKILL.md` + frontmatter。
   ClawHub 的 `skills` API 返回 `ownerHandle/slug/displayName/summary/tags/latestVersion`，
   **和本仓 `skills.py` 认的 frontmatter 字段几乎一一对应** ⇒ 可直接做「从技能市场装技能」。
   这比「装角色卡」更值钱：**技能是方法论，角色卡只是数据。**
9. **Chub / JanitorAI / CharacterHub 实测不可程序化拉**（见 §2），
   **Discord 中文社区**（尾巴镇 / 类脑 / 旅程）**无公开 API、且类脑与旅程要答题验证或 8 天缓冲期**
   ⇒ 主人转述里「国际聚合站 + 中文 Discord」这个分类是对的，但**可程序化性差别极大**。

## 1. 实测方法（口径先说清，避免「我以为」）

**不用 `curl` 猜 API 路径**——这几个站全是 SPA，猜路径只会拿到 HTML。
**用真浏览器抓网络请求**（Playwright + Chromium，与本仓 `tools/uicheck` 同一套工具链），
再对抓到的真实端点用 `curl` 复现。

> 🔴 踩坑记录（值得留档）：
> ① `curl https://aicharactercards.com/api/characters` 拿回的是 `<!DOCTYPE html>`——**页面路由不是 API 路由**。
> ② Node 里 `require('/d/tools/...')` 报 `MODULE_NOT_FOUND`——**Git Bash 路径 Node 不认**，
>    必须写 `D:/tools/uitools/node_modules/playwright`。
> ③ `r.headers()['content-type']` 对某些响应返回 `undefined` ⇒ `.split()` 直接抛。
>    **探针脚本自己会炸**——这跟本仓「门禁自己也会骗人」是同一类病。

### 2.1 aicharactercards 的真实端点（实测）

```
GET  https://api.aicharactercards.com/api/cards/home
GET  https://api.aicharactercards.com/api/cards/trending?period=7d&nsfw=all&skip=0&limit=12
GET  https://api.aicharactercards.com/api/cards/{id}          → 单卡详情 JSON
GET  https://api.aicharactercards.com/api/cards/{id}/download  → PNG 卡文件（实测 457KB / 968KB）
```

列表 JSON 已含 `id` / `title` / `description` / `excerpt` / `userId` 等字段，**够做标签筛选与搜索**。
`trending` 返回 `total: 664`（7 天窗口），说明**有分页可翻**。

### 2.2 character-tavern 的真实端点（实测）

- 卡片列表页 `https://character-tavern.com/search/cards`（SSR，服务端渲染）
- 卡片详情页 `https://character-tavern.com/character/{作者}/{卡名}`
- 图片 CDN：`https://ct-cards.storage.character-tavern.com/{作者}/{卡名}.png`（Cloudflare R2，**无鉴权直下**）
- 🔴 **但导出必须走浏览器端**：详情页有两个按钮
  「Download character card PNG. Works in SillyTavern.」和「Download as JSON」，
  实测**都是前端 JS 在内存里生成文件**（点它会触发 Playwright 的 download 事件，不是发 HTTP 请求）。
  ⇒ **纯 HTTP 客户端拿不到卡，只能上无头浏览器。**

### 2.3 aicharactercards 的私有 schema（实测字段树）

```
spec = "aicc_card", spec_version = "1.0"
data:
  name                str
  general_description str   ← 对应 SillyTavern 的 description
  appearance          str
  personality         dict { core, behavior_rules[], speech_style{} }
  background_history  str
  world_setting_context str
  dialogue            dict { greetings[], dialogue_examples[], group_only_greetings[] }
  prompts             dict { system_prompt, post_history_instructions, depth_prompt{} }
  world               dict { worldbook_name, worldbook_entries[] }   ← ⭐ 内核是标准 ST 格式
  metadata            dict { card_format, char_ui_name, creator, notes, version, tags[], features{} }
```

🔴 **关键观察**：`data.world.worldbook_entries[]` 的每个条目是**完全标准的 SillyTavern 世界书条目**：

```json
{"comment": "...", "constant": false, "content": "...", "enabled": true,
 "extensions": {"case_sensitive": false, "depth": 4, "position": 1, "priority": 10, ...},
 "id": 0, "insertion_order": 10, "keys": ["Ribarevo","village","Danube"],
 "position": "after_char", "secondary_keys": [], "selective": false, "use_regex": false}
```

⇒ **本仓的 `world_book_entries()` / `match_world_book()` / `_entry_hits()` 全部能直接吃这些条目。**
适配只在外壳层（把 `general_description` 映射成 `description` 等）。

### 2.4 本仓读 aicc 卡的真实下场（实跑）

```python
d = pc.load_card("card3813.png")
d["_spec"]   == "aicc_card"       # 不是 v2/v3
d["description"] is None            # 字段名不对 ⇒ 读不到
len(pc.build_system(d)) == 47       # 只有「你现在扮演「她」，对方是「主人」。」
```

**根因**（`persona_card.py:127-136`）：
```python
if spec in ("chara_card_v2", "chara_card_v3"):
    data = obj.get("data")
else:
    data = dict(obj)      # ← V1 顶层平铺分支：把 {"spec":..,"data":{...}} 当成平铺卡
```
⇒ `aicc_card` 落进「V1 平铺」分支，**`data` 成了外层 dict 的一个键**，真正的卡内容在 `d["data"]` 里没被取出。
**不报错、不告警、拼出空人设。** 这是本仓「静默失败最阴」的教科书案例。

## 4. 修正上一轮调研的两条结论

| 原结论 | 原文 | **实测后** |
|---|---|---|
| 结论 13 | 「程序化拉取**只推荐 GitHub 公开仓库**」 | 🔴 **过保守**。`aicharactercards` 有公开 API 且能下卡文件；`character-tavern` 的卡是标准格式 ⇒ **至少这两个可以作为拉取源** |
| 结论 15 | 「要做卡库浏览器吗？建议**先不做**……更该做卡的安全体检器」 | 🟡 **要拆开看**。「**卡库浏览器**」（可视化商店、标签筛选、预览）**仍然不做**（个人使用 + 社区红海 + 索引成本高）；但「**拉取器**」（给定 ID/URL 下载并体检）**该做**，且它正好是体检器的**上游入口**——先拉进来，才有东西可体检 |

**结论 15 的原意（先做体检器）仍然成立**，而且**现在更站得住了**：
体检器的输入就是「拉进来的外来卡」，而**外来卡源刚刚被证实是真实存在且可程序化获取的**。

## 6. 明确不改的（本仓的既有立场 reaffirmed）

1. **卡不进模型权重**——它是运行时 prompt 插件。主人这条判断与本仓 E-7 铁律天然一致。
2. **「卡是数据不是指令」的外框不放开**——体检器只**标记**，拦截权在人手里。
3. **不绕鉴权**——Chub/JanitorAI 需登录，我们不做程序化拉取，也不自造凭据路径。
4. **不做可视化商店**——个人使用场景，社区红海。
