## 一、先说结论：「合成不太行」的真因不在模型

今天在本机逐段实测，四条原因按**影响**排序（第 4 条我原本以为是主因，实测后被数据否掉，如实列在最后）：

### 真因 1：一句一个腔调，没有情绪（影响最大）

`edge_tts==7.3.1` **不开放 style 参数**（要走 SSML，库没放开）。`voice.py` 的注释里已经写明这件事：

```python
# edge-tts 7.3.1 只支持 rate / volume / pitch，不开放 style
```

能调的只有 **音色 / 语速 / 音调 / 音量**。这四样改变的是「谁说、说多快、多高、多响」，
**改不了「用什么语气说」**。所以无论提示词写得多有情绪，念出来永远是播音腔 ——
这是「不像人」的最大来源，且**换提示词解决不了**。

### 真因 2：整段落盘，长句先愣一下才出声

当前链路：`edge_tts.Communicate(...).save(mp3)` → ffmpeg 转 wav → winsound 播放。

`.save()` 是**把整段音频全部下载完才返回**。实测一句 4.30 秒的话，从发出到出声要等整句合成完。
而调研记录过 edge 的**首包是 0.916s**（短句）/ 1.342s（长句）—— 这个流式能力现在被浪费了。
听感上就是「说完之后要顿一下才有回应」，这是「不太好用」的重要来源。

### 真因 3：音色池只用了一半，而且全是播音腔

今天 `edge_tts.list_voices()` 实测：**中文音色有 14 个**

| 类别 | 音色 |
|---|---|
| 普通话女 | `Xiaoxiao` / `Xiaoyi` |
| 普通话男 | `Yunjian` / `Yunxi` / `Yunxia` / `Yunyang` |
| 方言女 | **`liaoning-Xiaobei`（辽宁）/ `shaanxi-Xiaoni`（陕西）** |
| 港澳台 | zh-HK 3 个 / zh-TW 3 个 |

而 `VOICE_PROFILES` 里实际接的只有 5 个左右，`Xiaoyi`、`Yunxia`、两个方言**都没接**。
方言音色是有生活气的，正好补「播音腔」这个短板。

### 真因 4（已被数据否掉，不再当理由）：降到 16kHz 播放

我原以为「mp3 是 24kHz，播放链路 `ffmpeg -ar 16000 -ac 1` 砍到 16k，音质发闷」是主因。
实测一句正常中文的频谱能量分布：

| 频段 | 能量占比 |
|---|---|
| 0–4 kHz | **97.8%** |
| 4–8 kHz | 1.5% |
| 8–12 kHz | **0.7%** |

⇒ 降到 16k 丢的是那 **0.7%**。能量上微不足道，**不能算主因**。
（听感上高频影响清晰度，但拿这个当「不太行」的解释就是自欺。）
真要改也不难（播放保持 24k，ASR 仍用 16k），但优先级排在 1/2/3 之后。

## 二、语音端：双轨设计

两条路都要，**按场景切换**，不是二选一。

| | 云端轨（默认，质量优先） | 本地轨（离线，隐私优先） |
|---|---|---|
| 现在 | edge-tts，免费无 key | 无（kokoro 未装，且中文弱） |
| 能升级到 | **Azure 官方 TTS**（支持 style/情绪，要 key）/ 豆包、MiniMax（音色更活，付费） | **sherpa-onnx + Piper 中文**（64MB，CPU 可跑） |
| 质量 | 高（晓晓本身很自然） | 中（能听懂，但不如云端自然） |
| 代价 | 要网络；Azure 要 key 和额度 | 要下载权重；RTF 必须本机重测 |
| 判据 | 同一句话 A/B 盲听 | RTF < 0.3 且能听懂 |

🔴 一条硬事实（已有调研，本机无独显）：**CosyVoice2 4.6GB / Qwen3-TTS 2.4GB / IndexTTS2 5.6GB 都不合适**，
CosyVoice 还会把 `transformers` 钉回 4.51.3，威胁现有北极星链路。**"换个大模型"这条路在本机走不通。**

### 建议的落地顺序（每步都能单独验收）

| 步骤 | 做什么 | 预期收益 | 依赖 |
|---|---|---|---|
| V1 | 音色池 5 → 14（含辽宁/陕西方言），按角色卡分配 | 立刻不"播音腔" | 无 |
| V2 | 改**流式**：边收边播，不等整段 | 首声从「整句时长」降到 ~1s | 无 |
| V3 | 播放链路不再降到 16k（ASR 仍 16k） | 高频不闷（小改善） | 需 ffmpeg |
| V4 | 接**一个**带情绪的云端 TTS（Azure 或豆包，二选一） | 真正有语气 | 要 key |
| V5 | 本地轨：sherpa-onnx + Piper 中文，本机测 RTF | 断网也能说话 | 要下权重 |

> V1–V3 是**白捡**（不花钱、不加依赖、不改架构）。V4 需要你决定用哪家、给不给 key。
> V5 不急，等云端轨稳定后再做「离线兜底」。

## 三、AI 双轨：本地与云端

现状已经有了（不是从零做）：`fleet/ai_backends.py` 里云端有 `pollinations` / `ovh` / `gateway1`，
本地有 `FLEET_LLM_URL`（OpenAI 兼容端点）。今天实测云端三路都通。

你说「电脑差的时候只能用云端，再通过提示词注入去检测」——现状已经接近，缺的是**选择策略**：

| 场景 | 走哪条 | 怎么判 |
|---|---|---|
| 本机有可用本地模型（显存/内存够） | 本地优先 | `FLEET_LLM_URL` 探活成功 |
| 本机没有 / 太慢 | 云端优先 | 探活失败或首字节 > 阈值 |
| 断网 | 本地兜底；都没有就明确说「现在没法回答」 | 不许假装成功 |

**提示词注入**已在用（`persona.system_prompt()` 拼角色卡 + 状态 + 世界书）。要补的是：
把「当前是本地还是云端、这个模型擅长什么」也注入进去，让回答风格随算力变化时**有自知**，
而不是云端答得很聪明、切本地突然变傻却不解释。

## 四、手机控电脑（桌面智能体）

### 现状：能力齐，入口缺

PC 端已有（今天 `/api/health` 实测）：**12 台设备 / 87 项能力**，包括桌面操控、窗口、剪贴板、应用、截图、键鼠。
W2 已做好审批闸门（有副作用的能力要主人点确认）。

缺的是**手机端的入口**：现在手机只能说话/听话，说不出「帮我把 Chrome 打开」然后真的打开。

### 要做的事

1. 手机端加「让它动手」入口（语音或按钮）
2. 指令 → PC 的 `ai.chat` 带工具意图 → 走 `registry.call` → 审批 → 执行 → 回报
3. **跨设备审批**：现在审批弹窗在 PC 上。手机发起时，确认应该在**手机**上点（你人在外面，看不到 PC 屏幕）

### 安全边界（必须先定，不能事后补）

| 问题 | 建议 |
|---|---|
| 手机能调哪些能力 | 白名单，先只给「无害可逆」的（打开应用、调音量、截图）；删除/关机/改系统设置一律不给 |
| 谁批准 | 手机发起 → 手机批准；PC 上同时弹一条「手机正在请求操作桌面」 |
| 误触怎么办 | 危险动作二次确认 + 可撤销 |
| 日志 | 每次手机发起的操作都进 `fleet_audit.jsonl`，手机上能查 |

## 五、排期（按你说的"一轮语音、一轮组网+手机"）

### 第一轮：语音端（V1–V3 白捡 + V4 待你定）
