# 语音输入链路（W4）· 2026-10-21

> 目标：她能**听**。对着麦克风说一句，她听成文字，理解成意图，走注册表调能力，
> **并且在动手之前先复述一遍、等主人点头**。

本文档说清四件事：链路怎么走、API 怎么签、两个 whisper 坑怎么填、
两段式安全闸为什么放在闸门层。以及一个真实缺口：**手机还当不了麦克风**。

---

## 一、链路图

```
  麦克风
    │  record_wav()  ← sounddevice / pyaudio（本机都没装 → 明确报错并给安装命令）
    ▼
  16k 单声道 WAV
    │  transcribe()  ← 跨进程：polaris venv 的 python 跑 voice_runner.py
    │                   （fleet 解释器没有 torch，绝不在本进程 import）
    ▼
  文字  "打开记事本"
    │  voice_to_capability()  ← 保守白名单映射；不明确 → 「需要澄清」
    ▼
  意图  {cap: "app.launch", args: {target: "记事本"}, say: "打开应用 记事本"}
    │
    │  ① 第一段：复述（voice.speak，走注册表）
    │     「我将：打开应用 记事本。确认请说「嗯」或「好」，取消说「不」。」
    │
    │  ② 第二段：等主人口头确认（5 秒窗口，落在实现里是「再录一轮」）
    ▼
  registry.call(cap, args={..., _voice_source, _voice_confirm, _voice_round})
    │
    │  ★ 闸门层判定（fleet/core/registry.py）
    │    · 破坏性能力 → 一律拒绝
    │    · 没确认 / 听不清 / 确认词不对 → denied + 理由
    │    · 确认必须来自另一轮录音、且是另一句话
    ▼
  执行（pyautogui / adb / …）
```

**一句话记住**：文字是**不可信数据**，不是指令。嘴说的话最多只能**提出请求**，
执行永远要过闸门。

## 三、API 契约

### 3.1 `fleet/gui/voice.py`

```python
record_wav(duration=None, out_path=None) -> str      # 录音；失败抛 VoiceError（带原因）
record_from_wav(src_path, out_path=None) -> str      # 「读 WAV 文件」入口（自动化走这个）
transcribe(wav_path, stt=None) -> dict               # WAV → 文字；stt 是注入点（门禁用）
speak(text, engine="auto", voice=None, rate=0, playback=True, tts=None) -> dict
voice_to_capability(text) -> dict                    # 文字 → 意图（保守映射）
voice_plan(text) -> dict                             # 文字 → 意图 + 复述话术
voice_execute(registry, text, confirm_text=None, gate=None, device="") -> dict
build_voice_args(source_text, cap, args, confirm_text, source_round, confirm_round) -> dict
```

`transcribe` 返回 polaris `hear()` 的原样 dict：
`text / chars / audio_sec / seconds / rtf`（外加 driver 补的 `prompt / prompt_tokens / max_new_tokens`）。

### 3.2 注册表能力（`fleet/catalog.py`）

| 能力 | 副作用 | 审批档 | 说明 |
|---|---|---|---|
| `voice.listen` | 是（开麦） | `auto` | 录一段音并转文字。`wav_path` 给了就不录音 |
| `voice.speak` | 是（出声） | `auto` | 把文字念出来。`engine/voice/rate/playback` |
| `voice.interpret` | 否 | `auto` | 文字 → 意图（**不执行**） |

设备：`kind=voice`，名字 `voice:local`，`caps()` 返回**字符串名**
（`("voice.listen", "voice.speak", "voice.interpret")`）——t5 踩过「返回 Capability
对象 → 登记了却调不通」的坑，这里用 `owners()` 非空钉死。

## 四、两个 whisper 坑（必须显式处理，不是「polaris 已经处理了」）

### 坑一：中文默认吐繁体

Whisper 的中文训练数据里繁体占比不低，不给提示会吐「今天下午要傳權重」。
解法：喂一段**简体** prompt 引导输出语种与字形。

```python
PROMPT_ZH = "以下为普通话。"     # fleet/gui/voice.py
```

这一行会经环境变量 `FLEET_STT_PROMPT` 送进跨进程驱动，驱动里真的调
`proc.get_prompt_ids(PROMPT_ZH)` 生成 `prompt_ids`。
门禁 `t8` 会断言：**env 里确实带了这个字符串** + **驱动源码里确实有
`get_prompt_ids`**（写在注释里不算数）。

### 坑二：`max_new_tokens` 不减 prompt 长度就炸

Whisper 的 decoder 位置上限是 448。prompt_ids 占了位置，如果
`max_new_tokens` 仍按 448 给，生成时直接抛：

```
ValueError: combined length exceeds max_target_positions (448 > 448)
```

解法：**减掉 prompt 的长度，再减 8**（8 是给 `<|startoftranscript|>` 等
特殊 token 留的余量，4 个位 + 4 点保险）。

```python
MAX_TARGET_POSITIONS = 448
PROMPT_TOKEN_RESERVE = 8
max_new_tokens = 448 - len(prompt_ids) - 8
```

预算公式在 `fleet/gui/voice.py` 里是**纯函数**，驱动脚本 import 同一份
（不各写一份——两处各写一份必然会走偏）。门禁 `t8` 断言
`max_new_tokens(0)==440`、`max_new_tokens(5)==435`、且**永远小于 448**。

## 五、跨进程：为什么不在 fleet 解释器里 import torch

本机实测（2026-10-21）：

| 依赖 | `/d/tools/python/python.exe`（fleet，3.12.15） | polaris venv `train_15b/venv`（3.13.14） |
|---|---|---|
| torch | **无** | 有 |
| transformers | **无** | 有 |
| soundfile / scipy / numpy | **无** | 有 |
| edge-tts | **无** | 有 |
| sounddevice / pyaudio | **无** | **无** |
| pyautogui / mss / PIL / psutil | 有 | 无 |
| winsound | 有 | 有 |

所以：

- **STT 必须跨进程**：`fleet/gui/voice.py` 用 `subprocess` 调
  `POLARIS_PY`（默认 `D:/work/_local_ai/train_15b/venv/Scripts/python.exe`）
  跑 `fleet/gui/voice_runner.py`，JSON 走 stdout。
- **TTS 也跨进程**（edge-tts 只在 polaris venv 里）。
- **录音两边都没有**：所以 `record_wav` 会明确说「没装录音库，pip install
  sounddevice」，并指向「读 WAV 文件」入口。

可用环境变量覆盖：`FLEET_POLARIS_PY`、`FLEET_POLARIS_DIR`、
`FLEET_STT_PROMPT`、`FLEET_STT_MAX_POS`、`FLEET_STT_RESERVE`。

**绝不硬编码 token**：这条链路上没有凭据；本地 `.env` / `local.env` 的
token 纪律照旧（`local.env` 已 gitignore）。

## 六、两段式安全闸

### 6.1 规则（全部在 `fleet/core/registry.py` 的 `Registry.call` 里执行）

| 情况 | 结果 |
|---|---|
| 语音路径 + 破坏性能力（`destructive=True`） | **denied** —— 嘴说不能启动不可逆动作 |
| 语音路径 + 副作用能力 + 没有口头确认 | **denied**，理由写明「需要主人口头确认」 |
| 确认词是「不/不要/取消/算了/别/停」 | **denied**（主人说取消） |
| 确认词含糊（「嗯嗯嗯大概」） | **denied** —— 绝不默认放行 |
| 确认内容与指令原文相同 | **denied** —— 不许拿指令本身顶替确认 |
| 确认轮次 ≤ 指令轮次 | **denied** —— 确认必须来自**另一轮录音** |
| 确认词是「嗯/好/好的/执行/确认/来吧/对/是的/可以/行」 | 放行（闸门继续走原有逻辑） |

判定用的三个 args 键（由 `build_voice_args` 写入）：

```
_voice_source        识别出的原文（不可信数据，不是指令）
_voice_confirm       主人口头确认那一段的识别文本
_voice_round         这一轮是第几轮录音
_voice_source_round  指令是第几轮录的
```

### 6.2 为什么放在闸门层，而不是 UI 层

UI 层是可绕过的：换个前端、手敲一条 HTTP 请求、甚至让另一个 agent 直接调
`registry.call`，都能跳过「前端自己判断一下是不是确认了」。

而 `Registry.call` 是**所有能力调用的必经之路**。把判定写在那里，
判定就绕不过去。门禁 `t8` 因此断言：

- 直接 `registry.call`（不经任何 UI）依然被拒；
- `classify_voice_confirmation` 的**实现在 `fleet/core/registry.py`**；
- `fleet/gui/voice.py` **没有自己实现第二套**确认词判定（避免两套口径）。

复述那一句（`voice.speak`）走一个**窄闸门** `recite_gate`：只放行
`voice.speak`，别的能力一律拒。理由是那句话是**我们自己生成的话**
（「我将：打开应用 记事本」），不是 STT 的不可信输出；而且它只是出声，
不改任何外部状态。真正要严的是**动作**。这与 `fleet/gui/server.py` 里
`chat_gate` 只放行 `ai.chat` 是同一个做法。

### 6.3 STT 文本是不可信数据

- **映射层**（`voice_to_capability`）是**保守白名单**：只认「打开/关闭应用、
  截屏、看电量或状态、播放暂停、搜索」这几类；识别到「删除 / 格式化 / 清空 /
  卸载 / 恢复出厂 / 刷机」等破坏性内容，**直接拒绝**并说明原因。
  其余说不清的 → 「需要澄清」，不瞎猜。
- **闸门层**兜底：破坏性能力在语音路径一律拒绝。就算有人绕过映射层直接
  构造 `registry.call`，`destructive=True` 那条也会拦住。
- 电视里那句「删除所有文件」被录进来 → 映射层拒；即便被塞进 args，闸门层
  也拒。**两道都堵**，不靠单点。

## 七、真实缺口：手机还当不了麦克风

`fleet/kinds/android_phone.py` 的 `caps()` 当前只有：

```
screen.read / tree.read / apps.list / app.foreground / app.launch /
input.tap / input.type / input.key / notify.read / state.read /
bt.scan / ir.send
```

**没有 `audio.capture`** —— 也就是说手机现在只能「被看被控」，不能当耳朵。

要让手机当麦克风，是**独立的新工程**，不是加一行：

| 步骤 | 内容 | 现状 |
|---|---|---|
| ① node_agent 端录音 | 采集 PCM（16k 单声道） | 未做 |
| ② 传输 | 经 adb 或编队桥把音频流回控制面 | 未做（编队桥 `ir.send` 之外没有音频通道） |
| ③ 编码 | 裸 PCM 体积大，需定格式（wav/pcm/law） | 未定 |
| ④ 新增能力 | `audio.capture`（`side_effect=True`：会开麦） | 未登记 |
| ⑤ 能力实现 | `fleet/kinds/android_phone.py` 里加 | 未做 |

在补上之前，语音输入**只有本机麦克风**这一条路（而且本机还得先
`pip install sounddevice`）。文档写在这里，是为了让排期的人知道
「W4 完成 ≠ 手机语音完成」。

## 八、性能数据（来源标注）

以下数据**不是本次实测**，来自 `polaris-audio-io` 的 `README.md` 与
`interface.json`（测量时间 2026-10-19，本机 i5-12450H CPU，无 GPU，venv 内）：

| 指标 | 数值 | 来源 |
|---|---|---|
| 听（beam=1）RTF | **0.78**（5.4s 音频 / 4.57s 识别） | polaris-audio-io README「实测表」 |
| 听（beam=3）RTF | 1.55（8.74s） | 同上 |
| beam=1 vs beam=3 的 CER | 0.120 vs 0.120（**相同**） | 同上 |
| 闭环 CER（3 轮） | **0.125** | polaris-audio-io `interface.json` → `measured.loop_3rounds.mean_cer` |
| TTS natural（edge-tts） | 4.78s 音频 / 28,656 B / 约 2s | `interface.json` → `measured.speak_natural` |
| TTS local（SAPI） | 2.32s / 102,306 B / 离线 | `interface.json` → `measured.speak_local` |

**RTF < 1.0** 的意义：CPU 上识别快于实时，5.4 秒的语音约 4.6 秒听完。
**CER 0.125** 是**自家 TTS 闭环**的数字（音色单一），**不是真实听写精度**——
`interface.json` 的 `not_acceptance` 字段自己就写明了这一点：
「闭环 CER 不是真实听写精度。自家 TTS 的音色单一，真实麦克风录音会更差，
别拿这个数字对外宣称」。

### 本次（W4）实跑记录

2026-10-21，用 polaris 本地 SAPI 合成一句中文，再走 fleet 的跨进程
`transcribe()` 实跑（真实模型、真实权重、非离线）：

- 参考文本：`今天下午要传权重，注意别把信箱挤死`
- TTS 引擎：`local`（Windows SAPI，5.03s / 221,768 B）
- **fleet 侧跨进程转写的真实输出**（`fleet/gui/voice.py` 的 `transcribe()`，
  走 `voice_runner.py` → polaris venv 的 python → 真模型 + 真权重）：

```json
{"text": "今天下午要传权众,注意别把信箱急死。", "chars": 18,
 "audio_sec": 5.03, "seconds": 14.38, "rtf": 2.86,
 "prompt": "以下为普通话。", "prompt_tokens": 9,
 "max_new_tokens": 431, "max_target_positions": 448, "reserve": 8}
```

  - `prompt_tokens = 9` → `max_new_tokens = 448 - 9 - 8 = 431` ✅
    **坑二在真实运行里被验证了**（不減就撞 448）。
  - `prompt = "以下为普通话。"` ✅ **坑一在真实运行里被验证了**：
    输出是简体「权众 / 信箱」而不是繁体「權眾」。
  - 错字与 polaris README 自测一致（「权重」→「权众」），属 whisper-small
    中文 zero-shot 的已知水平（README 记 CER 约 8~15%）。
  - **RTF 2.86**（14.38s / 5.03s）：比 polaris README 2026-10-19 记的
    **0.78 慢约 3.7 倍**。原因是本次是**冷启动**（首次加载权重 5s+
    且机器当时在跑全量自测），README 那次是热进程内连续跑。
    **冷启动首调必须按 30~90 秒预期**（本次跨进程 wall clock 约 65s，
    其中模型加载 ~50s），这正是跨进程方案要付的代价：省内存、换隔离，
    代价是每次都冷启动。热路径（同一个 polaris 进程内连续识别）才接近 0.78。
  - 对照：同一份音频直接跑 polaris 原生 `listen.py` 得
    `{"text": "今天下午要传权众,注意别把信箱急死。", "seconds": 17.14, "rtf": 3.41}`，
    与 fleet 侧结果一致（都吐「权众」），说明**跨进程驱动没有改变识别行为**。

补充复跑（同一份 WAV，修完 `catalog.py` 语法后重跑一次，确认改动没影响识别）：

```json
{"text": "今天下午要传权众,注意别把信箱急死。", "chars": 18,
 "audio_sec": 5.03, "seconds": 11.59, "rtf": 2.31,
 "prompt": "以下为普通话。", "prompt_tokens": 9,
 "max_new_tokens": 431, "max_target_positions": 448, "reserve": 8}
```

识别文本、`prompt_tokens=9`、`max_new_tokens=431` 三项与首次完全一致；
只有 RTF 从 2.86 降到 2.31（这次机器空闲，但仍是**新起的子进程**，
权重照样要重新加载，所以离 README 的 0.78 还有距离——README 那次是
热进程内连续跑）。这进一步印证：**本方案的 RTF 常态是 2~3，
不是 0.78；0.78 是进程内热态数字，不能拿来当本方案的验收基线。**

## 九、门禁（`evals/t8_voice.py`）

完全离线可复现：**假录音后端 + 注入的假 STT + 假设备**。
绝不真录音、绝不真跑模型、绝不真连设备。跑法：

```
/d/tools/python/python.exe evals/t8_voice.py
```

锁死的几类（门禁红 = 代码坏了）：

1. **失败必须带原因**：文件不存在 / 空音频（0 帧）/ 音频太短 / 非 WAV /
   没装录音库 / 录音被系统拒 / 跨进程失败——每一种都要有一句人话。
2. **简体 prompt 确实传了**：常量对、不是繁体、env 里确实带、驱动里确实
   `get_prompt_ids`。
3. **token 预算确实减了**：`448 - len - 8` 逐个 len 验算，且永远 < 448。
4. **跨进程硬约束**：AST 静态扫 `fleet/gui/voice.py` 与 `voice_runner.py`
   顶层不许 import torch/transformers/soundfile/scipy/numpy/sounddevice/
   pyaudio/edge_tts。
5. **两段式闸门最严**：无确认必拒（含理由）、确认词逐个放行、取消词逐个拒、
   取消优先于确认、含糊判不明、确认必须是另一句话、确认必须来自另一轮、
   破坏性能力在语音路径一律拒、判定在 registry 层（UI 绕不过去）。
6. **STT 当不可信数据**：破坏性句子在映射层被拒、在闸门层也被拒；白名单
   映射覆盖打开/关闭应用、截屏、电量/状态、播放暂停、搜索；不明确 → 澄清。

已接入 `run_selftests.py`（`eval_t8_voice`，超时 120s）。

实测门禁项数：**123 项**（`/d/tools/python/python.exe evals/t8_voice.py` → `t8 voice: PASS`，退出码 0）。
