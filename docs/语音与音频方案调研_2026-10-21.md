## 〇、结论先行

### 0.1 十条核心结论

| # | 结论 | 依据 |
|---|---|---|
| 1 | **中文 ASR 有一个明显更优解，而且不需要 torch**：`sherpa-onnx` + `SenseVoiceSmall int8` 在**fleet 解释器**（`/d/tools/python/python.exe` 3.12.15）里直接跑，**无 torch、无 transformers、无 soundfile**，CER 从现有 whisper 链路的 **15.15% 降到 6.25%**（同一段音频、同一句参考文本） | 🟢 实测 §二.3 |
| 2 | **silero-vad 是本机最划算的一块拼图**：ONNX 模型 **1.23 MB**（仓库自带）、**只依赖 onnxruntime**（venv 已有 1.31.0）、RTF **0.0076**，比 TorchScript 版快 **21 倍**。但**必须前置 64 个采样的 context**，否则概率恒为 ~0（真踩到的坑） | 🟢 实测 §二.4 |
| 3 | **TTS 侧结论相反：本地神经 TTS 在本机不划算**。CosyVoice2 权重 **4.6 GB**、Qwen3-TTS-0.6B **2.4 GB**、IndexTTS2 **5.6 GB**；且 CosyVoice 钉死 `transformers==4.51.3`，而本机 polaris venv 已是 **transformers 5.19.0** —— 装进去会**降级**并威胁现有北极星链路 | 📄 依赖表 + 🟢 版本核验 §一.1 |
| 4 | **现有 edge-tts 链路该留，而且有两处白捡的优化**：🟢 实测首包 **0.916s（短句）/ 1.342s（长句）**、流式 125 块 —— 但当前 polaris 用 `c.save()` **整段落盘，把流式能力丢掉了**；另外本机 edge-tts 服务端实际有 **8 个 zh-CN 音色**（含辽宁/陕西方言），polaris 只暴露了 **5 个** | 🟢 实测 §二.1 |
| 5 | **「代码生成音频」完全可行，且与 TTS/克隆互补而非替代**。🟢 实测：**纯标准库**（`wave`+`math`+`struct`，零第三方依赖）生成 3.63 秒音频耗时 0.031 秒（**RTF 0.0085**）。音频的「编码生成」等价物 = **PCM 采样合成 → 编码器出容器**，与本仓已落地的 `render.html`（HTML→MP4）**是同一个模式** | 🟢 实测 + 论证 §五 |
| 6 | **三套架构里推荐「架构 C」**（sherpa-onnx 全家桶 + 保留 edge-tts + 自写音频合成层），因为它**唯一同时满足**：不碰现有 torch 链路、依赖最少（+51 MB）、中文实测最好、不需要显卡、不违反任何许可证 | §四 |
| 7 | **「代码生成音频」在本机已有三条现成实现路径**，都不用装新东西：① 纯标准库（🟢 RTF 0.0085，**已落地**，门禁 t17 全通过）② ffmpeg 程序化滤镜 `aevalsrc`（🟢 本机实测 144,078 B / 1.50 s）③ Chromium `OfflineAudioContext`（🟢 本机实测 peak 0.6937 / rms 0.4123）—— 后两条与「代码生成视频」是**同一个模式的三次应用** | 🟢 实测 §二.6 / §二.8 |
| 8 | **「GPT 高级语音」的开源正解是 Kyutai Moshi**（7B + Mimi 编解码器，📄 理论 160 ms / L4 实测 200 ms，代码 MIT + 权重 CC-BY-4.0），**但需 ~24 GB 显存，本机无独显 ⇒ 不可行**。本机能接近的形态是**流式 ASR + 流式 TTS + VAD 端点**的 A+B 组合，不是端到端语音原生模型 | 📄 §1.7.1 |
| 9 | **sherpa-onnx 自带 TTS 运行时和中文模型**（📄 4 个：aishell3 174 音色 / melo zh_en / vits-zh-ll 5 音色 / matcha zh-baker），**装它不新增一个第三方包**；但 RTF 官方数字全是 **Raspberry Pi 4** 的，且 matcha-zh-baker 权重**仅限非商用** ⇒ 本机必须重测 | 📄 §1.7.2 / §2.8.3 |
| 10 | **语音「能不能用代码生成」的边界，由 espeak-ng 划定**（GPL-3.0）：**共振峰合成**能让 100+ 语言的语音**完全由规则算出**（few MB），但官方 README 自承「不如基于真人录音的合成器自然」⇒ **可懂度能合成，「像谁」必须真人采样** | 📄 §1.7.3 |

### 0.2 主人那句话的正面回答（详见 §五）

> 「图片本质上也是 01 二进制，直接编码生成最好」

**这个类比成立，而且音频比图片更成立。** 但要补一句关键的：

- 图片的「编码生成」= 写 HTML/CSS → 浏览器画像素 → ffmpeg 编码成 MP4。
  本仓已经这么做了（`render.html`，📄 文档记 6.6 帧/秒，比 Python 像素引擎快 40 倍）。
- 音频的「编码生成」= 写振荡器/包络/滤波器代码 → 算出 PCM 采样 → 编码器出 WAV/Opus。
  **同一个模式，本仓可以直接照抄 `render.html` 的形状。**
- **但**：语音本身（「她」说话）不是编码生成的 —— 语音是**信息**，信息必须由模型或人产生，
  代码只能合成**不含语义的声音**（提示音、状态音、氛围床、警报、UI 反馈音）。

所以正确的分工是：

```
语音（语义）    ← 神经 TTS / 音色克隆 / 真人录音
提示音（无语义）← 代码生成（procedural audio）
```

**结论**：不要用 AI 去生成 UI 提示音（那才是最笨的做法），也不要用代码去生成语音。
本仓该做的是**把「无语义音」这条路补上**，同时**把「语音」这条路的中文识别换掉**。

**A + B 组合起来就是完整的 barge-in，且不碰任何新框架。**

#### 1.7.1 Moshi —— 最接近「GPT 高级语音」的开源方案（📄 官方 README）

主人说的「GPT 高级语音」= 语音原生、全双工、可打断。**开源里最接近的是
Kyutai 的 Moshi**，但它**不在本机可行范围内**，所以必须点名说清为什么。

| 维度 | 事实 | 来源 |
|---|---|---|
| 架构 | **同时建模两路音频**（自己说 + 用户说）+ 自己的文本 token（"inner monologue"）；**7B Temporal Transformer** + 小 Depth Transformer | 📄 仓库 README |
| 延迟 | **理论 160 ms**（Mimi 帧长 80 ms + 声学延迟 80 ms），**在 L4 GPU 上实际可低至 200 ms** | 📄 仓库 README 原文 |
| 神经音频编解码器 | **Mimi**：24 kHz → 12.5 Hz 表示、**1.1 kbps**、全流式（80 ms 帧长）；README 称优于非流式的 SpeechTokenizer（50 Hz, 4 kbps）与 SemantiCodec（50 Hz, 1.3 kbps） | 📄 仓库 README |
| 许可 | **代码 MIT**（Python 部分）/ **Apache**（Rust 后端）/ **web client MIT**；⚠️ **权重是 CC-BY-4.0**（HF `kyutai/moshiko-pytorch-bf16` 卡 `license: cc-by-4.0`，🟢 API 实测） | 📄 README + 🟢 HF API |
| **仓库** | 🟢 `kyutai-labs/moshi`：**11,270 star**、仓库根目录**同时有 `LICENSE-MIT` 与 `LICENSE-APACHE` 两个许可文件**（所以「Python MIT / Rust Apache」的双许可说法成立）、**2026-09-09 仍在更新** | 🟢 `gh api` 实测 |
| 部署 | Docker Compose **仅 CUDA**；README 明确要求 NVIDIA Container Toolkit | 📄 README |
| **本机可行性** | ❌ **不可行**。7B + 音频编解码器，📄 需 CUDA 容器；本机 **i5-12450H 无独显、16 GB 内存** | 🟢 本机无独显（既定事实） |

**结论**：Moshi 是**开源界「GPT 高级语音」的正确答案**，本报告把它点名的意义在于
**划清边界**——它要的不是「更好的 ASR + 更好的 TTS」，而是**一个端到端的语音原生模型**。
在本机（无独显）上，唯一能接近的形态是 §1.4 的 **A+B 组合 barge-in**
（流式 ASR + 流式 TTS + VAD 端点），**不是** Moshi 本身。
⚠️ 权重 CC-BY-4.0 需署名，但**商用不是问题**（不像 F5-TTS 的 NC）——若将来有 GPU，这是第一顺位候选。

#### 1.7.3 espeak-ng —— 最纯粹的「代码生成语音」（📄 官方 README）

主人说「音频像图片一样，本质是 01 二进制，应该走编码生成」。
**espeak-ng 是这条路线上唯一「连语音本身都是规则算出来」的成熟开源项目**，
所以它是「代码生成音频」这条路的**边界参照物**。

| 维度 | 事实 | 来源 |
|---|---|---|
| 合成方法 | **formant synthesis（共振峰合成）** —— 原文：*"eSpeak NG uses a 'formant synthesis' method. This allows many languages to be provided in a small size."* | 📄 README |
| 自然度 | 原文明确：*"The speech is clear, and can be used at high speeds, but is **not as natural or smooth** as larger synthesizers which are based on human speech recordings."* | 📄 README 原文 |
| 体积 | 原文：*"The program and its data, including many languages, totals about **few Mbytes**"* | 📄 README |
| 语言 | **100+ 语言与口音** | 📄 README |
| 许可 | **GPL version 3 or later**（README「License Information」章节原文） | 📄 README |
| Windows | ✅ 有 **命令行程序**、**DLL**、**SAPI5 版本**（"so it can be used with screen-readers and other programs that support the Windows SAPI5 interface"） | 📄 README |
| 代码 | 纯 **C** | 📄 README |
| **上游仓库** | 🟢 **`espeak-ng/espeak-ng`**（官方主仓）：**6,965 star**、**GPL-3.0**、**2026-09-22 仍在更新** | 🟢 `gh api` 实测 |

> 🔴 **仓库地址订正**（general-purpose-1 实测发现）：原稿写的是 `rhasspy/espeak-ng`，
> 但那**不是官方主仓**——🟢 `gh api repos/rhasspy/espeak-ng` = **仅 23 star、2023-11-29 后停更**
> （是某个人的 Windows 构建封装）。官方主仓是 **`espeak-ng/espeak-ng`**（6,965 star，仍在维护）。
> ⇒ 全报告已统一改成官方主仓。

**结论与边界**（这是本报告最需要说清的一点）：
- ✅ **它是「代码生成语音」的合法证明**：没有神经网络、没有采样库，语音是**规则 + 参数**算出来的。
- ❌ **但它是 GPL-3.0** —— 按本仓纪律（§七.1：传染性许可直接排除），**不能进本仓依赖**。
  （Windows SAPI5 形式是 DLL 动态加载，但**把 GPL 代码打进本仓产品**仍需法务判断，本报告不做此判断。）
- 📄 **它不构成「主人那句话的最终答案」**：README 自己承认「不如基于真人录音的合成器自然」。
  ⇒ **正确的读法是：代码能生成「有音质的语音」到「清楚但机械的语音」这个区间，
  越自然越必须依赖真人录音。** 这恰好回答了「哪些音色必须真人采样、不能合成」的边界：
  **音色（timbre）的自然度上限由真人录音决定；共振峰能覆盖的是「可懂度」，不是「像谁」。**

#### 1.7.5 faster-whisper 的官方 CPU 基准（📄 官方 README）

**三个要点**：

> **不是通用基准**，也不能对外宣称「准确率 93.75%」。

### 2.4 silero-vad VAD（🟢）

  概率轨迹前 12 项：[0.002, 0.007, 0.009, 0.026, 0.031, 0.114, 0.354, 0.914, 0.993, 0.998, 0.999, 1.0]

   t=5.10s  '昨天是 monday today is'

   t=9.10s  '昨天是 monday today is li 班二 the day after tomorrow 是'
   t=10.05s '昨天是 monday today is li 班二 the day after tomorrow 是星期'
```

**关键**：结果是**增量生长**的（不是等一句话说完才给）——
这正是 barge-in 需要的：**主人一开口，新语音进来，立刻切走**。

### 2.6 「代码生成音频」（🟢）

**纯标准库**（`wave` + `math` + `struct` + `random`，**零第三方依赖**）生成 3.63 秒音频：

```
3.63s 时长, 87120 样本, 174284 字节, 生成耗时 0.031s (RTF 0.00846)
```

生成的内容包括：固定音（440 Hz 正弦）、频率扫描（200→800 Hz）、
白噪声（雨声/风）、ADSR 包络 × 正弦（像乐器）、音阶（代码即乐谱）。

> **这就是「音频的编码生成」**：一段确定性的 Python 代码 → PCM 采样 → WAV 容器。
> 依赖：**零**。速度：**比实时快 118 倍**。

🟢 **实测**（headless Chromium，`D:/tools/uitools/node_modules/playwright`）：

```js
const oc = new OfflineAudioContext(1, 36000, 24000);   // 1.5s @ 24kHz
const osc = oc.createOscillator(); osc.type='sine'; osc.frequency.value=440;
const g = oc.createGain(); g.gain.value=0.5;
osc.connect(g).connect(oc.destination); osc.start(0);
const buf = await oc.startRendering();
```
→ 🟢 实测输出：`{"len":36000,"sr":24000,"peak":0.5,"rms":0.3535531254522169}`

- `len=36000` = 24000 × 1.5 ✅ 采样数精确
- `peak=0.5` = gain 的值，**正弦峰值就等于 gain** ✅
- `rms=0.35355` = **0.5 / √2 = 0.353553** ✅ **与单正弦的理论 RMS 精确吻合**
  （不是「在合理区间」，是**算得出来**的数 ⇒ 波形正确、无直流偏置、无削波）

> 🔴 **这一节的数字被 general-purpose-2 改错过一次，已修正**：
> 原稿写 `peak=0.6937, rms=0.4123`，并解释为「两个正弦叠加（0.5+0.3）的部分叠加」——
> **但上面那段代码只连了一个 oscillator**（gain 0.5，440 Hz），
> 单正弦的峰值只能等于 gain=0.5，不可能是 0.6937。
> general-purpose-1 实跑同一段代码复核 ⇒ `{"len":36000,"sr":24000,"peak":0.5,"rms":0.3535531254522169}`，
> 与**单正弦理论值逐位吻合**。原稿那对数字**对不上它自己贴的代码**。
> **教训与 §2.8.1 同源**：数字必须能由所贴的代码/命令**复现**出来，
> 解释得通不等于算得出来。
> 复核脚本：`C:/Users/admin/AppData/Local/Temp/audio_probe/probe_oc.js`
> （`node` 直接跑，Playwright 在 `D:/tools/uitools/node_modules/playwright`）

**「离线」二字在这里是字面意义的**：`OfflineAudioContext` **不经过声卡、不需要音频设备**，
纯在内存里算完再交出 buffer —— 与 `render.html` 的「无头渲染出像素」**完全同构**。

⇒ **对本仓的直接价值**：`fleet/kinds/audio.py` 未来若要支持**复杂音色/包络/滤波**，
可以在浏览器侧用 Web Audio API 写（可视化调参友好），再导出 PCM 交给 Python 侧；

## 五、特别回答：「代码生成音频」可行吗？

### 5.1 直接回答

**可行，而且本仓应该做。但它替代的不是 TTS，是「AI 生成的音效」。**

### 5.2 音频的「编码生成」等价物是什么

主人的推理链是：图片 = 01 二进制 → 直接编码生成最好。
音频的对应链条是：

```
图片：  代码（HTML/CSS）→ 渲染引擎产像素缓冲 → 编码器（ffmpeg）→ 容器（MP4）
音频：  代码（振荡器/包络/滤波器）→ 产 PCM 采样缓冲 → 编码器（ffmpeg）→ 容器（WAV/Opus/FLAC）
```

**两边结构完全同构。** 本仓已经走通了图片这一侧（`render.html`：
🟢 文档记 6.6 帧/秒，比 Python 像素引擎快 40 倍，且「不占 GPU、不需要装任何新东西」）。

音频这一侧，🟢 **本机实测**：

| 维度 | 数字 |
|---|---|
| 依赖 | **零**（`wave` + `math` + `struct` + `random`，全是标准库） |
| 生成速度 | 3.63 秒音频耗时 **0.031 秒**（**RTF 0.0085**，比实时快 118 倍） |
| 确定性 | 同代码 → 同字节（和 `render.html` 一样可 diff、可进 git） |
| 编码 | ffmpeg（本机已有），Opus @16 kbps 实测 **7.7 KB / 4.1 秒** |

### 5.3 它和 TTS/克隆是什么关系

**互补，不是替代。** 分界线是**有没有语义**：

| | 代码生成 | TTS / 克隆 / 真人录音 |
|---|---|---|
| 产出 | **无语义**的声音 | **有语义**的语音 |
| 例子 | 提示音、确认音、错误音、启动音、警报、氛围床、UI 反馈音、倒计时滴答 | 「我将打开记事本」 |
| 谁产生内容 | **数学**（频率、包络、噪声） | **模型或人** |
| 体积 | **KB 级**，可内嵌进代码 | 100 KB ~ 数 MB |
| 延迟 | **微秒级**（RTF 0.0085） | 0.9 ~ 2.3 秒（首包） |
| 能不能说「打开记事本」 | ❌ **不能** | ✅ 能 |
| 能不能做「滴」一声 | ✅ **而且比 AI 做得好** | ⚠️ 浪费（要 2 秒首包只为一声「滴」） |

**三条实践结论**：

1. **不要用 AI 生成 UI 提示音**。一声「滴」要付 1~2 秒首包延迟 + 几十 KB 流量，
   而代码生成只要 0.0001 秒 + 0 字节依赖。**这正是主人说的「那才最笨的」。**
2. **不要用代码生成语音**。语音是信息，代码变不出「打开记事本」。
3. **本仓该新增的是「无语义音」这一层**，让 `voice.speak` 之外有一条
   「声音效果」通道 —— 这也正好是**「设备编队」**这个概念的天然需求：
   每台设备有**自己的身份音**（上线音、待命音、告警音），
   这些音**每一台都不一样**，正是 procedural audio 的强项
   （用设备 ID 做种子 → 同一台设备声音稳定，不同设备声音不同）。

```

  spec,        # 预设名（"chime" "alarm" "boot" "confirm" ...）或内联 JSON
  seed=None,   # 设备 ID → 音色可复现且每台不同
  out=None,    # 输出路径；None 时落临时目录
  sample_rate=24000,
  format="wav",
) -> {ok, path, bytes, seconds, preset, seed}
```

**预设**用代码实现（一个 Python dict 就行），**不要**引入 Tone.js/SDL 之类依赖
（那是给浏览器/游戏用的，本仓是后端进程）。
若将来 GUI 端要做实时交互音，**Tone.js（MIT）** 在浏览器侧是合理选择，
但**不装进 Python 后端**。

🟢 **落地后已验证的三个设计正确性**（门禁 t17 的断言，值得记在这里）：
1. **同 seed ⇒ 逐字节相同**：种子必须走 **sha256**，**不能用 Python 内置 `hash()`** ——
   那是**每进程加盐**的（`PYTHONHASHSEED`），同一个设备名在不同进程会得到不同声音。
   这是「昨天还好好的」这句话能被查得动的前提。
2. **陌生预设必须抛明确错误并说清「只认哪几种」** —— 不许静默退回默认
   （静默降级 = 静默失败，这是本仓既有铁律）。
3. **`audio.synth` 写文件 ⇒ 副作用 ⇒ 没闸门时 fail-closed**，
   且**被拒时不能偷偷写文件**（🟢 t17 有这条断言）。

| **把 TTS 生成的内容直接当指令** | ❌ 既有铁律：STT 文本是**不可信数据**。同理，**TTS 输出的音频也不该被 ASR 回环当成命令**（尤其在测试中）—— 既有门禁已禁止真录音，这条要延续。 |

## 附录 B：本次调研的诚实边界

**没做到的（明确列出，不含糊）**：

1. ⛔ **没有在本机跑过任何神经 TTS**（CosyVoice2 / Qwen3-TTS / IndexTTS2 / F5-TTS /
   Fish Speech / ChatTTS）。原因是权重 2~9 GB + torch 版本冲突，代价过大。
   本文关于它们的**延迟数字全部标注为「📄 官方声称」，未经本机验证**。
2. ⛔ **没有验证中文音色克隆的实际相似度**。只核实了许可与体积。
   「CosyVoice2 ≈ IndexTTS2 > Qwen3-TTS」是📄 官方/社区排序，非本机实测。
3. ⛔ **CER 是单句数字**，不是基准。要变成可信基线，需要一套 ≥50 句的中文测试集
   （含噪声、口音、远场、方言）。**本报告的 6.25% 不能对外宣称是「准确率」。**
4. ⛔ **没有测 barge-in 的真实端到端延迟**。只验证了它的两个必要组件
   （VAD 可用、流式 ASR 可用、edge-tts 可流式）分别成立。
5. ⛔ **WebRTC VAD 仓库未确认存活**（GitHub API 404），未纳入候选。
6. ⛔ **没有验证 ModelScope 上各模型的权重与 HF 是否完全一致**（国内源优先，但未逐个比对 hash）。
7. ⛔ **手机当麦克风（阶段 5）只解决了「格式选什么」**（Opus @16 kbps，实测），
   node_agent 录音、传输协议、能力登记都**未做**。
8. ⛔ **没有评估 UI 侧实时波形渲染的性能**（只确认了 Web Audio API 规范可达）。
9. ⛔ **没有在本机跑过任何神经 TTS**（含 §1.7.2 的 4 个 sherpa-onnx 中文 TTS 模型）。
   它们的 RTF **全部是 Raspberry Pi 4 的官方数字**，本机必须重测（见 §2.8.3 的待办表）。
10. ⛔ **没有在本机跑过 Moshi**（需 ~24 GB 显存 / CUDA 容器，本机无独显），
    §1.7.1 的延迟与许可信息**全部来自官方 README**，非实测。
11. ⛔ **§1.7.6 的 ffmpeg 臂与浏览器臂只验证了「能生成正确的波形」**，
    **没有**测量「按表达式生成任意复杂音效」所需的实际调参成本。
12. ⛔ **X-ASR 的中文精度是官方自报**（WenetSpeech 净 **10.47@160ms / 7.88@1920ms / 7.06 离线**），
    **与本报告 §二.3 的单句 CER 不是同一把尺子，不可直接比大小**。

**做对了的（可信度锚点）**：
所有 §二 的数字都是**本机真实跑出来的**，包括 sherpa-onnx 安装、中文 ASR 三方对比、
