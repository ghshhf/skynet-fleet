## 一、结论先行

**不建议 fork Operit，也不建议把它的界面搬过来。建议做「机制移植」：把它验证过的
六套机制，按我们的契约重写进现有 `tianwang_android` + `android_bridge`。**

三条路的账，先摆清楚：

| 路线 | 代价 | 结论 |
|---|---|---|
| A. 直接 fork Operit 当手机端 | 48 万行 Kotlin、Compose、118 个依赖、必须 Gradle+NDK+CMake；人格/后端契约和天网完全不同，等于把「她」塞进别人的房子 | ❌ 否决 |
| B. 机制移植（本计划） | 我们现有 5 个类 33.5KB 的 App + 16KB 的桥，按需补 3 块能力 | ✅ 推荐 |
| C. Operit 做能力后端、天网做人格前端 | 跨 App IPC，两个 App 都要活，故障面翻倍 | ⚠️ 备选，不做首选 |

理由一句话：**我们缺的不是「一个手机 AI」，是「她的手」**——读屏、按元素点、听见。
Operit 恰好把这三件事都做透了，而且做得很克制。

## 二、Operit 到底是什么（实测盘点）

### 2.1 规模

| 项 | 实测 |
|---|---|
| Kotlin 文件 / 行数 | **1402 个 / 484,336 行** |
| `app` 包内 | 约 44.8 万行（ui 22.0 万 + core 11.1 万 + data 4.6 万 + api 4.0 万 + util 1.6 万 + 其余 1.5 万） |
| Gradle 模块 | `app`、`avator/{dragonbones,mmd,fbx}`、`llm/{llama,mnn}`、`quickjs`、`terminal`(子模块)、`showerclient` |
| 构建 | minSdk **26** / targetSdk **34** / compileSdk **36** / 只出 **arm64-v8a** / 版本 1.12.2 |
| 依赖 | `implementation` 级 **118 条** |
| 权限 | **40 条**（含 SMS 读写、MANAGE_EXTERNAL_STORAGE、SYSTEM_ALERT_WINDOW、BIND_VOICE_INTERACTION、CALL_PHONE…） |
| 工具说明 | `SystemToolPromptsInternal.kt`（363KB）里 **292 条 ToolPrompt** |
| assets | **31MB**，其中含 `accessibility.apk`、`desktop.apk` 两个**独立子 APK** |
| TODO 目录 | `docs/TODO/` 下 **121 个**细化计划 |

一句话定性：**这不是一个玩具，是一个已经迭代了两年的手机 Agent 平台**。我们的正确姿势是
"取其中已验证的机制"，而不是"把它搬空"。

### 2.2 关键架构（我实际读过的部分）

```
模型输出 XML 工具调用
        ↓  ChatMarkupRegex + StreamXmlPlugin（流式边收边解析）
   ToolExecutionManager.extractToolInvocations()
        ↓
   AIToolHandler.executeTool()
        ├── AIToolHook        拦截（可 Block，带理由）
        ├── validateParameters 参数校验
        ├── ToolExecutor.invoke / invokeAndStream
        └── ToolProgressBus   执行进度广播（UI 上能看到"正在点第 3 下"）
        ↓
   <tool_result name=".." status="success"><content>…</content></tool_result>
        ↓  回灌模型，进入下一轮
```

工具调用的线上格式（`util/ChatMarkupRegex.kt:27` 实测）：

```xml
<tool name="click_element">
  <param name="bounds">[100,200][300,400]</param>
</tool>
```

**为什么这个设计对我们重要**：它不依赖 OpenAI 的 function calling，任何能写 XML 的模型
都能用。我们的本地 4B/0.6B 根本没有可靠的 function calling，但能照着格式写 XML。

## 三、六个我们真正用得上的机制（逐个说"它怎么做的 / 我们差在哪 / 搬多少"）

### ① 无障碍做成「独立 App + AIDL」，不是塞在主 App 里

**它怎么做的**（`UIHierarchyManager.kt`、`app/src/main/aidl/`）：

- 无障碍服务放在**另一个包** `com.ai.assistance.operit.provider`；
- 主 App 把 `accessibility.apk` 放在自己的 assets 里，首次运行解压到 cacheDir 再拉起安装；
- 跨进程用 AIDL 绑定，接口只有 10 个方法：

```aidl
String  getUiHierarchy();
boolean performClick(int x, int y);
boolean performLongPress(int x, int y);
boolean performGlobalAction(int actionId);
boolean performSwipe(int sx, int sy, int ex, int ey, long duration);
String  findFocusedNodeId();
boolean setTextOnNode(String nodeId, String text);
boolean takeScreenshot(String path, String format);
boolean isAccessibilityServiceEnabled();
String  getCurrentActivityName();
```

**为什么高明**：无障碍服务最怕"主 App 被系统杀掉，权限跟着断"。拆成独立 App，
服务活着、主 App 随便重启。而且 AIDL 是**强类型**的，不是拼字符串。

**我们差在哪**：`android_bridge/BridgeService.java` 已经是一个独立 APK 的无障碍服务，
走 **127.0.0.1 的 ServerSocket**，命令集 13 个（`PING/TAP/SWIPE/LONG/TEXT/BACK/HOME/
RECENTS/NOTIFY/FOCUS/IRINFO/IR/BTSTATE/BLE`）——**纯坐标级，没有读屏**。

**搬多少**：**纪律搬接口形状，代码自己写**。把 AIDL 那 10 个方法当作目标接口，我们的桥
按同样语义补齐；通道仍是 loopback TCP（我们已有 token 鉴权，Operit 是 Binder 无鉴权）。

---

### ② UI 树压缩成「模型能读的一屏文本」——这是他们最值钱的一招

**它怎么做的**（`ToolResultDataClasses.kt:905` 起）：

原始 `AccessibilityNodeInfo` 树动辄几千节点、几十 KB，直接喂模型必爆上下文。他们先压成
`SimplifiedUINode`，再渲染成纯文本：

```
▶ [android.widget.Button] T: "发送" ID: btn_send ⮞ [100,200][300,400]
◢ [android.widget.TextView] T: "今天天气不错…"
```

- `▶` = 可点，`◢` = 不可点
- `T:` 文本（**截到 30 字**），`D:` 无障碍描述，`ID:` 资源 ID，`⮞` 边界
- 剪枝规则 `shouldKeepNode()`：**只留** Button/TextView/EditText/ScrollView/Switch/ImageView
  **∪** 有文字/描述 **∪** 可点 **∪** 子孙里有值得留的

**点击怎么落到具体元素**（`AccessibilityUITools.kt:228`）：模型给 `bounds` 就取矩形中心直接
点；给 `resourceId/className/contentDesc` 就回原树里找（`resourceId` 用 `endsWith` 匹配，
因为前缀是包名），找不到/索引越界都返回明确错误，不静默。

**我们差在哪**：完全没有。`agent_phone.py` 的读屏走的是 `adb shell uiautomator dump`，
慢（秒级）、依赖 ADB、且拿不到实时焦点。这是我们和它最大的能力差。

**搬多少**：**照机制重写**（剪枝规则 + 文本格式 + bounds 点击这三件事，约 300~500 行 Kotlin，估）。
这是 P0 的全部内容。

---

### ③ 工具权限是「全局默认 + 单工具例外」，不是简单的开关

**它怎么做的**（`docs/doc-src/feature-protocol/tool_permissions.md`）：

- 三级：`ALLOW` / `ASK`（每次弹窗）/ `FORBID`
- 两层：全局默认决定"没配过的工具"，单工具例外覆盖全局
- 实际权限 = 例外优先，否则跟全局

**为什么这个设计对我们重要**：天网手机端将来会有"她自己去点外卖"这种场景，
必须能按工具粒度锁死（比如 `tap` 允许、`type` 每次问、`shell` 永远禁）。

**我们差在哪**：`agent_phone.py` 是**写死五个动作**（tap/type/back/home/done），
粒度对了但没有"每次询问"这一档，也没有 UI。

**搬多少**：**只搬模型不搬代码**。三个枚举 + 一张例外表，我们自己在 `Prefs` 里存。

---

### ④ 权限五级：ROOT / ADMIN / DEBUGGER / ACCESSIBILITY / STANDARD

**它怎么做的**（`ShellExecutorFactory.kt`）：按权限从高到低探测，取第一个可用的；
每级一个 `ShellExecutor` 实现。`DEBUGGER` 那级是 **Shizuku**。

**对我们的意义**：**这条对我们几乎没用，但有个关键交叉验证**——他们同样把
`ACCESSIBILITY` 当成一个正经权限等级，而不是"凑合方案"。这印证了我们记忆里的结论：
小米系 `input tap` 全废，无障碍是唯一活路（`天网-安卓端.md` 已实测 5 种失败路径）。

**搬多少**：不搬。我们的 `android_device.py` 已经有 adb 直连那套，比 Shizuku 更可控。

---

### ⑤ 语音四件套：VAD / 唤醒 / 离线 ASR / TTS 档案

**它怎么做的**：

| 件 | 实现 | 备注 |
|---|---|---|
| VAD | `OnnxSileroVad.kt`，依赖 `onnxruntime-android:1.17.1` | 帧级 `isSpeech(ShortArray)`，可设静音/语音时长 |
| 唤醒 | `PersonalWakeListener.kt` + `PersonalWakeEnrollment.kt` + `PersonalWakeFeatureExtractor.kt` | **自己录一遍就注册**，不依赖固定唤醒词模型 |
| 离线 ASR | `SherpaSpeechProvider`（sherpa-ncnn/ncnn 系） | assets 里**没有**模型 ⇒ 需另下 |
| TTS | `VoiceServiceFactory` + 9 个 provider（OpenAI / MiniMax / 豆包 / SiliconFlow / VITS / HTTP / 无障碍播报…），配置走"档案(profile)" | 档案有独立 DataStore、UUID、迁移规则 |

**对我们最有用的是唤醒那套"自注册"思路**：不做"小爱小爱"这种固定词，而是**录一遍"她"的
名字**＝主人自己的口音样本。这跟天网"私人陪伴"的定位是对齐的，而且省掉一个模型。

**我们差在哪**：手机端现在**没有本地语音**。录音 → adb reverse → PC 的 whisper。
一旦拔线，手机就是哑的（今天上午就是这么坏的）。

**搬多少**：VAD 用 ONNX Runtime 的官方 AAR（`.so` 可以直接进 `jniLibs`，aapt2 也能打包，
见 §六风险 1）。Silero VAD 模型 2MB 级别（估，需实测）。唤醒先**不做**，等 VAD 通了再说。

---

### ⑥ 手机作为「被调用的节点」——和天网的定位完全重合

**它怎么做的**：

- `integrations/http/ExternalChatHttpServer.kt`：默认端口 **8094**，
  `Authorization: Bearer <token>`，`GET /api/health`、`POST /api/external-chat`
- 三种返回方式：`sync` 一次给完 / `stream=true` 走 SSE（`start`→`delta`→`done`/`error`）/
  `response_mode=async_callback` 给个 `callback_url` 事后回调（**v1 不重试，非 2xx 只记日志**）
- `integrations/a2a/A2aHttpHandler.kt`：还说一套 **A2A**（agent-to-agent）JSON-RPC，
  带 `agent card`（name/description/capabilities.streaming/skills/securitySchemes）

**为什么重要**：这几乎就是我们 `fleet/gui/server.py` 的接口语义（`X-Fleet-Token` + SSE）。
差别只在：**它在手机上，我们在 PC 上**。天网的"任意节点可被调用"要落地，这就是现成答案。

**搬多少**：**只搬接口语义**（路径、字段名、SSE 事件名），代码按我们的 token 鉴权重写。
不要引入 NanoHTTPD 这个依赖——我们已有自己的 HTTP 服务写法。

### ⑦（附）记忆：图 + 向量，不是聊天记录堆叠

`MemoryRepository.kt` 是 `Memory` + `MemoryLink`（带 `type` / `weight` / `description`）
+ `MemoryTag`，配 `CloudEmbeddingService` 做检索，另有
`docs/doc-src/architecture/memory_candidate_scoring_formula.md` 定义"什么内容值得进记忆"的打分。

**对我们的意义**：天网现在的人格记忆是 `cards/` 里的角色卡 + `memory/` 的日志，
是"文件"不是"图"。这块**先不做**，但要知道别人是怎么做的：记忆是**有链接的有权图**，
不是一条条流水。

## 四、明确「不搬」的清单

| 不搬 | 原因 |
|---|---|
| 整个 app fork | 48 万行、Compose、118 依赖；我们的契约完全不同 |
| Compose UI（22 万行） | 我们的光球/字幕是既定设计（`天网原生端_计划书` §一），不引入新视觉语言 |
| `avator/`（dragonbones/mmd/fbx） | 3D 虚拟形象，我们现在不需要 |
| `quickjs` + ToolPkg | JS 工具包是"给别人的扩展机制"；天网的扩展面是 MCP |
| `llm/llama`、`llm/mnn` 的 JNI | 我们 PC 端已有 llama.cpp，手机上跑 4B 的收益要先量（估 10–15 tok/s，未验） |
| `web-chat/`（React） | 我们已有 `ui/`（app.js 65KB） |
| `showerclient`（虚拟屏） | 依赖外部 Shower server，天网没这个基础设施 |
| Shizuku / root 通道 | 与我们的 adb 直连冲突，且小米系用不上 |

## 五、许可证：LGPL-3.0 到底约束什么

仓库根 `LICENSE` 是 **GNU LGPL v3**，不是 GPL，也不是 MIT。三条纪律：

1. **只借机制、自己重写** ⇒ 无义务（最干净，本计划默认走这条）。
2. **复制源码进我们的仓库** ⇒ 该文件及衍生仍是 LGPL-3：保留版权声明、标注修改、
   并允许他人替换该部分。`skynet-fleet` 是 public 仓库，做到这点不难，但**会永久绑定**。
3. **把它的 APK 直接打包分发** ⇒ 需随包提供对应源码与安装信息（LGPL-3 的
   "Installation Information" 条款对 User Product 有额外要求）。

**执行**：默认 1；确需 2 时，在提交信息里写明来源 commit 与文件路径。

## 六、分阶段计划（一步一个脚印，每阶段有门禁）

顺序锁死：**读屏 → 点准 → 听见 → 被调用**。上一阶段验收不过，不进下一阶段。

### P0 · 让她「看见」——UI 树读得回来

| 项 | 内容 |
|---|---|
| 改哪 | `android_bridge/BridgeService.java` 加 `UI` 命令；`android_device.py` 加 `ui_tree()` |
| 做什么 | 无障碍读 `rootInActiveWindow` → 按 Operit 剪枝规则压成紧凑文本 → 经 loopback 返回 |
| 判据（门禁） | 对 K80 连续读 3 个不同界面（设置/微信/桌面），每次 ≤300ms、≤8KB，且人能读懂 |
| 估工 | 300~500 行 Kotlin + 100 行 Python |

### P1 · 让她「点准」——按元素点，不靠猜坐标

| 项 | 内容 |
|---|---|
| 改哪 | 桥加 `TAPEL`（`resourceId` / `text` / `bounds` 三选一）、`SETTEXT`、`SCROLL`；`agent_phone.py` 动作集扩到 8 个 |
| 做什么 | 元素寻址 + 点击；失败必须回明确原因（找不到 / 歧义 / 越界），**不许静默** |
| 判据（门禁） | "把亮度调到 30%" 端到端跑通；故意给不存在的元素，必须报"找不到"而不是乱点 |
| 估工 | 200 行 Kotlin + 200 行 Python |

### P2 · 让她「听见」——手机本地语音，不依赖 PC

| 项 | 内容 |
|---|---|
| 改哪 | `tianwang_android` 引入 ONNX Runtime + Silero VAD；ASR 二选一（见下方待拍板） |
| 做什么 | VAD 断句 → ASR 出字 → 现有 `/api/chat` 链路不变 |
| 判据（门禁） | **飞行模式**下说一句，手机本地出字 ≤2s（估，需实测）；连续 10 句不卡死 |
| 估工 | 400 行 Java + 模型 2~80MB |

### P3 · 让她「被调用」——手机成为天网的一个节点

| 项 | 内容 |
|---|---|
| 改哪 | `tianwang_android` 内置 HTTP 服务，语义对齐 Operit `external-chat` |
| 做什么 | `GET /api/health`、`POST /api/chat`（SSE：`start`/`delta`/`done`/`error`）+ Bearer |
| 判据（门禁） | PC 端 `curl -N` 到手机，流式出字；token 错必须 401 |
| 估工 | 300 行 Java |

## 七、风险（说清楚，不藏）

1. **ONNX Runtime 与「不用 Gradle」的冲突**（最大技术风险）
   它官方是 AAR。我们手搓 aapt2 也能打，但要自己从 AAR 里抽 `jniLibs/arm64-v8a/*.so`
   和 `classes.jar`。**这是可行的，但需要一次实跑验证**，不能靠猜。
2. **MIUI 保活**：独立桥 APK 现在能用是"用户在用的时候"，长期常驻（唤醒词要常驻）是另一回事。
   这块 Operit 也没解决，它靠前台服务 + 用户手动关电池优化。
3. **ASR 模型体积与速度**：arm64 K80 上 small 级别模型的速度**未实测**，不能拍脑袋说"够快"。
4. **48 万行的诱惑**：读它的过程会不断想"这个也搬那个也搬"。本计划的"不搬清单"是硬约束。
5. **LGPL 传染**：一旦复制源码，后续就绕不开声明义务。默认重写。

## 八、需要主人拍板的三件事

1. **允许引入 Gradle 吗？**
   现在是纯 `aapt2 + javac + d8` 手搓（`tianwang_android/build.sh`，CI 里 28 秒出包）。
   引 ONNX Runtime 后，手搓仍可行但要额外维护抽包逻辑；上 Gradle 就回到"能拉依赖"的舒服路，
   代价是构建变慢、CI 要配 Android SDK 缓存（Operit 的 CI 就是这么干的）。
   **我倾向先手搓试一次，跑不通再上 Gradle**——因为手搓链路今天已经验过是活的。
2. **手机 ASR 走哪条？**
   - (a) Silero VAD + **whisper.cpp tiny/small**（GGUF，和 PC 端同一套模型体系）
   - (b) Silero VAD + **sherpa-onnx 中文流式模型**（真流式，边说边出字，体积小）
   - 我倾向 (a)：模型体系统一，PC 端已有 whisper 经验；代价是不是流式。
3. **「她」要不要能从手机主动开口？**（唤醒词常驻）
   这决定 P2 的范围：不常驻就是一个"点开才听"的 App（简单、省电）；
   常驻就是随时能搭话（要前台服务 + 电池豁免 + 隐私取舍）。

## 九、本计划不做的事（写死，防跑偏）

- 不改天网的整体架构（桌面端 exe / 人格卡 / fleet server 都不动）。
- 不在手机上跑 4B 模型（除非先量出 ≥10 tok/s 的实测数据）。
- 不引入 Compose、不引入 Kotlin 以外的重资产框架。
- 不做"照抄 Operit 界面"。
- 任何改动不写兜底/回退代码（主人红线）。
