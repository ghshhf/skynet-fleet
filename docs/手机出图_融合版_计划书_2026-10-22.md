# 手机出图（融合版）计划书 · 2026-10-22

> 替代之前的《手机出图功能·动手范围》与《手机算力节点》中关于「借 Termux 跑 sd.cpp」的设计。  
> 主人三条要求（原话）：  
> 1. 手机到底需要下载什么？  
> 2. 我自己手机上手动选择出图，出完后远程投递给你（PC）。  
> 3. 为什么不把命令行软件（sd.cpp）融进咱们软件里面？还非要借别人的（Termux）？融合完后提取，这就是咱们的创意。

---

## 一、结论前置

1. **不再依赖 Termux**。把 sd.cpp 出图能力编进天网 APP 本身，通过已有 NDK/JNI 链（`jni/` 下已有 `whisper_jni.cpp` 先例）从 Java 调用 C++ 出图引擎，融合后就是咱们自己的能力。
2. **手机需要下载两样东西**：sd.cpp 编译后的 Android 库（~.so） + SD1.5 量化模型文件（q8_0 ~1.1GB 或 fp16 ~2GB，需主人认可后下载）。
3. **用户在手机APP上手动选择出图**：输入 prompt、选尺寸/步数、点生成 → 手机本地跑 sd.cpp 出图 → PNG 保存到手机 → 通过已验收的 N+1b 配对通道（TLS1.3 + 会话令牌）远程投递给 PC → PC 按 `result_id` 登记制回取展示。
4. **传输不新建协议**：直接复用 N+1b 已验收的配对通道（广播发现 → 6位验证码握手 → TLS1.3 会话），不新建鉴权、不新建传输。

---

## 二、手机需要下载什么（明确清单）

| 项 | 大小 | 来源 | 说明 |
|---|---|---|---|
| sd.cpp Android 库（`libfleet_sd.so`） | ~30–60MB | 自身编译（NDK，Adreno/Immortalis Vulkan 后端） | 打包进 APK，或首次启动从 PC/网络下载到 APP 私有目录 |
| SD1.5 模型（q8_0） | ~1.1GB | HuggingFace `stable-diffusion-v1-5` 量化版 | 需主人明确认可后下载；后续可换 SDXL Turbo/SDXS 提速 |
| Vulkan ICD | 系统自带 | 手机系统 `/system/lib64/libvulkan.so` | 不下载，运行期 dlopen 系统 ICD，不借 Termux 的 Mesa wrapper |

**下载时机**：APP 首次点「出图」时提示「需要下载出图模型 ~1.1GB，是否现在下载？」，主人点确认后下载，下载失败给出精确原因（网络/空间/权限），不静默。

## 三、用户手动选择出图 + 远程投递流程

```
用户在手机天网APP「出图」tab
  1. 输入 prompt（必填，1–500 字符）
  2. 选择尺寸（512 / 768 / 1024，默认 512）
  3. 选择步数（1–30，默认 10）
  4. 选择种子（空=随机，或手动输入）
  5. 点击「生成」
  6. 手机本地 sd.cpp 出图 → 保存 PNG 到 APP 私有目录 + 相册
  7. 通过 N+1b 配对通道远程投递给 PC（TLS1.3 + 会话令牌）
  8. PC 收到 result_id，按登记制回取展示/保存
```

**关键点**：
- 「手动选择」在手机APP上完成，不依赖PC下指令。PC 只是「结果接收方」，可主动连手机查看/下载，也可被动等手机主动投递。
- 投递用 N+1b 已验收的「信箱机制」：手机端主控，PC 端被控，或反过来——握手双向，任一端可发起。
- 失败带原因不静默：模型没下、sd 库缺、Vulkan 绑错、网络断、配对未建——各给出精确文案。

## 四、把 sd.cpp 融进咱们软件（不再借 Termux）

### 方案选型

| 方案 | 做法 | 工作量 | v1 决策 |
|---|---|---|---|
| A. 借 Termux RUN_COMMAND（旧方案） | APP 调外部 Termux 跑 fleet-img.sh | 小 | ❌ 用户反对，融合度低 |
| B. 打包 sd.cpp 二进制 + 子进程调用 | sd.cpp 编译成 Android 可执行文件，打进 APK，APP 内 Runtime.exec 调用，读结果文件 | 中 | ✅ **v1 选它**：最小改动，不碰 NDK/JNI，就是「把命令行软件放进自己软件里跑」 |
| C. NDK + JNI 直跑 | sd.cpp 编译成 `.so`，Java 通过 JNI 调用（参考 `jni/whisper_jni.cpp`） | 大（按天算） | ❌ v1 不做，留 v2 |

### v1 融合路径（方案 B）

1. **编译**：用 NDK 把 `stable-diffusion.cpp` 编译成 Android 可执行文件 `sd`（Vulkan 后端，Adreno/Immortalis）。
2. **打包**：把 `sd` 二进制放进 APK `assets/` 或首次启动下载到 APP 私有目录 `/data/data/app.skynet.tianwang/files/sd/`。
3. **调用**：APP 内 Java 代码构造命令行参数（`--prompt --steps --size --seed -o`），以子进程方式调用 `sd`，日志写私有日志文件，stdout 只回一行 JSON（`{ok,path,ms,temp,steps,size}`）。
4. **结果**：PNG 写到 APP 私有目录 + 系统相册 `Pictures/fleet/`，APP 读取后通过配对通道投递给 PC。

### v2 融合路径（方案 C，留后）

- 把 `sd.cpp` 改成可嵌入的 C++ 库，编译 `libfleet_sd.so`，放进 `jni/`，参考 `whisper_jni.cpp` 的 JNI 绑定方式，从 Java 直接调用，无子进程开销、无命令行解析。

## 六、验收标准（每项都要能指到文件/命令）

1. **下载清单可验**：APP 私有目录下有 `sd` 二进制 + `sd15-q8_0.gguf` 模型文件（大小匹配）。
2. **手动出图可验**：手机APP内输入 prompt → 点生成 → 本地出一张真 PNG（非占位图）。
3. **远程投递可验**：手机端点「投递给PC」后，PC端能按 `result_id` 收到并展示/保存该 PNG。
4. **参数越界拒**：步数>30、尺寸不在白名单、prompt为空 → APP 给出精确失败文案，不生成。
5. **融合无 Termux**：APP 内出图不再调用 `com.termux.RUN_COMMAND`，不依赖外部 Termux 安装。

---

## 七、诚实边界（写死，不许当卖点）

1. **D2 独显 / NPU 摸不到**：APP 是 Linux userspace，MTK APU 与 D2 要 Android NNAPI/QNN，v1 不做、不承诺，只用 Vulkan。
2. **Vulkan 绑定是生死线**：绑错（软件光栅）= 极慢或崩溃；v1 实测盯 sd.cpp 启动日志里是否出现 Vulkan 设备名。
3. **模型下载 1.1GB–2GB**：需主人明确认可；蜂窝下载慢，建议 WiFi。
4. **持续出图必热降频**：10分钟后帧率曲线一定劣化，v1 实测记录，不假装恒速。
5. **跨网传输复用 N+1b**：打洞/中继尚未做（N+1b-4 待开工），跨网投递走 IPv6 直连或手动端点交换，LAN 下无阻碍。

---

## 八、待拍板（或一句「按建议来」即开工）

1. **模型选 q8_0 (~1.1GB) 还是 fp16 (~2GB)？**——建议 q8_0，平衡体积与质量。
2. **v1 融合选方案 B（打包二进制+子进程）还是 C（NDK+JNI）？**——建议 B，最小改动，先跑通；JNI 留 v2。
3. **sd 二进制是预编译打进 APK，还是首次启动从 PC/网络下载？**——建议首次下载，避免 APK 过大。
4. **顺序**：先把 N+1b 桌面端互控（加速/打洞/GUI）收尾，再插入手机出图融合 v1；或者与 N+1b 并行（不冲突，传输共用）。

---

*本计划不新建传输协议、不新建鉴权体系、不依赖 Termux——全部挂接已验收的 N+1b 配对通道，sd.cpp 能力融进天网 APP 本身。*
