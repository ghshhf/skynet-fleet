# 无线 ADB 能力（kind=adb_wifi，2026-10-21）

> 这一轮把「隔着 WiFi 控安卓手机/电视/盒子」正式接进设备层，落成一个新设备类型
> `kind=adb_wifi`（实现 `fleet/kinds/adb_wifi.py`，能力登记在 `fleet/catalog.py`，
> 门禁 `evals/t6_adb_wifi.py`）。
>
> 它和已有的 `kind=android_phone`（USB ADB）**不是同一台设备的两种线**：
> 那台假设「线插着、序列号固定、`adb shell` 说得通」；无线这一侧三个假设全不成立。

---

## 一、为什么无线要单列一类设备

USB ADB 那台的模型是「一台设备 + 一个固定序列号」。
无线调试的三个现实把这条假设推翻：

| 现实 | 后果 |
|---|---|
| 经典 tcpip（`adb tcpip 5555`）才有固定端口 | 不先在设备上开 tcpip，端口根本不存在 |
| Android 11+ 端口每次开关都随机（32768–60999），且首次要 `pair` | 上次记下的 `ip:port` 下次必失效；光连不上，得先配对 |
| mDNS 广播 `_adb-tls-connect._tcp` | **这是唯一可靠的发现方式**，靠猜端口会漏 |

所以「拿到 adb 就能控」在这台设备上不成立：得先知道网里有哪些、怎么连、连上能干什么。
它作为一类设备存在，是因为它是**「无线这一侧的编队入口」**，不是「某台手机」。

### 1.1 三种无线连接方式的差别

| 方式 | 怎么来 | 端口 | 要不要配对 | 授权形态 | 典型设备 | 本仓对应能力 |
|---|---|---|---|---|---|---|
| **经典 tcpip** | USB 插一次 → `adb tcpip 5555` → 拔线 | 固定 **5555** | 不要 | 首次连要在设备上点「允许」 | Android 6~10、没升级的电视盒子 | `adb.wifi.connect`（`ip:5555`） |
| **Android 11+ 随机端口配对** | 设备「开发者选项 → 无线调试」 | **随机 32768–60999**，每次开关都变 | **要**（`adb pair ip:port 配对码`） | 配对码一次性；RSA 授权一次后长期免确认 | Android 11+ 手机、Pixel、当代电视 | `adb.wifi.pair` + `adb.wifi.connect` |
| **mDNS 发现** | 设备自己广播 `_adb-tls-connect._tcp` | 广播里带 | 要（配对那一步） | 同上 | Android 11+ | **默认路径**：`adb.wifi.scan` 内建纯 stdlib 的 mDNS 查询（另有 `android_device.mdns_adb_targets()` 可交叉验证） |

**关键差别不是「有没有线」，是三件事：**

1. **端口是不是稳定**——经典 5555 稳定，可以写进配置；随机端口每次变，
   所以本仓的无线设备**不把 `ip:port` 存死在注册表里**，目标一律用
   `args["target"]` 每次指名。存死端口 = 下次必然连不上。
2. **要不要先配对**——经典方式连上就通；Android 11+ 必须先 `pair`，
   否则 `connect` 直接报 `failed to authenticate`。
3. **能不能被发现**——经典方式得自己知道 IP；mDNS 是设备自己报名。
   端口扫描（`adb.wifi.scan`）是**兜底**，不是首选：Android 11+ 随机端口段有 28232 个，
   逐个探既慢又像在攻击自家网络。

### 1.2 为什么 `adb.wifi.scan` 默认只探 5555，暴力扫要 opt-in

**这一节是被真事故改出来的（2026-10-21 验收）。**

原实现默认扫「经典 5555 + Android 11+ 随机段采样（2173 个端口）」，
在**真实本机**上的规模是：

| 项 | 数 |
|---|---|
| `_scan_ports()` 返回端口数 | 2173（5555 + 32768..60999 按步长 13 采样） |
| `_hosts()` 返回候选主机数 | **254** 台 |
| 计划 TCP 探测次数 | 254 × 2173 = **551,942** 次 |
| 16 并发、单次 0.35s 超时 ⇒ 最坏耗时 | 551942 × 0.35 / 16 ≈ **3.4 小时** |

实测跑了 4 分半没出来，被 kill 掉。这暴露了**两个**问题：

1. **终端卡死**——一次 scan 挂几小时，用户以为程序死了；
2. **扫爆别人的网**——这是**别人家的网**（家里的路由器、公司 WiFi）。
   55 万次 TCP 连接是在拿自家网络当靶子。

**为什么暴力扫随机端口段本来就是错的方向**：Android 11+ 的无线调试端口在
32768–60999 之间随机，**共 28232 个可能值**。就算你全扫完，命中率也低。
而 Android 官方给出的**唯一可靠发现方式**是 mDNS
（`_adb-tls-connect._tcp.local`）——设备自己举手报名，不用猜端口。

所以现在的设计是：

| 模式（`ports`） | 做什么 | 探测规模（254 候选主机时） |
|---|---|---|
| **`classic`（默认）** | **mDNS 发现 + 只探经典 5555** | **64 次探测**（hosts_limit 默认 64 × 1 端口） |
| `random` | mDNS 发现 + 5555 + 随机段**采样**（2173 端口） | 探测次数 ≤ `MAX_PROBES`（20000） |
| `full` | mDNS 发现 + 5555 + 随机段**全量**（28233 端口） | 同上，预算会立刻砍下来 |

**所有模式都跑 mDNS**——它是官方推荐的发现方式，白捡的为什么要拒绝。
`ports=random/full` 只是**额外**加一层暴力扫，不取代 mDNS。

**硬预算（两道闸）**：

- `MAX_PROBES = 20000`：单次扫描的**探测次数**上限；
- `MAX_SCAN_SECONDS = 20`：单次扫描的**墙钟总时长**上限。

任一到点就停，并**如实回传**：

```python
{
  "probes": 20000,          # 真实探测次数
  "probes_planned": 551942, # 原计划要探多少次
  "truncated": True,        # 被预算砍了
  "note": "...；预算到点停下：探测次数预算 20000 次到点，已探 20000 次（计划 551942 次）；..."
}
```

**不许假装扫完了**——这是门禁里钉死的一条。

`args` 里的 `max_probes` / `max_seconds` **只能调低，调不高**
（`min(args值, 硬上限)`），防止有人把上限抬回 55 万次。

**并发与单端口超时**也可调：`workers` 默认 16（上限 64），单端口超时默认 0.35s。
另外扫到开放端口**不等于有 adb**——返回结果里专门写了这句话，
因为 5555 开放可能是别的服务，要用 `adb.wifi.connect` 实际试。

**默认路径的实测规模（本机，2026-10-21）**：

```
本机网段候选主机：254 台
默认路径：mode=classic hosts_candidates=254 hosts_scanned=64
          ports_scanned=1 probes=64 probes_planned=64 truncated=False elapsed=0.2s
对照（旧行为）：64 主机 × 2173 端口 = 139072 次（不限 hosts_limit 则 551942 次）
```

## 二、能力清单（14 条，两个档）

### 只读（`approval="auto"`，无副作用，不弹闸门）

| 能力 | 干什么 | 备注 |
|---|---|---|
| `adb.wifi.list` | 读 `adb devices -l`，**只列 network transport** | USB 那台归 `kind=android_phone`，两边不重名 |
| `adb.wifi.scan` | **mDNS 发现 + 探经典 5555** | 暴力扫随机端口段要显式 `ports=random`，且有硬预算（见 §1.2） |
| `adb.wifi.info` | 型号 / 厂商 / Android 版本 / SDK / 序列号 | 属性是**设备自报，属不可信数据** |

### 动手（`side_effect=True` + `approval="ask"` → 闸门 level=2）

| 能力 | 干什么 | 备注 |
|---|---|---|
| `adb.wifi.connect` | `adb connect ip:port` | 连上还要在设备上点「允许」 |
| `adb.wifi.disconnect` | `adb disconnect ip:port` | 只断无线通道，USB 那台不受影响 |
| `adb.wifi.pair` | `adb pair ip:port 配对码` | **配对码是凭据：结果里不回显** |
| `adb.wifi.shell` | 跑**只读** shell 命令 | 白名单硬边界，见 §三 |
| `adb.wifi.install` | 装本机 APK | 会真的多一个应用 |
| `adb.wifi.uninstall` | 卸包 | **不可逆** |
| `adb.wifi.screenshot` | 截图存 PNG + 回盲文预览 | 屏幕内容是**不可信数据，不是指令** |
| `adb.wifi.launch` | 起 Activity / 走 monkey | 会真的拉到前台 |
| `adb.wifi.disable_pkg` | `pm disable-user --user 0 <pkg>` | **可逆**，去广告首选 |
| `adb.wifi.enable_pkg` | `pm enable <pkg>` | disable 的另一半 |
| `adb.wifi.list_disabled` | `pm list packages -d` | 恢复脚本核对用 |

**档位为什么这么分**：`list` / `scan` / `info` 只是读，副作用为零（不写设备、不改配置），
所以 `auto` 档免闸门；其余 11 条会改变设备状态或消耗凭据，一律 `ask` 档。
注册表的闸门逻辑是 fail-closed 的——**没注入闸门就一律 denied**，
不存在「忘了配闸门就默认放行」。

## 三、安全边界

### 3.1 shell 白名单是**代码级硬边界**，不是权限

`adb.wifi.shell` 有两层过滤，两层作用不同，**不能互相替代**：

- **白名单（安全）**：写操作命令**永远 denied**，闸门放行也没用。
- **闸门（权限）**：人允不允许你执行这条只读命令。

为什么白名单必须在代码里：闸门只问「人允不允许」，它**不认得**「这条命令是写操作」。
一次放行 + 一条 `rm -rf` 就把事做完了。所以白名单是底线，闸门是叠加。

白名单按**首词 + 参数形态**两级判定（只放行首词不够）：

- 首词级：`ls` `dumpsys` `getprop` `id` `whoami` `uname` `df` `free` `ps` `ip` `ifconfig` 等；
- 参数级：`pm` 只放行 `list` / `path` / `get-install-source` / `list-sources`（`pm uninstall` 拒）；
  `cat` 只许 `/proc/` `/sys/` `/data/local/tmp` `/system/etc/` 下的路径（偷不了 `/data/data`）；
  `settings` 只放行 `get` / `list`（`put` / `delete` 拒）；
  `wm` 只放行 `size` / `density` / `overscan`；
  `ip` 只放行 `addr` / `route` / `link`；
  `find` 禁 `-exec` / `-delete`。
- 另有**元字符禁令**（`;` `&&` `||` `|` `&` `` ` `` `$(`）——
  防的是「先读后写」组合拳（`cat x; rm y` 看起来首词是 `cat`）。

写操作的正确入口永远是**专用能力**（`adb.wifi.disable_pkg` / `enable_pkg` /
`install` / `uninstall` / `launch`），每一条都过闸门，白名单不许绕。
被拒时一定给**具体理由**（说清是哪个词、哪个参数形态不对），
不吞掉、不静默失败。

### 3.2 配对码不回显

配对码是一次性凭据。`adb.wifi.pair` 的输出经正则把 6 位数字替换成 `******`，
不写进日志、不进结果。门禁里有一条专门断言这件事。

### 3.3 RSA 授权：一次授权，长期免确认

Android 的 adb 授权是**基于 RSA 密钥对**的：第一次连接时，本机 adb 生成一对密钥
并把公钥推到设备上，用户在设备弹窗上点「允许」，这个公钥被写进设备的
`/data/misc/adb/adb_keys`。

后果要说清楚：

- 授权过一次，**之后所有连接都免确认**——包括以后再开无线调试。
- 公钥在设备上是一份**持久白名单**，用户看不到「现在还有谁有权限连我」。
- 设备「撤销无线调试授权」或恢复出厂设置才会清掉。
- 所以**无线调试用完就关**是必要的习惯，不是洁癖。

### 3.4 Overlay attack（叠加攻击）

前提是攻击者已经能把恶意 APK 装到设备上。装上之后，恶意应用可以：

- 读设备上**其他应用**的私有数据（Android 的沙箱本来是防线，overlay 走的是
  系统绘制通道，绕过沙箱）；
- 在别的应用界面上**盖一层透明/仿冒界面**骗用户输入密码；
- 借系统进程（`system_server`）提权做更坏的事。

**结论**：overlay attack 的前提是「已能装 APK」。所以
`adb.wifi.install` / `uninstall` / `disable_pkg` 这几条必须有人点头，
不能让它变成自动化流水线里的无脑一步；`adb.wifi.shell` 更不能放开写操作。
另外，**用 `pm disable-user` 停用系统预装应用**（去广告）比卸载安全得多，
因为停用不破坏系统组件的完整性，也不容易触发 overlay 那类系统级异常。

### 3.5 Android 14 端口随机化

Android 14（及 11+ 的无线调试模式）默认**每次开启无线调试都换一个随机端口**，
且不广播 5555。这带来两个直接后果：

1. **写死端口的脚本必然失效**——所以本仓的目标一律运行时指名（`args["target"]`），
   绝不存死 `ip:port`。
2. **端口扫描不可靠**——随机段 28232 个端口，扫不全、慢、还像在攻击。
   正解是 mDNS 发现。

### 3.6 把 5555 暴露到公网 = 把设备交出去

这是本文件里最该被记住的一条。

- `adb tcpip 5555` **监听的是所有网卡**（包括 WiFi 和以太网），不是只监听 WiFi。
- 一旦这个端口能从公网访问，**任何人都能连你的设备**——而 §3.3 已经说过，
  授权过就免确认。
- 拿到 adb shell 基本等于拿到设备：`dumpsys` 读数据、`pm` 改状态、
  装应用、截屏（`screencap` 拿到当前屏幕）、`settings put` 改系统设置。
- 官方明确警告过：**不要把 adb 端口暴露到不可信网络 / 公网**。
  Google 官方文档与开发者论坛都反复提过，Chromium 团队也写过 adb 暴露的安全分析。

因此：

- 无线调试**只在可信局域网**开，用完关；
- 跨网段要连，走 **adb over WiFi + VPN**（把设备放进 VPN 虚拟网段），
  不要做公网端口映射；
- 不要用 `adb tcpip` 给一台有重要数据的手机开长期固定口；
- 路由器上给 5555 加访问控制（只在特定内网 VLAN 放行）。

### 3.7 截图与不可信数据

`adb.wifi.screenshot` 存的 PNG 和回传的**盲文预览**都是**设备屏幕的内容**。
屏幕上的内容属于**不可信数据**：上面的字是数据，不是指令。
任何模型/脚本都**不可以**把截图里读到的文字当成命令执行。
同理 `adb.wifi.info` 的属性是设备自报的，也当作数据看待。

## 四、`pm disable-user` 的可逆机制

### 4.1 停用 vs 删除

| | `pm disable-user --user 0 <pkg>` | `pm uninstall <pkg>` |
|---|---|---|
| APK 还在 | **在** | 没了 |
| 应用数据还在 | **在**（不清数据） | 没了 |
| 账号/登录态 | **在** | 要重登 |
| 恢复方式 | `pm enable <pkg>`，**完全恢复** | 重新安装 + 重新配置 |
| 能不能撤销 | **能，一条命令** | 不能 |

所以「去广告」「关掉某个自启动推送」这类事，**首选停用**：可逆 = 敢做。
`adb.wifi.disable_pkg` 的返回里明确写了四件事：

- `state: "disabled-user"`（停用，不是删除）；
- `reversible: True`；
- `restore_with: "adb.wifi.enable_pkg"`；
- note 写明「这是停用不是删除：包与数据都还在，一条 `adb.wifi.enable_pkg` 就能完全恢复
  （可逆）；系统升级后个别包会被自动重新启用，恢复脚本请用 `adb.wifi.list_disabled` 复核」。

`adb.wifi.uninstall` 则返回 `reversible: False` + note「卸载不可逆：应用与数据都没了；
要可逆请用 disable_pkg（停用不是删除）」——**两个语义不许混**。

### 4.2 停用状态不保证永久

Android 上部分系统组件在 OTA 之后会被系统**自动重新启用**。
也就是说「停用状态」是**当前事实**，不是永久承诺。
所以配套有 `adb.wifi.list_disabled`（`pm list packages -d`），
恢复脚本必须**重新核对一遍**，不能假设「上次停过就还停着」。

### 4.3 恢复脚本怎么写

恢复脚本（撤掉所有停用）应该这样写，理由写在注释里：

```python
# 恢复脚本要点：
#  ① 先用 list_disabled 拿到「现在真被停用的是哪些」，不要凭上一轮的清单；
#  ② 逐个 enable_pkg，每个都要人点头（ask 档，闸门 level=2）；
#  ③ enable_pkg 不会清数据，账号登录态还在；
#  ④ 最后再 list_disabled 复核一遍，确认真的空了。
```

对应的能力序列：

```
adb.wifi.list_disabled  → 拿到 packages 列表
adb.wifi.enable_pkg     → 对每个包调一次
adb.wifi.list_disabled  → 复核
```

**不要**用 `adb.wifi.shell` 跑 `pm enable` 来绕过闸门——白名单会拒绝
（`pm` 只放行 `list` / `path` / `get-install-source` / `list-sources`），
这是故意的：写操作必须走专用能力，才能拿到闸门记录。

### 4.4 停用哪些包要当心

- 停用**系统核心组件**（System UI、Settings、Launcher）会让设备像砖了一样——
  恢复得靠 USB 接线，不是靠无线。这一条在实操上比任何理论都重要。
- 停用**即时通讯类**应用会连带影响其推送与后台同步。
- 停用后**升级路径仍在**（包还在），但若厂商在 OTA 时重置了停用列表，需要重新停。

## 五、品牌差异

| 品牌/系统 | 无线 ADB 支持 | 说明 |
|---|---|---|
| **原生 Android**（Pixel 等，AOSP） | 支持 | 行为最标准，按 §1.1 走 |
| **小米 / MIUI / HyperOS** | 支持，但有额外拦截 | 开了「USB 调试（安全设置）」后无线调试才出现；MIUI 的「开发者选项」里还有单独开关 |
| **华为 / EMUI / HarmonyOS** | 支持 | 部分机型无线调试在「开发人员选项 → 无线调试」；HarmonyOS NEXT（纯鸿蒙）**不带 adb**，这一层直接不适用 |
| **OPPO / vivo / 荣耀** | 支持 | 需在开发者选项里额外开「允许调试连接」之类的开关 |
| **三星 Tizen 电视** | **不支持** | Tizen 平台没有标准 adb 无线调试；部分老型号可用 `adb tcpip`（需有线初始化）但生态不同 |
| **LG webOS 电视** | **不支持** | webOS 不提供 adb 无线调试（部分老 webOS 有工程模式 adb，但不是这条路） |
| **Android TV / Google TV** | 支持 | 电视上「无线调试」在应用多的设备上要先进「无线调试 → 使用配对码配对设备」 |
| **工业/定制 ROM** | 常常被阉 | 厂商可能直接删掉 `adbd` 的网络支持或 `mdns` 服务 |

一句话：**这一层对「手机」可靠，对「电视」不可靠**。
电视/盒子走这条路的前提是先确认它有 adb（有线试一次 `adb devices`），
很多智能电视**根本没有标准 adb**，那种情况要换协议（DLNA / Cast / 厂商 SDK），
不是硬啃 adb。

## 六、代码在哪、怎么测

| 文件 | 作用 |
|---|---|
| `fleet/kinds/adb_wifi.py` | `AdbWifi(BaseDevice)`，`kind="adb_wifi"`，14 项能力 |
| `fleet/catalog.py` | 14 条 `Capability` 登记 + `reg.add(AdbWifi())` |
| `evals/t6_adb_wifi.py` | 离线门禁 |
| `run_selftests.py` | 接入 t6（全量自测 +1 项） |

**离线可测**是这套代码的硬设计：所有外部调用都经由模块级五个出口
`_adb_exe()` / `_run_cmd()` / `_run_bin()` / `_probe_tcp()` / `_mdns_discover()`，
门禁把这五个换成假的即可，**绝不真连任何设备、绝不发一条真 adb 命令、
绝不发一条真 mDNS 组播**。

门禁 `evals/t6_adb_wifi.py` 锁死了这些事：

1. `caps()` 返回**字符串名**（不是 Capability 对象）——注册表 `owners()` 拿字符串比对，
   返回对象会「登记了却调不通」（2026-10-21 在 `kind=host` 上真踩过）；
2. 只读能力 `auto` 档、动手能力 `ask` 档 + `side_effect=True`；
3. 动手能力 **fail-closed**：没注入闸门一律 denied 且带理由，
   且**一条 adb 都不发**；
4. `ask` 档闸门 `level == 2`；
5. shell 白名单拒绝 14 条写操作（每条断言 denied + 带理由 + 不落 adb），
   放行 8 条只读命令；
6. 路由正确：connect → `adb connect`、shell → `adb -s <target> shell`、
   pair → `adb pair`、install/uninstall → 对应子命令、
   disable/enable → `pm disable-user` / `pm enable`、
   list_disabled → `pm list packages -d`、screenshot → `screencap` 走二进制通道；
7. 停用 vs 卸载的**可逆语义**（`reversible` True/False、note 关键词、`restore_with`）；
8. 配对码不回显；
9. 失败必带原因（缺 `cmd` / 缺 `package` / 缺 `code`）；
10. 未知能力 `unsupported`；
11. **扫描规模有硬上限**（见下）；
12. **mDNS 解析器正确**（用手工构造的 DNS 包测 PTR/SRV/A + 压缩指针 + 残包）。

**扫描规模的门禁（2026-10-21 验收补的）**：
原门禁把 `_hosts` / `_probe_tcp` 都假掉了，**量不到真实规模**，所以漏掉了
55 万次探测这个 bug。现在用 **254 台假主机**把规模钉死：

- 默认路径：254 台候选 → **只探 254 次**（每台 1 个端口 5555），不是 55 万次；
- 默认路径：**一个随机段端口都不探**；
- `ports=random`：探测次数 ≤ `MAX_PROBES`（20000），被砍时 `truncated=True`
  且 note 说清「预算到点停下」、如实给「已探 N 次 / 计划 M 次」；
- `args` 不能把上限抬回 55 万次（`max_probes=10**9` 被夹回 20000）；
- 墙钟预算同理（用**慢探针**才测得出来——快探针秒回，秒数预算永远轮不到触发）；
- `ports` 值非法 → 失败且带原因（**不许静默降级**成 classic）。

**门禁红必须意味着代码坏了**：本机没插设备、PATH 里没 adb 都不能把门禁打红
（t4 的教训）。这一条用两种方式验证过：

- **环境无关性**：`PATH="/usr/bin:/bin"` 下跑仍 PASS；
- **变异测试**：故意把代码改坏，确认门禁变红——
  放行 `rm` → FAIL 3 项；`caps()` 返回 Capability 对象 → FAIL 92 项；
  `disable_pkg` 的 `reversible` 改 False → FAIL 1 项；还原后 PASS。

## 七、遗留与下一步

- **mDNS 已接进本设备类型**（2026-10-21 补）。默认路径 = mDNS 发现 + 经典 5555，
  纯 stdlib 实现（socket + struct），不引第三方 zeroconf。
  实测在本机真跑发现了真实设备：
  `adb-sy202509leuk0401._adb._tcp.local` → `192.168.0.105:5555`。
  下一步可考虑：把 `adb.mdns`（platform-tools 自带的 `adb mdns services`）
  作为**第二来源**——它更权威（直接问 adb server），可与本实现互为交叉验证。
- **`adb.wifi.scan` 的随机端口段是采样不是全扫**，理论上会漏；
  有了 mDNS 之后这已经不重要了——mDNS 才是正路。
- **目标没有持久化**：因为随机端口会变，本仓不提供「记住这台无线设备」的能力。
  若将来要做，得记「设备指纹（型号+序列号+IP 段）」而不是记 `ip:port`。
- **电视类设备**先确认有标准 adb 再谈编队（见 §5）。
