# 视频 / 漫剧技术路线（2026-10-30 晚）

> 起因：主人看完第一版手机视频说「做的有点太过于奇怪了，你估计那个时间帧啊之类的有点没用对」。
> 结论：**他说对了，是时间轴的问题，不是画质的问题。** 本文是查证 + 重做 + 实测的完整记录。
> 所有数字都是本机真跑出来的，没有估的。

## 一、市面上的视频模型，到底有哪几类

查到的东西按「怎么产生运动」分成三类，这是理解一切的钥匙：

| 类 | 代表模型 | 运动从哪来 | 一句话 |
|---|---|---|---|
| **① 视频扩散**（真·时空模型） | AnimateDiff（SD1.5 + motion module）、SVD、CogVideoX、LTX-Video、Wan 2.x、Seedance 2.0、Kling 3.0、Sora 2、SkyReels-V4 | 模型内部有「时间维」的注意力，一次吐出 N 帧 | 质量天花板最高，**但要吃显存、要 GPU**，手机上不可能 |
| **② 逐帧 img2img 链** | Deforum（2D/3D 模式）、ebsynth 类 | 把上一帧当输入，重新采样 | 算力需求 = 单张出图，**手机能扛**，但运动靠模型自由发挥 |
| **③ 出图 + 补帧** | RIFE / FILM 插帧、SVD 做「图生视频」 | 先出关键帧，再用光流网络插中间帧 | 关键帧少、插帧便宜；RIFE 要跑一个网络（手机得转 ncnn/MNN） |

**关键认知**：①是「模型自己知道时间」，②是「人不给时间，模型瞎猜」，③是「时间由插帧器猜」。

我们原来的做法是 ②，而且**连 Deforum 该有的那半套都没做**——
Deforum 在 img2img 之前会先 `cv2.warpPerspective` 把上一帧按 (zoom, pan, rotate) 变一次，
运动由几何精确决定，模型只补细节。我们只做了「丢给 img2img」，
等于把运动权也交给了模型 —— 所以每帧都在重新构图，观感就是抽搐 + 无目的漂移。

> 出处：`deforum-stable-diffusion/helpers/animation.py:184-213`（`anim_frame_warp_2d`），
> 关键帧调度格式 `frame:(value), frame:(value)`，`get_inbetweens()` 用 pandas 线性插值填中间帧。

### 手机端为什么用不了 ①

local-dream 的模型是 **QNN 预编译的 `.bin`**（`unet.bin` + 按分辨率切的 `512.patch` / `768.patch`），
不是 safetensors。这意味着：

- ❌ **装不了 LoRA**（AnimateLCM、MotionLoRA、IP-Adapter 全是 LoRA 形式）——这是最致命的一条
- ❌ 装不了 motion module（AnimateDiff 的核心就是一个 `mm_sd_v15_v2.ckpt`）
- ⚠️ 理论上能塞自编译的 `.bin`，但要过 Qualcomm AI Hub / QNN SDK 编译，不是拉个文件就行
- ✅ 能做的：SD1.5 全流程 t2i / img2img / 超分，尺寸受 patch 表限制

**所以「手机上跑真视频扩散模型」这条路，当前是关着的。** 这不是算力问题，是工具链问题。

### 我们最终选的路线（第三类变体，比 ② 强、比 ① 便宜）

```
关键帧稀疏生成（模型） → 播放帧几何合成（不调模型）
```

具体是 `fleet/motion.py` + `video_gen_runner.localdream_backend`：

1. **关键帧**：`gen_fps = 2~6` 张/秒。每张生成前，先把上一关键帧按相机轨迹
   `warp` 到当前视角，再当 img2img 输入，denoise 保持 0.28（低）。
   → 运动精确可控，模型只负责补细节和刷新纹理。
2. **播放帧**：`fps = 24~30`。**不调模型**，用两张相邻关键帧各自 warp 到该时刻、
   再按 smoothstep 交叉混合：
   ```
   P(t) = lerp( warp(K[i],   cam_i   → cam_t),        // 都已推到同一视角
                warp(K[i+1], cam_{i+1} → cam_t), p )
   ```
   两个候选像素几乎对齐，混合不重影，只轻微软化。
3. **步骤分层**：首帧全步数（定调），后续 `steps × 0.65`（低 denoise 走不满轨迹，
   全步数纯烧时间）。512×768 实测 9.0s → 5.5s/帧。

**为什么这比 RIFE 插帧更适合我们**：RIFE 要再跑一个网络（手机上还得转 ncnn/MNN），
而我们的中间帧本来就是「相机动了、内容没变」，几何 warp 是精确解，不是猜的。

### 相机模型（`fleet/motion.py`）

`Camera = (cx, cy, s, theta)`：画面中心、放大倍数、滚转角，**全是绝对量**。

绝对量这一点很关键：Deforum 的 `zoom: 0:(1.02)` 是「每帧 ×1.02」的**增量**，
所以改 fps 就会改速度（这是它的老毛病）。我们改成 `Track.at(t)` 直接求值，
fps 与运动速度彻底解耦，关键帧稀疏、插值、跳帧都不会累积误差。

预设运镜：`push_in / pull_out / pan_left / pan_right / tilt_up / tilt_down / dolly / sway / orbit / none`。
也支持关键帧表 `Track(keys=[(0,{}), (2,{"zoom":1.15}), (4,{"zoom":1.15,"pan_x":0.06})])`。

## 二、「画布」是什么

客户说的「画布」有两个完全不同的意思，我都查了：

### 1. 节点式无限画布（工作台形态）

2026 年 AI 漫剧/短剧的**生产工具形态**。Pixmax、LibTV、Zoviz Canvas、星宇智算、
卓特视觉这些平台都是这个套路：

- 一块可无限平移缩放的二维空间
- 每个单元是一个**可执行节点**（提示词 / 参考图 / 出图 / 图生视频 / 配音 / 超分 / 导出）
- 节点连线成 **DAG**，上游输出自动流进下游
- 改上游 → 下游全部重跑；整套流程存成模板，下次换 brief 直接复用

它的价值不在「画布大」，在**流程可追溯、可分支、可复用**：
传统对话框是「填提示词→出图→拿结果」的线性黑盒，改一个参数就得重来一遍。

→ 我们的对应物是 `fleet/storyboard.py` 的 **board 数据 + 一次调用**。
   手机端不需要可视化画布（那是人机交互层），需要的是「一份 DAG 描述 → 一条成片」，
   所以压成了 JSON。

### 2. 成片画布尺寸（分辨率/宽高比）

这个是技术约束，更硬：

| 画布 | 尺寸 | 用途 | 手机出图尺寸（自动挑） |
|---|---|---|---|
| `9:16` | 1080×1920 | 抖音/快手竖屏漫剧 | 512×768（裁掉 15.6% 宽） |
| `16:9` | 1920×1080 | 横屏剧情/B站 | 768×512（裁掉 15.6% 高） |
| `3:4` | 1080×1440 | 小红书 | 768×1024 |
| `4:5` | 1080×1350 | 朋友圈 | 768×1024 |
| `1:1` | 1080×1080 | 方图 | 512×512 |
| `2.39:1` | 1920×804 | 电影宽银幕 | 768×512 |

**为什么必须自动挑**：手机只认 7 个尺寸（有对应 patch），表外尺寸会**静默回退 512 出彩色噪声**
——不报错，直接给你一张花的。所以画布定了之后，出图尺寸是按宽高比对数距离最近的来选，
再 `cover` 裁切到画布。裁切比例最多 15.6%，构图靠提示词里的 `wide shot / medium shot` 控制。

## 三、漫剧的工业流水线（查到的 + 我们对得上的）

2026 年主流做法已经固化成五步（多篇行业拆解口径一致）：

```
剧本(LLM 出 JSON 分镜) → 角色定妆(一致性) → 图片生成 → 图生视频 → 配音配乐 → 剪辑成片
```

行业规范值（抄来直接用的）：
- 每集 **10~14 个分镜**，单分镜 **2~5 秒**
- **前 3 镜完成钩子**，中段推进冲突，末尾留反转
- 竖屏 1080P、30fps、**字幕每行 ≤15 字**、配乐低于人声 6~10dB、FFmpeg `crf=23`

角色一致性是命门，成熟方案是 IP-Adapter FaceID Plus v2 + ADetailer + 专训 LoRA（30-50 张，一致性 97%）。

**我们逐环节的诚实对账：**

| 环节 | 我们的做法 | 差距 |
|---|---|---|
| 分镜脚本 | board JSON，可由 LLM 直接生成 | 无 |
| 角色一致性 | 文字锚点 + 固定 seed | **做不到** LoRA 那级；无法多角度锁定 |
| 出图 | 手机 QNN NPU，512~1024 | 低一档，需超分补分辨率 |
| 图生视频 | 稀疏关键帧 + 几何运镜 | 没有真视频扩散 |
| 配音 | edge_tts（在线，中文音色可选） | 可用 |
| 剪辑 | 画布适配 + 转场 + 字幕 + 混音（本机 ffmpeg） | 可用 |

### 这里补上了「时间帧」的另一半

漫剧里镜头时长**不是拍脑袋定的，是台词念完需要多久**。
所以 `run_board` 的顺序是：

```
① 先合成台词配音 → 拿真实语音秒数
② 镜头时长 = max(编剧写的, 语音 + 0.35s 呼吸)
③ 再反过来出画面
```

实测效果（4 镜头那段）：编剧全写 2.5 秒，配音实测 3.19/3.43/2.90/2.28 秒，
最终镜头被拉成 **3.54 / 3.78 / 3.25 / 2.63 秒** —— 如果按 2.5 秒硬切，
每句台词都会被掐尾。这就是「时间帧没用对」的第二个来源。

## 四、实测定量（这才是重点）

### 旧做法 vs 新做法，同 prompt / 同 seed / 同模型

| 指标 | 旧（逐帧 img2img 链） | 新（稀疏关键帧+运镜） | 新（更稀疏 2/秒） |
|---|---|---|---|
| 帧间差 mean | **12.33** | 3.36 | 2.15 |
| 帧间差 max | 12.86 | 4.40 | 3.38 |
| 帧间差 std | 0.30 | 0.78 | 0.63 |
| 亮度漂移 | 0.5 | 1.6 | 1.5 |
| 边缘保留 | 93% | 88% | 89% |
| 画面观感 | 无目的漂移（礁石/房子/闪电位置每帧都变） | 稳定推近 | 稳定推近 |

「帧间差」= 相邻播放帧的平均像素差。旧做法每秒 12 次大跳（12×12.33=148/秒），
新做法 24 次小步（24×3.36=80/秒），**运动总量更小，但有方向**。
这就是「抽搐」和「运镜」的量化区别。

### 产能实测（手机 K60 / 8+ Gen 1 / QNN HTP）

| 项目 | 实测 |
|---|---|
| 512×512 / 8 步 / t2i | 4.0s |
| 512×512 / 12 步 / t2i | 5.4s |
| 512×768 / 8 步 / t2i | 6.3s |
| 512×768 / 12 步 / t2i | 9.0s |
| 512×768 / 12 步 / **img2img（分层后 8 步）** | ~5.5s |
| 512×512 + 4× 超分 → 2048² | 8s 总计 |
| 排版（PIL，1080p） | 0.2s |

### 优化过程（同一个 4 镜头 13 秒漫剧）

| 版本 | 关键帧 | 总耗时 | 做了啥 |
|---|---|---|---|
| 第一版 | 44 | **562s** | gen_fps=3，每帧全步数，PNG 中间帧，逐帧重排字幕 |
| 第二版 | 31 | **320s** | gen_fps=2 + 步骤分层 |
| 第三版 | 31 | **261s** | 字幕图层复用（整镜头渲染一次）+ JPEG 中间帧 + 编码 preset |

**261 秒 = 4.35 分钟，出 13.2 秒竖屏漫剧**（4 镜头、1080×1920、24fps、字幕、配音、BGM、淡入淡出+叠化）。

### ⇒ 10 分钟能干多少

- 纯出图（512×512 4s/张）：**约 150 张**
- 单镜头视频（3 秒，gen_fps=2，8 关键帧）：**约 4 个镜头 ≈ 12 秒**
- 完整漫剧（分镜+字幕+配音+转场）：**约 13~15 秒成片，4 个分镜**
- 极限省（gen_fps=1.5、steps=8、512×512）：**约 25 秒成片，7-8 个分镜**

一集 1 分钟的标准漫剧（12 个镜头）在这个速度下要 **20~25 分钟**。
这是真实数字，不是「理论上」。

## 五、把引擎夺过来：不经过 App 的直驱（2026-10-31 凌晨）

上一版我们还在「借 App 的能力」：控制口 8808 是 App 的 RemoteHostService 提供的，
出图要 App 在线、要开 host mode。这一版把中间那层拆了。

### 引擎到底是什么

local-dream 的 App 只是个壳，它 exec 的是自带的 native 可执行文件：

| 二进制 | 大小 | 覆盖类型 |
|---|---|---|
| `libstable_diffusion_core.so` | 12 MB | sd15cpu / sd15npu / sdxl / sdxlmnn / anima |
| `libdit_engine.so` | 56 MB | zimage / klein / qwen21 / krea2turbo（DiT 系） |

它本身是**命令行 HTTP 服务**：`--type --model_dir --lib_dir --patch --port --listen_all`，
还有 `--upscaler_mode`、`--convert <dir>`。**所谓「NPU 引擎」就是它**，拿到它等于拿到手机算力。

### 踩出来的三个硬坑

1. **SELinux 域决定能不能用 NPU。** 以 `run-as <pkg>` 身份跑 → `createUnsignedPD failed, 0x3`（PD 申请被拒）；
   换成 `adb shell`（u:r:shell:s0）→ 正常过。二进制和库一模一样，只有域不同。
2. **私有目录读不到。** 模型在 App 私有目录里，shell 身份看不见。解法是跨身份管道：
   `run-as pkg sh -c 'cd files && tar cf - models runtime_libs' | tar xf - -C /data/local/tmp/ld`
3. **HTP 独占。** 同时只能一个 diffusion 进程，换模型/换分辨率必须先 kill 旧的，且 kill 后要等 ~1.5s 再拉新的。

### 结果（同一台 K60，App 全程处于 force-stop 状态）

- HSV: 512×512/12 步 **5.1s** 起（进程已热）、冷启动含模型加载约 22~25s
- 512×768 / 768×512 自动带对应 patch 重启正确出图，不再是彩色噪声
- 与ylon sv gen-video + 本地 TTS 串起来：**4 镜头 10.2 秒成片，274 秒** 完成

### 关于「为什么只能用那几个预设模型」

App 内置的那几个模型是**编译过的 QNN 权重**（unet.bin / clip / vae_decoder 各自一个 .bin），
所以不能直接拿 safetensors 往里丢。但引擎自带 `--convert`：
把 `model.safetensors` 放进目录跑一次就能转成 MNN 权重再用。这条已经验证过入口存在
（`src/main.cpp:305 runConvertMode`，还顺带支持 `lora.N.safetensors` + `lora.N.weight`）。
下一步就是把 DreamShaper / RealisticVision 这类更好的底模转上去。

## 六、配音本地化（同夜）

原先 `storyboard.tts()` 只走 edge_tts（要联网、要有微软端点）。现在改成**先本地、再云端**：

- 主体：`sherpa-onnx`（v2.0.1 aarch64 静态二进制 + libc++_shared.so + ChatTTS/MeloTTS 中文模型）
  直接 adb 推上手机跑，不联网、不依赖任何 App
- 实测：Chinese 短句 **RTF ≈ 0.48**（4.5 秒语音 2.2 秒合成），44.1kHz → 统一降到 24k 单声道再进混音
- 保值：本地挂了才退 pc_sherpa，再退 edge_tts；失败原因写进异常，不静默静默

## 七、还没做的（别当已经做完了）

1. **角色一致性**：没有 IP-Adapter/LoRA，只能文字锚点 + 固定 seed。
   多镜头同一角色，脸会变。这是手机 QNN 路线最硬的天花板。
2. **真·视频扩散**：捕捉运动的能力还是「几何 warp + 关键帧」，K 帧之外motion 不是模型算的。
   更长的连续动作（5s+）会漂。
3. **口型对齐**：漫剧的音画同步（SkyReels-V4 那一套）完全没有。
4. **长镜头**：ism같单镜头 30 秒内没问题，再长关键帧链会累积漂移（有稳定器但没验证过 30s+）。
5. **BGM**：现在是 `audio_synth` 合成音，不是真正的配乐库。
6. **自己的模型**：`--convert` 已在 GC: VERIFIED 入口存在，但还没实测跑通，且 DiT 系模型需要另行验证。
7. **./ sosb资产管理**：模型目前放在 `/data/local/tmp/ld`（临时目录），重启/清理会没，需要落 स्थ长期目录。
