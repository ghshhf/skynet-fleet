# 设备层 + 终端层扩展计划书（2026-10-21，只出书，不动手）

> **本轮定调（用户重述）**：hermes 的真正价值是「**它是个终端**」——有了参考方向，终端不必自己从零造；有了终端，整个未来计划的每一层才有显影面。所以这份计划从「设备层」升级为「**设备层 + 终端层**」双主轨。
>
> 参照物：`NousResearch/hermes-agent`（MIT，浅克隆实测 **9,962 个 .py / 250.3 万行 / 357MB**；agent/ 322、tools/ 284、gateway/ 274——平均每个文件 251 行，碎片化程度可量化）。
> 本轮要解决的不是「再加一个天线」，而是**天网没有「设备」这个概念**——44 个根目录脚本各自认识一台具体设备，没有一层能说「这台设备是什么、能干什么、现在能不能干」。

## 一、先看 hermes：抄什么，不抄什么

### 1.1 它到底是什么

一个**自进化的个人 agent 产品**：终端 TUI + 七个消息平台网关（Telegram/Discord/Slack/WhatsApp/Signal/Email/Home Assistant），跑在 VPS 上，模型可换（OpenRouter/GLM/Kimi/NIM/OpenAI/自定义端点），核心卖点是「闭环学习」（从经验造技能、技能自我改进、FTS5 会话搜索、Honcho 用户建模）。

**它不是设备编队**。它只有「执行环境」概念，没有「设备」概念。

### 1.2 值得抄的四件东西（都是设计，不是代码）

| 它的做法 | 我们对应缺的东西 | 证据 |
|---|---|---|
| `BaseEnvironment` ABC（804 行）：`execute / fetch_file / init_session / cwd 追踪 / kill 进程树` 一套接口套住 local、docker、ssh、singularity、modal、daytona、vercel_sandbox | 我们的 `android_device.py` / `pc_state.py` / `sweep.py` 各有一套自己的返回结构，调用方得记住「这个模块返回 dict、那个返回 tuple」 | `tools/environments/base.py:256` |
| **插件化后端注册 + 内置名保留**：`terminal_env_registry`，插件不许覆盖内置名，注册即被 `_create_environment` 选中 | 加一类设备 = 改 `commander.py` 加分支。没有「丢一个文件就多一类设备」的机制 | `agent/terminal_env_registry.py:17-46` |
| **「为什么不可用」要传到用户面前**：`terminal_backend_unavailable_reason()`——失败原因存全局，CLI 启动提示和 `hermes doctor` 都读它，用户第一次用之前就知道为什么没有这个工具 | 我们的 `caps` 已经做了这件事（这点我们是对的），但只覆盖手机，没覆盖「设备」 | `tools/terminal_tool_backends.py:47` |
| 工具注册表：每个工具文件自己 `registry.register(name, schema, toolset, check_fn)`，工具集（toolset）按会话下发，deferred 工具按需加载 | 我们的能力是函数名，没有 schema、没有 check_fn、没有「按会话下发」——所以她/本地模型/MCP 都无法「发现」能做什么 | `tools/registry.py:216`、`toolsets.py` |
| 进程注册表（后台进程 + 等待策略 + 输出日志 + 终止） | 我们的长任务靠 `queue_store` + 人肉 `tail`，没有统一生命周期 | `tools/process_registry*.py` |
| 审批分层（`approval_floors` / `yolo` / `gateway_wait` / `smart`） | 我们只有 `_gate()` 一个布尔闸 | `tools/approval_*.py` |
| **`evals/`：一故障一脚本**（74 个独立场景，每个是一次真实翻车的可复现复现，如 `ws_orphan_reconnect.py`） | 我们的 `run_selftests.py` 31 项都是「函数返回对不对」，**没有一个脚本复现「桥被 MIUI 杀掉」「热点占满射频扫不到 AP」这类真事故** | `evals/` 74 个场景 |
| 注意别认错：`agent/transports/` 是 **LLM 线路层**（anthropic/chat_completions/bedrock/codex），**不是设备通道**——它全仓库确实没有设备层 | 这点反而证明我们这条路是原创的 | `agent/transports/` |

### 1.3 明确不学的

| 它的毛病 | 我们的判断 |
|---|---|
| 病态碎片化：`auxiliary_*.py` 40 个、`hermes_constants_scratch_stuck.py` 这种文件名进仓库、291 个工具文件 | 这是「产品靠堆积演化」的产物。我们保持「大模块 + 少量文件」 |
| 8 层 provider 抽象（provider→registry→adapter→endpoint→credentials→hooks→health→key rotation） | 过度。我们只需要「transport → device → capability」三层 |
| 云端产品假设（VPS 常驻 + Telegram 是主入口 + 订阅制 Tool Gateway） | 我们本地优先、主人人格、设备是身体。可以借网关思想，不借它的托管模型 |
| 多语言 README / badge / Discord 营销 | 无关 |

### 1.4 三条可选的接法（这是长计划里的关键判断，不是本轮要做的）

| 方案 | 做什么 | 成本 | 我的评价 |
|---|---|---|---|
| **A. 只借 MCP** | 天网把设备能力暴露成 MCP server，hermes（或任何 agent）通过 MCP 操控我们的设备 | 低（我们写 server，它写 config） | **推荐先做**。双方各自演进，不合并代码 |
| **B. 写 `fleet` 终端后端插件** | 用它的插件接口注册一个新 backend，让它的 `terminal` 工具直落天网任意节点（手机/路由器/树莓派），而不是只在本机 | 中（要读它的 `TerminalEnvironmentProvider` 契约） | 可选。价值是「它的 shell 能伸到设备上」，但只解决 shell 一类能力 |
| **C. 直接拿它当「她」的外壳** | 省掉我们写 persona/gateway/cron/skills 的全部工作量，只留天网做身体 | 高（人格要重写进 `SOUL.md`，我们的「她」跟它的 SOUL 是两套语言） | **暂不**。她的记忆/宪法/主人口吻是这套东西的根，换外壳等于换人 |

结论：**A 立刻做，B 观察，C 不动。**

还有第四条，但它不是「选项」而是这份计划的第三章：**抄它的终端信息架构，不用它的技术栈**（React+Ink 换成 prompt_toolkit+rich）。你给这个仓库的核心意图就在这里——它的价值不是「又一个 agent」，而是「原来终端可以长成这样」。

## 二、天网现在的真实差距（不是感觉，是清单）

| 层 | 现在有什么 | 缺什么 |
|---|---|---|
| 传输 | node_agent 明文 socket + 密码；adb；手机桥（8765）；蓝牙；红外（经手机） | 没有统一「transport」抽象；没有 SSH/HTTP/RTSP/MQTT/串口；没有 TLS |
| 设备 | 一台 Android 手机、一本机 Windows、局域网 IP 列表 | 没有「设备对象」；45 台局域网设备里我们只认得 IP+MAC，**一台都操控不了** |
| 能力 | 44 个模块里的函数 + REPL 十几条命令 | 没有注册表、没有 schema、没有 check_fn、没有「不可用原因」的统一出口（`caps` 只覆盖手机） |
| 编排 | `orchestrator.py`（111 行，能带依赖+回滚）、`capabilities.py` **还在 `origin/feat/capability-self-description` 分支上没合** | 能力索引接不上真实设备表 |
| 出口 | REPL（人敲） | 没有 MCP、没有 HTTP API、没有网关——所以「她」和本地模型都无法调用设备 |
| **终端（T）** | `input("cmd> ")` 单行；42 个 `elif`；19 行手写 help；`print` 与她的话会插进输入行 | **没有终端层**——不是缺美化，是缺「一个能让所有能力显影的界面」（详见第三章） |

**一句话：我们现在是一堆「能用的脚本」，不是一层「可被发现、可被调用、可被编排的设备层」，而且没有一个能让这些东西显影的终端。**

## 三、终端层（T）：为什么它是要先立的那根线

你把 hermes 给我，指向的不是「再抄一个 agent」，而是**它是个终端**：

> 「这个项目相当于做的是一个终端。这样咱们才有终端，要不然很多东西只能自己造；有参考方向，制作就更简单了。加上这个参考方向，整个未来计划更新就有了——把咱们所有能接触到的一切、整个计划书的一切，有个终端界面。」

所以终端不是「顺便做个界面」，它是**所有计划的显影面**：设备层能干什么、她现在想说什么、规则昨天触发了什么、一次跨设备意图执行到第几步——全都在这一屏上发生。没有它，前面每一层都只是仓库里的函数，只有我一个人（AI）知道怎么调。

### 3.1 它的终端是怎么做的（实测，但别照着抄栈）

- 技术栈：**React 19 + 自己 fork 的 Ink**（`ui-tui/packages/hermes-ink`）+ nanostores + TypeScript，npm 构建（`npm run build:ink`）。
- 它自夸的五件事：多行编辑、斜杠命令自动补全、对话历史、中断重定向、流式工具输出。
- **这五件是信息架构，跟 React 无关。**
- **不抄栈的理由**：我们是纯 Python + Windows + Git Bash，本机没有 npm 链，Ink 的 Windows 支持历来是坑。为了一个终端引入 Node/React，是给身体装一个外国关节。

### 3.2 我们用什么：`prompt_toolkit` + `rich`（本机都还没装，纯 Python、可离线 wheel）

| 它给什么 | 对应哪句需求 |
|---|---|
| 多行编辑 + 历史 + 补全 | 跟她说话不该一行一行敲 |
| 底部状态栏常驻 | 她在不在 / 手机在不在 / 几台设备在线，一眼看到，不用敲 `caps` |
| 流式输出不打断正在输入的行 | 她开口时我正在打字，不该把我的字冲掉 |
| rich 的表格与面板 | `caps` / `phone status` / `usage` 不再是一坨手写 print |

### 3.3 现在的 REPL 有多痛（实测数字，不是感觉）

| 症状 | 证据 |
|---|---|
| 单行输入，无历史、无补全、无多行 | `commander.py:1618` → `line = input("cmd> ")` |
| 分发是 **42 个 `elif op ==`** | `grep -c 'elif op ==' commander.py` = 42 |
| 帮助是 **19 行手写 `print("      \| ...")`** | `grep -c 'print("      \|'` = 19 |
| 加一个能力实际要改三处 | `elif` + help + `accounts.ORDER_OPS`（分权表） |

⇒ 这就是「**终端必须由注册表驱动**」的硬理由：注册表一改，命令、补全、帮助、状态栏全自动跟着变。否则每加一类设备，我们都要在三个地方手工登记，漏一处就是「能力存在但没人知道」。

### 3.4 三个出口，一张注册表

```
              ┌──────── registry（唯一真相）────────┐
              │       设备 / 能力 / schema          │
              └───┬───────────────┬─────────────┬───┘
        TTY 终端（人）      MCP（模型/别的 agent）   网关（手机：微信/Telegram/一页 HTML）
```

终端是「人在电脑前」，MCP 是「模型在调用」，网关是「你在外面用手机」。**三者不许各写一套命令**——这是这张图唯一的要求。

### 3.5 终端必须装下的四类东西（也就是它的验收）

1. **一行命令调任意能力**：`screen.read --device phone`，补全候选来自注册表，不是硬编码列表。
2. **她主动开口在同一屏，但不打断正在输入的行**（现在的 `print` 会直接插进 `input()` 的提示符里，把字冲掉）。
3. **设备事件流**：上线/掉线/异常滚动显示，可回溯（`journal` 已经落盘，缺的是显示）。
4. **一次跨设备意图的执行过程可见**：`orchestrator` 的每一步、成/败/回滚，逐行出现，失败停在那一步并说清原因。

## 四、设计：一台设备 = 一个 adapter，一项能力 = 一条注册表记录

```
fleet/                        # 新包（旧脚本原地不动，先写 shim 适配，不搬代码）
├── core/
│   ├── device.py             # BaseDevice ABC：probe() / invoke(cap,args) / caps()
│   ├── result.py             # 统一结果信封（见下）
│   └── registry.py           # 设备表 + 能力索引，落盘 ~/.fleet/devices.json
├── transports/               # 「怎么连」——一类通道一个文件
│   ├── tcp.py                # 现有 node_agent 协议
│   ├── adb.py                # 手机/电视/盒子
│   ├── ssh.py                # Linux/macOS/OpenWrt/PC
│   ├── http.py               # 路由器/打印机/音箱/带 REST 的设备
│   ├── rtsp.py               # 摄像头（取帧需 ffmpeg）
│   ├── mqtt.py               # ESP32/智能家居（待物料）
│   └── ir.py                 # 红外（经手机发射，已有）
└── kinds/                    # 「是什么」——一类设备一个文件，声明它支持哪些 cap
    ├── android_phone.py  android_tv.py  windows_pc.py  linux_node.py
    ├── router.py  camera.py  printer.py  speaker.py  mcu.py
```

### 4.1 三条铁律（写进代码，不靠自觉）

1. **registry 是唯一真相**。任何能力必须在 registry 里有一条记录（name / title / params schema / side_effect / check_fn / 归属设备），否则上层看不见、调不到。
2. **不可用必须给原因**。`check_fn` 失败时返回 `unavailable + reason`（照抄 hermes 的 `unavailable_reason` 思路），不许静默消失。
3. **动手与只读分开**。`side_effect` 是注册表字段，不是调用方记得的事。只读自动过，动手过 `_gate`，破坏性双确认。

### 4.2 统一结果信封（所有 transport / kind / cap 共用）

```python
{
  "ok": bool, "cap": "input.tap", "device": "phone:k80",
  "data": {...},                 # 成功时的载荷
  "err": "桥不在线", "code": "unavailable",   # ok/unavailable/denied/timeout/error/unsupported
  "ms": 412, "side_effect": True, "via": "adb"
}
```

`code` 枚举是关键：有它，上层（规则/她/模型）才能决定「重试 / 换设备 / 叫人 / 算了」。现在我们的模块返回 `{"ok": False, "err": "..."}`，错误不可分类，规则引擎没法写。

### 4.3 能力命名空间（把现有函数收进规范名）

| 新名 | 现在的实现 | 副作用 |
|---|---|---|
| `shell.exec` | `node_agent` exec 白名单 | ✔ |

| `input.tap` / `input.type` / `input.key` | `phone_ops` | ✔ |
| `app.launch` | `android_device.launch` | ✔ |

## 五、设备种类扩展清单（按「手边能不能验证」排序）

实测这张网里有 **45 台主机**（`~/.fleet/nearby_hist.json`），其中 **20+ 台摄像头**、2 台路由（`.0.1` / `.0.16`）、PC、手机若干。端口实扫（本轮现场证据）：

```
192.168.0.1    [80]                         ← 路由/光猫 Web
192.168.0.16   [80]                         ← 路由
192.168.0.101  [23,80,554,8000,8080]        ← 摄像头：RTSP + telnet + Web + SDK 口
192.168.0.121  [80,443,554,8000,8443]       ← 摄像头（带 HTTPS）
192.168.0.130  [23,80,554,8000,8080,9999]
192.168.0.109  [554]                        ← 只有 RTSP
```

| 优先级 | 设备类 | 能力 | 真机验收判据 | 前置 |
|---|---|---|---|---|
| **P0** | Android 手机 | 已有全部 | 已有 | — |
| **P0** | Windows 本机 | 已有 | 已有 | — |
| **P0** | **摄像头**（数量最多，20+） | `camera.frame`（取一帧存证）、`camera.info`（ONVIF/RTSP 元数据） | 对**确认本人所有**的一台，取到一帧 PNG，记 md5+分辨率+耗时 | 需 ffmpeg（本机没有，约 80MB） |
| **P0** | **路由器**（.0.1 / .0.16） | `router.info`（型号/固件）、`router.clients`（在线客户端表） | 拿到客户端列表，与 `sweep` 的结果对得上 | Web 登录（凭据不落盘，走环境变量/交互） |
| **P0** | **WOL 唤醒** | `power.wake` | 把一台已关机的机器唤醒并 ping 通 | 目标机 MAC（我们已有全表） |
| **P1** | 电视 / 盒子 | `cast.start`（DLNA）、`input.key`（ADB） | 电视上真的出现画面/换台 | 同网 + 开 ADB 或 DLNA |
| **P1** | 打印机 | `printer.info`、`printer.job` | 打出测试页 | IPP 端口通（本网暂无） |
| **P1** | 音箱 | `media.play`（DLNA/AirPlay） | 出声 | 本网暂无 |
| **P2** | 旧手机当固定节点 | `sensor.read` 常开（光线/加速度/电量） | 连续 24h 在线率 >95% | 一台旧机 + 充电器 |
| **P2** | ESP32 / 单片机 | `mqtt.*`、`gpio.*` | 一个继电器真的通断 | 需采购（约 30 元） |

**顺序理由**：摄像头和路由器是这张网里数量最多、且现在**完全不在我们手里**的两类——它们代表「不是我们装系统的设备如何进来」，这是设备层真正的考题。电视/打印机/音箱是「有标准协议的家电」。ESP32 是「自己造一台设备」。四类都跑通，才叫「扩展」。

## 六、五道红灯（写在计划里，也写进代码）

1. **归属确认**：那 20+ 台摄像头、2 台路由，**如果不是你的设备，一律只做端口探测，不发任何带凭据的请求、不取任何画面**。未经授权访问他人摄像头在国内是刑事级别的（非法侵入计算机信息系统 / 侵犯公民个人信息），不是「技术探索」。→ 需要你逐台认领或给网段授权。
2. **凭据不落盘**：路由器/摄像头密码走环境变量或一次性交互，registry 里只存「有没有凭据」，不存凭据本身（沿用 `accounts.py` 的账本纪律）。
3. **动手过闸**：`side_effect=True` 一律过 `_gate`；跨设备编排（`orchestrator`）每一步单独过闸，不许批量放行。
4. **只读优先**：新设备类的第一个版本只读（看得到、拿得到），第二个版本才给动作。摄像头尤其——先能取帧，再说云台。
5. **隐私边界**：摄像头帧、PC 剪贴板内容、手机通知正文默认不进共享上下文（`memory` 的 ns 白名单外），要进必须显式。

## 七、分阶段（顺序锁死，一步一验收）

## 八、与整体长计划的合流（这是你问的「长计划」）

天网不是五个独立项目，是**一具身体 + 一个她 + 一张网 + 一颗脑**：

```
   ┌──────────── 脑：北极星 0.4B（tool-call 格式 SFT）────────────┐
   │         ▲ 训练语料                                    │ 调用
   │         │（D5 轨迹）                                   ▼
   ┌───── 神经：事件总线 + policies 规则 ▸ 编排 orchestrator ─────┐
   │         ▲ 感知/事件                          │ 动作          │
   ┌───── 身体：设备层（本轮 D0–D2）◂──────────────┘              │
   │  transport: tcp/adb/ssh/http/rtsp/mqtt/ir                   │
   │  kinds: 手机 电视 PC 路由 摄像头 打印机 音箱 MCU              │
   └──────────────┬─────────────────────────────────────────────┘
                  │ 全部走同一张注册表
   ┌──────────────▼─────────── 嘴：网关（手机/微信）──────────────┐
   ┌──────────────▼─────────── 记忆：TinyContext（逐条可删）──────┐
```

上面这张是「零件图」。**加上终端之后才是「能住人的房子」**——终端不是第五个零件，它是把四个零件同时显影的那面墙：

```
                        ┌──────────────────────────────┐
                        │  终端（T）：人在这里生活        │
                        │  · 一行命令调任意能力           │
                        │  · 她开口 / 事件流 / 编排进度    │
                        │  · 状态栏：她·手机·在线设备      │
                        └───▲──────────▲──────────▲────┘
                  显影注册表 │   订阅事件  │   订阅对话 │
        ┌──────────────────┴───┐  ┌───────┴──────┐  ┌┴─────────┐
        │ registry（身体+能力） │  │ 事件总线（神经）│  │她（人格） │
        └──────────────────────┘  └──────────────┘  └──────────┘
                            │
                    ┌───────▼────────┐
                    │ MCP / 网关出口  │  ← 机器与手机走这两个口，命令不重写
                    └────────────────┘
```

四层合流的判据（这才是「一个系统在动」，不是一堆命令）：

1. **一句话答得出身世**：「家里现在几台在线？哪台不正常？」——答不上来，设备层没成立。
2. **一个意图跨三台设备**：「我看电影的时候来电话，把电视静音、手机接听」——三步带依赖、失败回滚。这是 `orchestrator.py` 的本命。
3. **她主动开口有依据**：开口前先看 `pc.state`（你在不在座位上）、`state.read`（手机什么状态）、设备事件（谁刚掉线）。主动说话最容易犯的错是时机，不是内容。
4. **模型能自己调**：北极星 0.4B 输出的 tool-call 能被 registry 直接执行（先教格式，内容靠检索/TTT——沿用「模块只教格式」的一贯原则）。

**长计划的时间轴（不排日期，只排依赖）**：

```
D0 契约 → T0 终端 → T1 收敛 ┬→ D1 MCP ──→ D2 新设备类 → D3 事件闭环 → D4 家电扩展
                             └→ D5 轨迹回流 → 北极星 tool-call SFT → 脑接管部分调用
                                                                 ↘ 网关（嘴）：手机端入口
```

**为什么终端排在 MCP 前面**：MCP 是给「别的机器」用的口，终端是给「你自己」用的面。人先能用，机器再用；反过来的话，我们会先花一轮把接口做得漂亮，却依然只能靠 REPL 敲命令验证它——等于还是我在替你操作。

**其中唯一能「提前」的支线是网关（嘴）**：`memory.py` 里已有 `persona`/`recall`/`followups`，你手机上的 Telegram/微信才是「她」的真实入口。但它要等 D3 的事件流，否则只是个聊天框。

## 九、风险与坑（都是本轮已实测或已踩过的）

| 坑 | 证据 | 对策 |
|---|---|---|
| 编队桥被 MIUI 杀掉后**adb 拉不起来** | 进程消失 / 8765 无监听 / 无障碍开关被清空；`am start` 报 No activities found、`am start-foreground-service` 报 no service started（内存仅剩 800MB） | D4 必做：掉线事件 + 引导人手点一次；或改走 Shizuku/无线调试保活 |
| 明文 socket + 密码 | `commander.serve` 现状 | 只在 Tailscale / 公网 v6 内网用；D1 之前把 TLS 或 PSK 加上 |
| 公网 v6 入站未验证 | 探针已起 19099、防火墙已开，等手机流量连一次 | 待人工 30 秒 |
| 本机无 ffmpeg | `shutil.which('ffmpeg')` = None | D2 前下载静态包（约 80MB），或先用 RTSP DESCRIBE 只取元数据 |
| 手机无 SIM | `state.read` 实测 `gsm.sim.state` 空 | 定位/蜂窝类能力直接标 unavailable，不假装支持 |
| mDNS 无 responder | 组播能发能收，本网 0 个 responder | 设备发现别押 mDNS，押端口指纹 + OUI + ONVIF/SSDP 单播 |
| 44 个脚本在根目录 | `ls *.py` | D0 建包但不搬家，旧脚本留 shim，避免一次性大重构 |
