# 手机端能不能让模型自己用工具 —— 实测 + 开源调研 + 决策

日期：2026-10-24
设备：红米 25060RK16C（Android 16 / 天玑 9400 / 11.2GB）

## 结论前置（三句话）

1. **手机现在跑的是 0.6B**（北极星-V7-Q8_0，639MB），不是 4B。4B 在磁盘上但没起。
2. **工具不在模型手里**。现在联网是 PC 侧 `webtool.augment` 替它搜好、把正文拼进
   system prompt，模型只负责「读资料用自己的话说」。模型完全没有 function calling。
3. **不把 agent loop 搬到手机上**。4B 单轮能调工具（实测合法 `tool_calls`），
   但连续 5 轮就开始空转（140~172 秒不收敛）。这不是 bug，是 4B 的能力边界——
   BFCL 上 Qwen3-4B 多轮只有 22.12%。

## 一、实测：三个模型的真实边界

### 同一道资料理解题（给一份含 Android 17 / API 28 的正文，要求标 [编号]）

| 模型 | 输出 | 评价 |
|---|---|---|
| 0.6B 北极星-V7 | 「17.0.1，要求 28+…16.0.1 是 2025 年 6 月发布的…这数据跟时间线完全对不上，明显是被篡改了」 | **编了两个不存在的版本号**（17.0.1 / 16.0.1），还自造了一段推理 |
| 4B Qwen3VL | 「最新的安卓版本是 Android 17，于 2026 年 6 月发布，最低支持 API 级别提升到 28 [1]。」 | 一句话、标出处、零编造 |

0.6B 第二次跑又说「是 17.0，把 16.0 之后的都绕了。要不你给我挑一个 17.0 试试看」——
连 API 28 都丢了。

### 工具调用（给 web_search / open_page 两个 schema）

| 模型 | finish_reason | tool_calls |
|---|---|---|
| 0.6B（不加 --jinja） | stop | `null`，只说「先查价格，再看新闻」 |
| 0.6B（加 --jinja） | stop | `null`，行为不变 |
| 4B（加/不加 --jinja 都一样） | **tool_calls** | `web_search({"query":"今天比特币价格和相关新闻"})` |

**0.6B 加 `--jinja` 也救不回来**：北极星-V7 是微调/蒸馏版，本身没保留
function calling 能力。这是模型权重的问题，不是服务端配置。

### 4B 跑完整 agent loop（搜 → 挑页 → 点开 → 答）

第一版跑通，拿到了答案：

```
1. web_search("比特币当前价格和最近大事")       4.6s
2. open_page(binance)                          21.9s
3. open_page(okx)                              72.6s   ← 从 HTML 里抠到 $81,590.1
4. 收敛："比特币当前价格 $81,590.1。关于最近的大事，目前没有具体的信息"
                                          总 195.1s
```

行为是对的：它会换站、会承认「大事查不到」。但 195 秒——手机上没人等这个。

修完正文清洗后（拿不到裸 HTML 里的数字了），它连开 4 个交易所都失败，
5 轮不收敛，172.6 秒。**这就是小模型多轮工具调用的真实样子。**

## 二、开源调研：为什么是这个结果

### BFCL V4（Berkeley Function Calling Leaderboard，2026-04）

| 模型 | 单轮调用 | 多轮 | 不该调时正确不调 |
|---|---|---|---|
| Qwen3-8B | 87.58% | 41.75% | 79.07% |
| Qwen3-4B-Instruct-2507 | **87.88%** | **22.12%** | 84.93% |
| Qwen3-1.7B | 82.92% | 11.00% | 76.54% |
| Qwen3-0.6B | 65.9% | — | — |
| xLAM-2-3b-fc-r（专为 FC 微调） | 82.96% | **58.38%** | 63.45% |
| Llama-3.2-3B-Instruct | 82.67% | 4.00% | 52.06% |

**三条规律**：
1. 单轮调用，小模型基本都能做（4B 有 87.88%，不比 8B 差）。
2. **多轮会崩**——而 agent loop 恰恰是多轮。4B 从 88% 掉到 22%，这不是调参能补的。
3. 专为 function calling 微调的模型（xLAM-2 / Hammer / ToolGrad）多轮能保住 58%，
   代价是「不该调时乱调」的比例升高。

我们实测的 0.6B「tool_calls 永远是 null」对得上它的单轮 65.9%——而且北极星-V7
还比原版 Qwen3-0.6B 更差（微调掉了工具能力）。

### 配置层：`--jinja` 是硬性前提

llama-server 不加 `--jinja` 时不走 GGUF 内嵌的 chat template，退回**启发式解析器**。
那个解析器不认识模型自己的工具调用分隔符，于是 `tools` 字段被整个忽略、
工具调用被当普通文本吐出来。表现就是「模型明明会调工具，但 tool_calls 为 null」。

其他已知坑（社区共识）：
- **量化越狠，格式越容易坏**。Q3/Q2/IQ 出畸形 tool call，Q5_K_XL 以上明显更稳。
- **上下文太小会静默失败**：system prompt + 全部工具 schema 可能就有几千 token，
  窗口不够时尾部被截断——而工具的 schema 通常就在尾部，模型于是「真的没有工具」。
  表现和模板问题一模一样，很难分辨。
- **采样参数按模型作者推荐值**，别用默认。agent 场景 temp 一般落在 0.6 左右。

### 格式可靠性：GBNF 能保证什么、不能保证什么

`llama.cpp` 原生支持 GBNF 语法约束解码（`grammar` / `json_schema` / `response_format`），
原理是在采样前把「会破坏结构的 token」概率强制归零。它保证的是：

- ✅ 输出一定是合法 JSON / 合法 tool call 结构（**零结构失败**）
- ❌ **不保证选对工具**——模型可以完美地调一个不该调的工具
- ❌ 不保证参数值正确

有一份实测说得很直白：「量化损坏格式可靠性比损坏推理更快，这正是本地小模型需要它、
而托管大模型基本不需要它的原因。」

对我们当前场景（服务端预搜索，模型只读资料），GBNF 用处有限——
那个场景的问题不是格式，是 0.6B 会编内容。

### 框架层面：不需要上框架

2026 年的框架对比里，对我们的规模有用的几条：

| 方案 | 定位 | 对我们要不要 |
|---|---|---|
| LangGraph | 图状态机，条件分支/循环/持久化 | 不要。我们就是线性「搜→答」 |
| CrewAI | 多角色编排 | 不要。单模型单任务 |
| OpenAI Agents SDK | 类型化工具、handoff | 不要。绑 OpenAI |
| **MCP** | 工具暴露的传输层协议，schema-first | **可以看**。我们已有 `fleet/catalog.py` 109 项能力，形态本来就像 MCP |
| smolagents | 模型写 Python 代码当工具 | 不要。4B 写代码调工具更不可控 |

CSDN 那篇实测的说法很到位：「你只做 ChatBot + 少量工具，选 Function Calling，
不需要 MCP 那套重型架构。」我们现在就是 ChatBot + 联网工具。

## 三、决策

### 做（已做）

1. **`serve.sh` 加 `--jinja`** —— 标配。对支持的模型必需、对不支持的模型无害。
2. **修搜索标题爆长**（netforce 8a8fe04）——刷屏仓库把整篇长文塞进 repo description，
   一条 5.9 万字，5 条 31 万字，直接撑爆 4096 上下文（HTTP 400）。
   根因是合并时「取最长 title」：刷屏页的标题必然最长，于是必然胜出。
   修完同一 query：maxTitleLen 59321 → 36。
3. **修正文清洗漏 SVG** —— android.com 洗出 7616 字「正文」里基本全是 path data。
4. **`webtool.open_page()`** —— agent loop 的「打开这一页」入口，清洗规则复用一份。

### 不做

1. **手机端不上 agent loop。** 4B 多轮 22%、一轮 20 秒、5 轮 172 秒不收敛。
   投入产出比太差。
2. **不换 0.6B 去做工具调用。** 它的 tool_calls 永远为 null，加 --jinja 也没用。
3. **不引入 LangGraph/CrewAI。** 我们是线性链路，不需要图状态机。

### 待定（需要你拍板）

**要不要把手机默认模型从 0.6B 换成 4B？**

实测差异：

| | 0.6B 北极星-V7 | 4B Qwen3VL |
|---|---|---|
| 生成速度 | tg 51 t/s | tg 12 t/s |
| 内存 | ~0.7GB | ~2.6GB |
| 读联网资料 | 会编版本号、丢关键数字 | 标出处、零编造 |
| 工具调用 | 不支持 | 单轮支持 |
| 启动 | 2~3 秒 | 1~9 秒 |

11.2GB 内存**装不下两个同时跑**（实测两个都起时 4B 的 prefill 从 31.8 掉到 11 t/s，
内存用到 11.16G/11.28G）。所以只能按需切换。

我的建议：**联网问答用 4B，闲聊/设备控制用 0.6B**，`serve.sh` 传模型参数切换，
重启 2~9 秒可接受。理由：读资料回答是抗幻觉要求最高的场景，4B 明显更好；
而设备控制是对格式要求高、对内容要求低的场景，0.6B 够快。

## 四、留给下一次的坑（已验证，未修）

- **行情类页面抓 HTML 永远拿不到价格。** binance/coinbase 是脚本渲染，
  okx/coinglass 拿到的是导航文字。彻底修法不是改进清洗，是**加结构化数据通道**
  （公开行情 API），而不是指望模型从 HTML 抠数字。
- **工具输出必须自带预算。** 第一版 agent loop 一次搜索返回 31 万字，
  第二轮直接 HTTP 400（超出 4096 上下文）。现在强制 `search ≤1200 字 / open_page ≤1500 字`。
- **错误文案要说「怎么办」。** 只写「页面是脚本渲染」时，4B 又连开 binance/coinbase，
  白烧 60 秒。改成「换同类站也没用，要么换信息型站点，要么直接说拿不到」之后才止住。

## 更新（2026-10-24 凌晨）：Qwen3-1.7B 上机实测——当前最优解

Qwen3-1.7B-GGUF Q8_0（1.75GB，ModelScope 下载，sha256 与上游一致）已装入
`files/home/models/Qwen3-1.7B-Q8_0.gguf`。同一套四项探针，全部同口径：

| | 0.6B 北极星-V7 | **1.7B Qwen3（关思考）** | 4B Qwen3VL |
|---|---|---|---|
| 读联网资料答题 | 不引用、丢 API 28 | **3/3 全对、带 [1] 引用、热身 1.6s** | 对、标出处，但慢 |
| 原生 tool_calls | null | **合法（finish_reason=tool_calls）** | 合法 |
| 单轮决策（schema 约束） | 3/6 | **6/6，平均 1.9s** | 未测 |
| 内存 | ~0.7GB | ~1.9GB | ~2.6GB |
| 生成速度 | tg 51 t/s | tg ~25 t/s | tg 12 t/s |

**三个新知识：**

1. **Qwen3 系列必须处理思考开关。** 默认 `enable_thinking=true` 时，
   max_tokens 预算被 `<think>` 吃掉，`response_format` 的 JSON 是空的——
   不是模型不行，是预算没了。调用时带
   `chat_template_kwargs: {"enable_thinking": false}` 后：
   决策 1.9s、读资料 1.6s、零编造。深问题才值得开思考。

2. **「中间测出来变差」先怀疑自己的脚本。** 复测时一度全员编造"Android 14"，
   以为是 kv 缓存污染，重启清缓存后依然。最后发现是临时脚本的
   doc 提取切片写错，**喂给模型的资料是空字符串**——模型对着空资料
   只能拿训练先验硬答。重启后同题 3/3 全对。教训：A/B 测试先打印输入长度。

3. **Git Bash 会把以 `/` 开头的参数当本地路径改写**（MSYS path conversion）。
   `adb push /d/x.gguf /data/local/tmp/` 的远端路径被改写成
   `C:/Program Files/.../data/local/tmp/`，push 静默失败（文件永远不出现）。
   修法：`MSYS_NO_PATHCONV=1` + 本地路径写 `D:/...` 格式。
   另外 run-as 进程**丢附加组**，所以 Termux 身份读不了
   `/sdcard/Android/data/com.termux`（组 ext_data_rw 有权限但 run-as 不带组）；
   `/data/local/tmp`（shell 可写、文件 chmod 644 后 run-as 可读）是可靠的两跳通道。

**结论修订：** "默认模型怎么定"不用拍板了——**1.7B 全面占优**：
抗幻觉追平 4B，速度是 4B 的 2 倍，内存比 4B 少 0.7GB，还白送原生工具调用。
下一步把 serve.sh 默认模型切到 1.7B（待用户确认后执行）。
