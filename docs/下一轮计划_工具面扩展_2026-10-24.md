# 下一轮计划：把「搜索工具」扩成「手机工具面」（学 Operit）

2026-10-24。基于 Operit（github.com/AAswordman/Operit）调研 + 本机实测数据。

## 一、现状盘点：差在哪儿

**模型能用的工具，目前只有一个 `web_search`。** 而 PC 侧能力注册表已有 **109 项**，
其中手机侧独占的就有一批：截图识屏（`screen.read`）、应用列表/启动（`apps.list`/`app.launch`）、
通知（`notify.read`）、输入（`input.tap/type/key`）、Wi-Fi 扫频（`radio.wifi.survey`）、
蜂窝（`radio.cell`）、蓝牙（`bt.scan`）、热状态（`thermal.read`）、shell（`shell.exec`）、
文件传输（`file.push/pull`）、红外（`ir.send`）、语音（`voice.*`）、出图出视频（`image.gen`/`video.gen`）。

**问题不是能力少，是能力没接到模型手上。** 现在 109 项能力是「我（PC agent）手动调用」；
手机 App 里的 1.7B 助手，只会在 `web_search` / `none` 之间二选一。

## 二、Operit 值得抄的架构（已核实源码/文档）

1. **22 个内置工具类**（`core/tools/defaultTool/standard/`）：文件系统、shell/终端、
   Intent/广播、设备信息、UI 自动化（无障碍+Shizuku+Root 三通道）、浏览器会话、
   HTTP、FFmpeg、音乐播放、系统操作、软件设置、计算器、聊天管理、记忆查询、工作流。
   外加 ToolPkg 生态（examples/ 里 130+ 个 JS/TS 工具包：12306、浏览器自动化、
   各家绘图 API、SSH、Tasker、地图……）。
2. **工具协议不依赖模型训练**：`<tool name="x"><param name="k">v</param></tool>` XML
   写进 system prompt，客户端流式解析、`<tool_result>` 回填历史——任何模型都能跑。
   v1.9.1 起加了「严格工具调用」，v1.6.3 支持原生 tool call，两套并存。
3. **权限三档**：自动允许 / 每次询问 / 禁止，默认「询问」。这是它敢开放 shell/短信/UI 控制的前提。
4. **按任务分模型**：聊天、记忆、总结、UI 控制可以分别指定模型——和「小模型只做简单事」的思路一致。
5. **UI 自动化三板斧**：无障碍（免 root）、Shizuku（ADB 级）、Root；虚拟显示做无人值守操作。
6. **工作流引擎**：触发（手动/定时/Tasker/Intent/语音/应用启动）→ 节点编排 → 日志/统计/取消。
   ——这就是我们 `fleet/jobs.py` + automation 的同类物，可对标补齐。

## 三、下一轮计划（按阶段，每阶段有验收）

### P0：工具面接模型（核心，先做）

**目标：手机助手的决策 schema 从 `{tool: web_search|none}` 扩成多工具枚举，首批评 6 个。**

首批工具选择原则：**安全（无破坏性）、手机独有或明显更强、单轮就能出结果**。

| 工具 | 对应注册表能力 | 为什么先做 |
|---|---|---|
| `web_search` | webtool | 已有，保底 |
| `app_launch` | app.launch | 高频、无破坏、参数就是一个包名/别名 |
| `notify_read` | notify.read | 「谁给我发消息了」类问题的唯一解 |
| `screenshot_describe` | screen.read + 看图 | 手机独有；链路已验证（imgscale 缩略） |
| `device_status` | thermal.read + state.read | 已实测好用（体温/电量/降频） |
| `wifi_survey` | radio.wifi.survey | 手机独有；已是注册能力 |

**实现要点：**
- 决策 schema 用枚举 + 各工具独立参数 schema，仍走 `response_format: json_schema`
  （0.6B 实测：枚举是它唯一守得住的约束形式）。
- **先验证再铺开**：拿 1.7B 跑「多工具枚举决策」探针（≥10 用例），确认 6/6 不是
  二选一巧合。若决策准确率 <80%，退回「两级决策」（先选类别再选工具）。
- 关键词/参数同样由 schema 约束；服务端执行沿用能力注册表，执行结果回填到下一轮 prompt。
- 不做 function calling 多轮 agent loop（BFCL + 本机实测：1.7B 多轮必崩）；
  保持「单轮决策 + 服务端执行 + 结果回填再答」的两段式。

### P1：多轮循环（学 Operit 的骨架，加我们自己的缰绳）

- `<tool_result>` 回填 → 模型可以**再决策一次**，硬上限 2 轮、总预算 60s，超时强制作答。
- 每轮结果必须带预算截断（上次实测 31 万字撑爆 4096 的教训已修，参数层再防一次）。
- 「不该调时乱调」用规则兜底（0.6B 实测 76.5%；纯代码/算术/翻译类直接短路不进决策）。

### P2：权限三档 + shell 白名单

- 对齐 Operit：工具分 `自动 / 询问 / 禁止` 三档，App 设置页做成三个胶囊（已有胶囊组件）。
- `shell.exec` 不进首批；若进，走白名单（只读命令），并记审计日志。
- 短信/联系人/通讯录类能力**不开放**（隐私边界，不跟随 Operit 的激进面）。

### P3：定时与工作流

- `jobs.py` 已有租约/迁移；补「定时触发」入口（每日/每周），对齐 automation 的自然语言配法。
- 场景示例：早上 8 点「读一次通知 + 天气 + 电池，合成简报推给 App」。

## 四、风险与验收标准

- **验收**：门禁 64/64 保持全绿；新增决策探针脚本（`tmp/probe_decide.py`）入 tmp 归档；
  端到端实测至少 5 条真实问题走新工具并截图留档。
- **风险 1**：多工具枚举让 1.7B 决策掉点 → 预案是两级决策。
- **风险 2**：工具结果回填让上下文膨胀 → 每轮工具输出硬限 1200 字符（复用 webtool 经验）。
- **风险 3**：越权（模型请求执行破坏性操作）→ 首批只上只读/低危能力；执行层再校验一次，
  不信任模型输出的任何参数（正则/枚举双重检查）。

## 五、明确不做的

- 不做 ToolPkg/JS 沙箱生态（Operit 用 QuickJS，我们场景不需要）。
- 不做浏览器 Agent（App 内浏览器自动化）——手机上已有识屏点击闭环，重复建设。
- 不做多角色/记忆图谱（已有 memory_pack，够用）。

## 执行记录（同日凌晨·P0 已落地）

- **决策探针（PC 同款 1.7B）**：7 选 1 枚举 16/16 全对、平均 5.1s——两级决策预案不用启用。
- **新模块 `fleet/agent_tools.py`**：决策 schema + 规则短路（翻译/代码/算术/寒暄不进决策）
  + 6 工具执行器（渲染器按能力 data 字段取值，失败也返回文字不抛异常）
  + 结果硬限 1200 字符。自测 19 项全过。
- **relay 接线（server.py Relay.chat）**：web=on 强制搜索 / web=auto 走 7 选 1 决策 /
  web=off 全关；决策模型 = 手机 1.7B（`AT.DECIDER_URL`，可环境变量覆盖）；
  决策失败静默降级为无工具面，不拖垮对话。app.launch 走注册表 fail-closed 闸门，
  无审批时被拒——拒绝原因会如实转告用户。
- **端到端（PC 1.7B 扮演决策+生成）**：notify_read / device_status / 规则短路 /
  web_search 四条分支全 PASS；手机不在时工具报「adb 无设备」并如实转告，零编造。
- **App v34**（构建完成，待手机空闲后安装）：状态栏显示工具专属文案
  （「正在用手机工具 notify_read…」「已用手机工具 …」），联网文案不变。
- 门禁 64/64 全绿。
