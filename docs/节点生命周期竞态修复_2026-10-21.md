# 节点生命周期竞态修复（2026-10-21）

> 一句话：**临时节点断线重连时，「下机即清」这个核心承诺在最常见的场景下失效了**——
> 入网凭据 PSK 留在账本上，等于把那台机器的钥匙挂在门上。

---

## 一、结论先行

| 项 | 内容 |
|---|---|
| **表面症状** | `commander.py --self-test` 偶发红：`凭据余 1 / 排队余 0 / 令牌余 1`（应全 0） |
| **复现频率** | 修复前连跑 6 次红 1 次；全量门禁并行跑时更容易红，单跑常常是绿的 |
| **真因** | 四个缺陷叠加，**根子在最底层那个**（客户端 socket 超时） |
| **性质** | **不只是测试不稳定**——是一个真实的安全缺陷 |
| **修复后** | 自检连跑 **10/10 全绿**；全量门禁 50/50 |

## 二、四个缺陷与它们的关系

```
【根因·缺陷4】客户端 socket 建连超时(10s) < 心跳间隔(15s)
        ↓  socket.timeout 留在 socket 上，每 10 秒必抛
        ↓  ⇒ **每个节点必然每 ~13 秒断开重连一次**（与网络状况无关）
        ↓
【缺陷1】重连是「同名」REGISTER，服务端注册表被覆盖
        ↓  旧连接的 finally 按 sock 找自己 → 找不到 → nm=None
        ↓  ⇒ 整个 _drop_node → session_end 策略 → _session_cleanup 被跳过
        ↓
【后果】临时节点「下机即清」失效：PSK / 卸载令牌 / 离线队列全残留
        ↓  别人拿那台机器还能认证进来
        ↓
【缺陷2】就算改成「按名字 pop」来修缺陷1
        ↓  ⇒ 会把活得好好的**新连接**一起摘掉 → 幽灵节点（心跳判死/路由全错）
        ↓
【缺陷3】自检用固定 sleep 等节点上线
        ↓  机器一慢就打出假阴性（实测见过「上线: False（session 模式已上报）」）
```

**为什么之前没发现**：缺陷 4 让「同名重连」从罕见情况变成**常态**，
而缺陷 3 的固定 sleep 又让自检在快机器上「看起来是好的」。
只有在全量门禁并行跑（机器忙）时，缺陷 3 的假阴性与缺陷 1 的清理跳过才会同时暴露。

## 三、逐个说清

### 缺陷 4：建连超时留在 socket 上（根因）

`node_agent._session` 原来这么写：

```python
s = socket.create_connection((host, port), timeout=10)
```

**`create_connection` 的 `timeout` 会留在 socket 上**——它是 socket 的默认超时，
不是「只作用于建连」。于是之后每次 `recv` 超过 10 秒没数据就抛 `socket.timeout`。

而心跳是 **15 秒**一次（`time.sleep(15)` 后发 HEARTBEAT）。
**10 < 15 ⇒ 必然周期性断开。**

实测证据（探针，真实 socket）：

```
RESULT: socket.timeout 在 10.0s 触发
```

节点日志里能直接看到 `PC-Net` 注册了两次、`Her-Phone` 注册了两次——
不是网络抖动，是**必然**。

**修法（双保险，缺一道就复发）**：
1. 建连超时提到 **30 秒**（> 心跳间隔）——即使后面的 `settimeout(None)` 被删也不周期性重连；
2. 建连后立刻 `s.settimeout(None)` 回到阻塞模式——读超时交给心跳/看门狗判断，不靠 socket 报。

> 教训：**「建连超时」与「读超时」是两回事**。前者该有，后者不该有。
> 它们的耦合是隐形的，症状出现在几秒后的重连上，离病根十万八千里。

### 缺陷 1：清理被整段跳过（安全缺陷）

`commander._handle_node` 的 finally 原来这么找自己的节点名：

```python
nm = REGISTRY.with_lock(lambda d: next((k for k, v in d.items() if v["sock"] is conn), None))
if nm:
    _drop_node(nm)
```

而注册是**同名覆盖**：`d.__setitem__(name, {...})`。

同名重连后，旧连接断开时注册表里那名字的 `sock` 已经是**新连接**的了
⇒ `v["sock"] is conn` 匹配不上 ⇒ `nm = None` ⇒ **整段清理被跳过**。

探针实测输出（真复现，非推测）：

```
[gen1] finally: 找到自己=None (REG 里 sock 的 gen=2)
[gen1] => 清理被跳过（注册表已被新连接覆盖）
```

失败日志里 `[+] 节点上线: PC-Net` 出现两次，坐实同名覆盖。

**为什么这是安全缺陷**：`_session_cleanup` 负责「临时节点（网吧/借用设备）下机即清」——
撤销入网凭据 PSK、作废卸载令牌、丢弃离线队列命令。
这个项目的核心承诺之一是「那台机器的钥匙不能留在门上」。
而**临时节点断线重连是最常见的场景**，恰恰在这个场景下清理失效。

**修法：连接世代号（generation）**。

- 每次注册发一个递增号 `gen`；
- 连接断开时，`_drop_node(name, expect_gen=我的gen)` **只摘「指定世代」的那一条**；
- 世代对不上 ⇒ 已经换代了 ⇒ 什么都不做。

这样两条语义就分开了：

| 场景 | 世代对得上吗 | 该做什么 |
|---|---|---|
| **真下机**（最后一个连接断了） | 对得上 | 清理（PSK/令牌/队列全清） |
| **同名重连**（旧连接断了，新连接接管了） | 对不上 | **什么都不做**（节点还在线） |

### 缺陷 2：`_drop_node` 误杀新连接

原来 `d.pop(name, None)` 不校验身份。**如果按名字 pop 来修缺陷 1，会把活得好好的新连接一起摘掉**，
新连接从此变成幽灵节点（心跳判死、路由全错）。

修法：弹出动作在**同一把锁内**完成「校验世代 + 移除」，不多一次检查少一次竞态。

### 缺陷 3：固定 sleep 造成假阴性

自检原来这么等节点上线：

```python
node_agent.run_node(..., "PC-Net", ...)
time.sleep(0.9)
print(f"  上线: {bool(REGISTRY.with_lock(lambda d: d.get('PC-Net')))}（session 模式已上报）")
```

机器一慢（门禁并行跑、磁盘慢），0.9 秒不够注册完成 ⇒ 这行打印出「上线: False」——
**假阴性**。我在失败日志里亲眼看到这句自相矛盾的话。

修法：新增 `_wait_online(name, timeout=10.0, poll=0.05)`，轮询等条件成立，
到点没成立就带明确原因报错（「XX 在 10 秒内没有上线」）。

> 教训：**等待不够久会稳定失败；等到了就是等到了。**
> 「固定 sleep 到点就断言」是门禁误红的常见来源。

## 三又二分之一、缺陷 5：并发串味（这才是「偶发红」的真根因）

**这一节是后来才挖到的，比前面四条都底层。**

修完上面四条后，自检单跑 20/20 全绿，但**全量门禁里 commander 仍偶发红**。
第一次我以为是「机器忙、等待不够久」——**这个判断是错的**。

理由：**等待不够久会稳定在超时点失败；偶发红意味着条件本身可能永不成立。**

于是构造并发场景复现：

```bash
for i in 1 2 3 4; do (commander.py --self-test &) ; done
```

复现成功：**四个并发实例，第二个起就报「PC-Ghost 在 10 秒内没有上线」。**

### 根因链

1. 自检用**固定端口 9000**；
2. `netpath.listen` 在所有平台都设了 `SO_REUSEADDR`；
3. **Windows 上 `SO_REUSEADDR` 的语义和 Linux 不同**：允许第二个进程绑上**同一端口**，
   且新 socket **抢走**后来者的连接（实测：第二个 `bind` 成功，且 `SO_EXCLUSIVEADDRUSE` 才会报 10048）；
4. ⇒ 后启动实例的 `node_agent` 连上的是**先启动那个实例的 server**，
   `PC-Ghost` 注册进了**别人的注册表**；
5. ⇒ 自己进程里 `REGISTRY` 永远没有 `PC-Ghost` ⇒ `_wait_online` 永远等不到
   ⇒ **条件永不成立**（不是等得不够久）。

第二个固定端口也在这条链上：bootstrap 分发服务用 9100 ⇒ 并发时报 `10048`。

### 修法（两层，缺一不可）

**① 底层语义修正：`netpath.listen` 在 Windows 上改用 `SO_EXCLUSIVEADDRUSE`。**

端口重复是调用方的错，让它**响**（明确报 10048），绝不静默抢连接。
Linux 上保留 `SO_REUSEADDR`（那边语义是「允许 TIME_WAIT 复用」，没问题）。

**② 上层隔离：自检一律用 port=0（系统随机分配）。**

- `commander.self_test`：`netpath.listen(host, 0)` → `getsockname()` 取真实端口 → 用它起节点；
- `bootstrap.start_server`：`port=0` → 从 `httpd.server_address[1]` 取真实端口；
- `commander.serve` 新增可选参数 `sock`，支持外部传入已绑好的套接字。

### 验收

| 项 | 修复前 | 修复后 |
|---|---|---|
| 4 路并发自检 | 1 绿 3 红 | **4/4 全绿** |
| 6 路并发自检 | — | **6/6 全绿** |
| 单跑 20 次 | 20/20 绿 | 20/20 绿 |
| 全量门禁 | 49/50（偶发红） | **50/50** |

### 教训

> **「偶发红」几乎不会是「等待不够久」。** 等不够久是稳定失败。
> 偶发红 = 条件可能永不成立 ⇒ 必须**构造出那个竞态单独复现**，
> 而不是加长超时、加长 sleep、把断言放宽。
>
> 这次的复现手法就是**并发跑多份**——把偶发条件变成必现条件。

## 四、语义澄清：重连的临时节点算不算「下机」？

**不算。** 它还在线。

- 重连时 `node_agent` 用的是**全局密码**认证（`password` 参数），不是用 PSK；
- 所以重连本身不代表「它又该有一枚 PSK」；
- 清理只在**该名字的所有连接都没了**（真下机）时发生。

这条语义现在被门禁正面钉死（见下）。

---

## 五、顺带加的能力：干净下机

原来的 `node_agent` 只有 `stop_all()`（全局停），且**没有按名字停的能力**。
这导致「临时节点下机即清」这条语义**没法验证**——测试想模拟「拔线」，
客户端 3 秒后就重连并同名接管，于是测的其实是「重连」而不是「下机」。

新增：

- `node_agent.stop_node(name)` —— 只停指定节点（**全局停机会误伤 PC-A/Box 等后续阶段要用的节点**，
  实测「统一意图编排」阶段会报 probe 失败）；
- `node_agent.stop_all()` —— 停全部；
- `node_agent.reset_stop()` —— 复位。

## 六、门禁：`evals/t11_node_lifecycle.py`（15 项，完全离线）

不开真端口、不发真密码、不启动真节点。覆盖：

1. 同名重连：旧世代的收尾**不摘**新世代的节点；
2. 同名重连：旧世代的收尾**不触发** session 清理（节点还在线，凭据/令牌各留 1）；
3. 真下机：当前世代的收尾**触发**清理（PSK/令牌/队列全清）；
4. 清理不可重放（重复清理安静返回 None）；
5. `_drop_node` 不带 `expect_gen` 时仍按名摘（向后兼容，心跳判死路径用）；
6. 世代号严格递增且唯一；
7. **客户端建连后必须 `settimeout(None)`**（AST 检查，不是脆弱的字符串窗口）；
8. **建连超时必须 >= 心跳间隔**（源头约束，防「只删掉 settimeout 就复发」）；
9. 自检等待上线用轮询而非固定 sleep；
10. `_wait_online` 等不到返回 False 而不抛异常；
11. `node_agent` 有按名字停机的手段；
12. `stop_node` 只停指定的节点，不影响别的；
13. **自检用随机端口**（AST 检查 `port=0` + `getsockname`）；
14. **Windows 上 SO_REUSEADDR 只能在非 Windows 分支**（AST 定位分支归属）；
15. **两个监听套接字在 Windows 上不能绑同一端口**（行为断言：真的去撞一次 10048）。

> 第 15 条是**行为断言**不是看代码——它真的去 bind 一次，
> 确认第二个监听会被拒。这是唯一能证明语义真的变了的断言。

**手法说明（第一次写这个测试时踩过）**：**不许篡改真实注册表里的 sock**——
那个 socket 还被服务端的 `_handle_node` 线程持有，替换它会让那个线程永远读不到东西、
finally 又因世代不匹配而不下线 ⇒ 节点条目永久残留 ⇒ 污染后面所有阶段。
正确做法：用**隔离的名字**直接验证 `_drop_node` 的世代语义（真代码真行为）。

## 八、已知限制

- **「下机即清」仍依赖服务端能感知到连接断开。** 拔网线 / 机器休眠 / 交换机清 MAC 表这类
  硬断线，服务端可能要等心跳超时（90s 探测、180s 判死）才认。
  这条路径走的是 `_drop_node_silent`（心跳判死用），**它不触发 session 清理**——
  也就是说硬断线的临时节点，其 PSK 要等心跳判死后才会被清。这是**已知缺口**，未修。
- 世代号是**进程内**的。控制面重启后计数从头开始，但注册表也重建了，不冲突。
- `node_agent` 停止后**不会**主动通知服务端「我要下了」（靠关 socket 让服务端感知）。
  服务端感知有延迟（见上）。
