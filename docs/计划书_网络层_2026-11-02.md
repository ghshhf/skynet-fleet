## 一、一句话结论

**网络层的「上层建筑」已经建完了（42 个能力、4611 行核心、12 道门禁），但「地基」一处都没通：本机没有全球 IPv6、墙外没有一台中继、天网三个常驻服务一个没起。**

所以现在不该继续加能力。该做的是**把已有的 42 个能力从「能跑」推到「真在用」**——按投入产出排，优先修三件事：**自己是谁（地址选取）→ 有没有人能连进来（服务在线）→ 墙外有没有人（中继部署）**。

## 三、必须攻克的五个点（按「投入 < 产出」排序）

### 🔴 攻克点 #1：入口层把链路本地地址当成对外地址（真 bug，零成本修）

**实测证据**：`rdv.self` 返回
```
self_id:  sf-f27c010af6f4a58f
current:  169.254.83.107          ← Tailscale 的 link-local，外部永远不可达
candidates[0]: 169.254.83.107     ← 排在第一位
candidates[2]: 192.168.0.103      ← 真正的对外地址，排第三
```

`169.254.0.0/16` 是 RFC 3927 链路本地地址，只在单一网段内有效，任何跨网段/跨 NAT 的连接都不可能到达它。把它当 `current` 上报，等于**主动告诉对端一个死地址**。

**为什么这是第一优先**：整套入口层（10 个 `rdv.*` + 12 个 `tun.*`）都建在"当前地址"这个变量上。地基变量错了，上面 22 个能力全在算错的数。而且修复是纯本地逻辑 + 可门禁，**零外部依赖，今晚就能落**。

**验收**：`rdv.self` 的 `current` 永不为 `169.254.*` / `fe80::*`；门禁锁死该不变量。

---

### 🔴 攻克点 #2：墙外零中继 —— 22 个能力全是空转（最致命）

**实测证据**：`rdv.auto` 从未跑过一个周期（`runs:0`、`status:never`）。门禁 `t58_rdv_auto.py` 里开头就 `pop("FLEET_WSRELAY")`——**说明这套门禁从来只在"没有中继"的状态下测过，全是 mock**。

已有的弹药：
- `tools/cloudnode/wsrelay.py` —— 把 TCP 塞进 WebSocket，让免费 PaaS 当代理出口（README 里明写：onrender / koyeb / netlify 等 10 个部署域名没被点名）
- `tools/cloudnode/cloudnode_up.py` —— 一键拉起「订阅 → mihomo → 本地网关 → 热点设备可用」
- `tools/cloudnode/entry_guard.py` / `entry_probe.py` —— 入口守卫与墙外探针

**缺的只有一样**：**一台真实墙外机器 + 一次真部署**。

**判断**：这是整个网络层"从演示到可用"的唯一瓶颈。tun/rdv 的能力再优雅，没有墙外对端就永远 `unverified`。

**验收**：`rdv.auto.status` 从 `never` 走到 `linked`（即"报上去了 + 墙外确实连得进来"），至少一个完整周期。

---

### 🟡 攻克点 #3：天网服务零在线 —— 最后一公里（成本最低、收益最高）

**实测证据**：本机对外监听只有 `8091`（IP Helper）。三个常驻服务 **8765 commander / 8787 zen-gate / 8899 r4_fileserver 全都没起**。热点网段 `192.168.137.x` 上**一个端口都没在监听**——就算手机连上热点，也没有东西可以连。

**为什么排第三但仍然紧急**：成本几乎为零（起服务 + 绑 `0.0.0.0`），收益是"手机能不能用"这个最直接的体感问题。但它**依赖攻克点 #2 才有意义**（没有中继，服务在线也只在局域网内可用）——所以顺序上排在 #2 之后、但可与 #1 并行。

**验收**：三服务常驻并监听 `0.0.0.0`；从热点网段地址能访问到。

---

### 🟡 攻克点 #4：IPv6 全球地址拿不到（外部条件，不该投入）

**实测证据**：`verdict: local-only`，只有 3 个 `fe80::`。诊断建议原文指向路由器：*"要问的是路由器，不是本机。"*

网关是 `192.168.0.16`（兼 DHCP），主 DNS 还配了个跨网段死项 `192.168.1.1:53`（实测拒连）。

**判断：这条路当前堵死，且不是代码能解的。** `c65c944` 提交里已经写明"换线即得"——意味着换一条有 v6 的宽带就有了。

**处理原则**：`tun.ipv6` 保持"建好待验"，**不投入开发时间，不因此等待**。主攻 v4 打洞 + WS 中继。等哪天换线/路由器开了 v6 前缀，`ipv6_diagnose` 一跑就知道，那时再验。

---

### 🟢 攻克点 #5：DNS 死项拖慢首包（小修，可选）

主 DNS = `192.168.1.1`（跨网段、实测拒连）+ `192.168.0.16`（网关，正常）。每次解析先撞死项超时再回落，**首包延迟被白吃**。

**处理**：把 `192.168.0.16` 提到主位，或直接删掉 `192.168.1.1`。属于网络配置而非代码，需要您点头才动。
