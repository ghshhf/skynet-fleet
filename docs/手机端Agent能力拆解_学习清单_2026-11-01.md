# 手机端 Agent 能力拆解 · 学习清单

> 写于 2026-11-01 23:00，依据：当日检索的上游项目 README / 官方博客 / 第三方横评。
> 一句话：**"AI 完整使用手机"不是模型问题，是权限通道 + 界面理解 + 执行回环三件事的工程问题。**
> 本文只回答一个问题：别人凭什么能自己操作手机，天网缺的是哪一块。

## 结论先行

1. **三条路，没有第四条**：Shizuku/ADB 特权、无障碍服务、VLM 视觉。现实里的项目全是三条路的组合拳，单走一条都有死角。
2. **能力上限由权限通道决定，不由模型决定。** 同一个模型，给了 Shizuku 就能装应用改系统，只给无障碍就只能点看得见的控件，什么都没有就只能读文件。
3. **决定成功率的是"界面表示"而不是"模型智商"。** 把 UI 树压成紧凑语义喂给模型（DroidRun 路线），比截图喂视觉模型（AppAgent 路线）在 AndroidWorld 上差一个数量级——这是当前最重要的一个工程结论。
4. **天网现在缺的不是模型，是通道。** 手机 App 已有 llama.cpp 本地推理 + 云端 API 双后端，但操作手机还得靠电脑侧 adb，手机自己什么都不能干。
5. **可学的最高性价比一条**：把手机本身做成 MCP Server（`rish-mcp` / `AndroidMCP` 的做法），天网控制面直接当 MCP 客户端 —— 不用改控制面架构，手机能力立刻进编队。

## 一、三条技术路线（机制层，必须吃透）

### 1.1 Shizuku / ADB 特权（uid 2000）

**原理**：Shizuku 通过一次无线调试授权拿到 ADB 权限，把 shell 身份（uid 2000）借给普通 App。App 于是能直接跑 `input tap`、`screencap`、`pm`、`am`、`uiautomator dump`。

- 优点：**免 root、能力最全、能跨 App、能装应用能改系统设置**。
- 缺点：首次要手动开无线调试；**设备重启后失效**（需带 autostart 的维护版治）。
- 天网对应物：已有 `ui_automation`，但走的是**电脑侧 adb**，不是手机自持。

### 1.2 AccessibilityService（无障碍服务）

**原理**：系统把界面变化事件推给服务；服务用 `getRootInActiveWindow()` 拿到 `AccessibilityNodeInfo` 视图树（文本、坐标、可点击、层级关系），再用 `GestureDescription` 执行点击/滑动/长按/输入。

- 优点：**不截屏、不烧 token、快、准、省**，且拿到的是结构化语义而非像素。
- 缺点：拿不到 WebView 内部 DOM；很多 App 开发者不写无障碍标签（按钮就叫 `Button1`）；部分自定义/Compose 视图语义树残缺。
- 需要用户手动授权（可检测：`AccessibilityManager.getEnabledAccessibilityServiceList`）。

### 1.3 VLM 视觉（截屏 → 模型 → 坐标）

**原理**：`MediaProjection` 或无障碍截图 → 喂视觉语言模型 → 模型返回点击坐标或动作。

- 优点：**最通用**，任何界面都能点，包括游戏、WebView、自绘控件。
- 缺点：慢、贵（每步一张图）、纯坐标点击易点偏、手机本地跑 VLM 速度基本不可用。
- 定位：**只能是兜底，不能是主路**。

### 1.4 三条小支线（少数项目在用，记着备用）

| 支线 | 代表 | 门槛 | 说明 |
|---|---|---|---|
| 系统级 API / Intent / AIDL | 小米 miclaw | 必须系统签名、绑自家设备 | 稳定不被封，但只在自家生态成立 |
| INJECT_EVENTS 注入 | 需 root 或系统签名 | 高 | 比 adb 更底层，应用层更难检测 |
| LSPosed / Xposed 进程内注入 | AndroidMCP | 需 root + 框架 | 能反射目标 App 内部方法、读私有字段、抓原始 View/Compose 语义树 |

## 二、比路线更重要的五个工程结论

### 2.1 结构化表示 > 像素

DroidRun 的公开数据：AndroidWorld 成功率 **91.4%**、单任务成本 **$0.075**、平均 **78 秒**；同基准下 AppAgent 约 **7%**、Mobile-Agent 约 **30%**（第三方横评口径，非官方基准，样本与配置未公开，仅作数量级参考）。

差距来源不是模型，是**输入形态**：它把 UI 树压成紧凑语义表示（谁可点、文本是什么、层级在哪），token 少、决策快；视觉路线每步送整张图，信息密度高但效率低。

⇒ **天网的 `ui_automation` 已经在正确的路上**（拉节点树 + textRegex 抗漂移），这条不要换。

### 2.2 感知分流：先树后图

现实项目全这么干：能读树就读树，读不到（WebView / 游戏 / 自绘）才截图走视觉。切分点应该是**一次树读取失败**，不是"看起来复杂"。

### 2.3 权限降级要显式，不许重试

DeepSeek Harness 安卓版的做法值得抄：Shizuku 与无障碍是**互补通道**，两条都没授权时**降级到文件读写/预览编辑**（只需"所有文件访问"），并**明确不再反复尝试系统操作**。反面教材是每步都试一次然后超时。

### 2.4 抗漂移三件套

- **语义定位**（textRegex / 描述匹配）优先于坐标；
- **执行后校验**（等目标控件出现/消失，不是固定 sleep）；
- **失败重规划**（UI-TARS 的自我纠错、Mobile-Agent-v3 的反思层）。

天网前两条早已有（`textRegex` 抗文案漂移），第三条 **2026-11-07 已接**：`Replan.kt` 把失败回包分类并给确定的换路建议，权限 / 锁屏 / 重复动作硬止损（见 §四、§七）。

### 2.5 保活与不抢前台

手机 Agent 跑长任务必然遇到：息屏、Doze、厂商杀后台、前台被抢。
需要：前台服务 + WakeLock + 电池优化白名单 + 开机自启。更激进的是 **Ruto-GLM 的虚拟屏/多窗口**——在虚拟显示里跑 App，agent 干活不占用用户当前界面。这一条天网完全没有。

补充两个引擎层参照（不是 App，但决定上限）：

- **LiteRT-LM**（Google）：原生 function calling（`ToolSet`/`@Tool` 注解）、**constrained decoding 强制 JSON schema**、Thinking Mode + KV 状态复用、Android/iOS/WebGPU 三端。官方数据：FunctionGemma **270M** 参数在 Pixel 7 Pro 上 prefill 1916 tok/s、decode 142 tok/s。
- **ExecuTorch**（Meta）：QNN delegate 走骁龙 NPU 最快（1B INT4 约 18–25 tok/s），但**读不了 GGUF**，要桌面预导出 `.pte`，NPU 产物按 SoC 绑定 —— 与"任意模型即插即用"冲突。

### 3.1 手机跑模型：运行时横评（2026-11-07 复核）

> 背景：手机端本地推理一直卡在「没有 `libfleet_llama.so`」——仓库里没有 llama.cpp 源码、
> 也没有 NDK，`build-llama.sh` 又写死了某台 Windows 机器的盘符。所以先回答一个问题：
> **是换引擎，还是把现有引擎的构建修好？**

| 方案 | 模型格式 | Android 接入 | 约束解码 / 工具调用 | 许可 | 结论 |
|---|---|---|---|---|---|
| **llama.cpp**（上游 tag `v0.9.0`，2026-11-04） | GGUF | 需 NDK 自编；本仓库已有 JNI + KV 前缀复用 | **GBNF**（采样层屏蔽非法 token）；无原生 function calling | MIT | **主路**：格式生态最广、现有代码全在这条线上 |
| **MediaPipe LLM Inference**（`com.google.mediapipe:tasks-genai` **0.10.35**，Google Maven 2026-04-27） | `.task`（LiteRT） | 官方 AAR，**不需要 NDK** | 无 GBNF；靠提示词 | Apache-2.0 | 备选：只有「坚决不装 NDK」时才值得换，模型要先转格式 |
| **ONNX Runtime GenAI**（`onnxruntime-android` **1.31.1**，Maven Central 2026-10-26） | ONNX | AAR，不需要 NDK | 有采样约束能力，但生态围绕 ONNX | MIT | 不选：与 GGUF 存量模型不兼容 |
| **MLC-LLM** | 每个模型单独编译 | TVM 产物，每模型一个 `.so` | 弱 | Apache-2.0 | 不选：「任意 GGUF 即插即用」直接不成立 |
| **ExecuTorch** | `.pte` | 桌面预导出，NPU 产物绑 SoC | 弱 | BSD | 不选：同上，且换机要重导 |
| **MNN**（阿里） | MNN | 自研引擎，CPU prefill 快 | 有 | Apache-2.0 | 若要换/加引擎，这是第一候选（多模态齐全） |

**结论：不换引擎。** 真正的瓶颈不是 tok/s，而是两件事：

1. **构建不可复现** —— 已改 `build-llama.sh`：NDK/cmake/ninja 全部探测，缺源码时按
   `LLAMA_REF`（默认 `v0.9.0`）浅克隆到 `third_party/llama.cpp`，编前校验上游 API
   与 `llama_jni.cpp` 匹配，产物落 `app/src/main/jniLibs/`。Windows / Linux / macOS
   同一份脚本。
2. **小模型守不住工具调用格式** —— 已接 **GBNF 约束解码**：JNI 每轮重建采样链
   （penalties → grammar → top_k → top_p → temp → dist），`LocalToolProtocol.toolGrammar()`
   把工具名穷举进文法；**只在「想调工具但 JSON 写坏」时重试一次**，正常聊天不加约束。
   这与 android-agent / llama.cpp server 的 json_schema 是同一套机制。

**顺带修正一个旧结论**：之前记「JitPack 不通 ⇒ 用不了 sherpa-onnx」是错的。
sherpa-onnx **v2.0.1** 在 GitHub Releases 直接发 AAR
（`sherpa-onnx-static-link-onnxruntime-2.0.1.aar`，37MB，内含
`jni/arm64-v8a/libsherpa-onnx-jni.so` 24MB，已实测可下载）。
所以离线 ASR 不需要 JitPack：把 AAR 放 `app/libs/` 用 `implementation(files(...))` 即可。

## 四、天网现状 vs 缺口（对着代码看）

已具备（`tianwang_app/.../next/`）：

- `Model.kt`：`ModelBackend` 接口 + `LocalBackend`/`CloudBackend` 双实现，`backendFor()` 单点分支（架构正确，别动）
- `LlamaNative.kt`：JNI 直通 llama.cpp，KV 前缀复用、abort、GPU 探测、`GenStats` 实测限速
- `Dev.plan()`：按实测设备推 ctx/线程/GPU 层数，不写死任何一台手机的值

明确缺口：

| 缺口 | 现状 | 学谁 | 动作 |
|---|---|---|---|
| 本地模型没有真 tool calling | 工具结果"折成文字"塞进上下文 | android-agent 的 grammar 约束；LiteRT-LM 的 constrained decoding | 已接 GBNF（2026-11-07）：`toolGrammar()` 穷举工具名，解析失败才重试一次；仍无原生 function calling |
| 手机不能操作自己 | 只能靠电脑侧 adb | Angel / rish-mcp / AndroidMCP | App 内加 Shizuku 通道（首选）+ 无障碍（次选） |
| 手机能力没进编队 | 控制面只能下发 adb 命令 | rish-mcp | 手机端起 MCP Server，天网控制面当客户端 |
| 无视觉兜底 | 无 | DroidRun 分流 | 树读取失败才截图，且截图走云端 VLM（本地跑不动） |
| 无失败重规划 | 规则匹配不到就报错 | UI-TARS / Mobile-Agent-v3 | 已接 `Replan.kt`（2026-11-07）：回包分类 → 下一步换路建议；权限 / 锁屏 / 同动作重复失败 / 累计三步硬止损；停手带回已完成步骤 |
| 两台手机不能同时借算力 | `self.peer.call` 顺序换机，一次只跑一台 | DroidRun 并行多机 | 已接 `PeerPool.kt`（2026-11-07）：本机 + 对端 + 电脑/API 同时跑，`race` 取先回 / `all` 并排列出；`pc=true` 且已配对时电脑算力同波参与，`api=deepseek,zhipu` 可钉死云端端点；第一波全失败或本机上下文/显存不够时升级到名册其余手机；只问不写 |
| 无长任务保活 | 无 | Ruto-GLM 虚拟屏 | 前台服务 + WakeLock + 电量白名单；远期用 VirtualDisplay |
| 无端侧界面理解模型 | 无 | AutoGLM-Phone-9B / UI-TARS | 可选：7-8B 量化到 Q4 跑本地，专用于"这是什么界面" |

## 五、"完整使用手机"还差哪些非点击能力

"完整"二字真正卡人的地方，往往不是点击，而是这些旁路通道：

- **通知监听**（`NotificationListenerService`）—— 读完即走的场景全靠它
- **剪贴板** 读写
- **悬浮窗**（`SYSTEM_ALERT_WINDOW`）+ 前台服务常驻
- **全文件访问**（`MANAGE_EXTERNAL_STORAGE`）
- **通话/短信/联系人**（需运行时权限 + 平台合规）
- **相机/麦克风**（视觉兜底与语音入口）
- **电池与散热**：持续推理会降频，长任务要测"十分钟后还剩多少 tok/s"，不是只测峰值
- **息屏运行**：Doze 白名单，否则长任务一息屏就断

## 六、边界与风险（只写有触发条件、有动作的）

1. **平台风控**：无障碍 + 事件注入可能被 App 判为外挂（豆包手机助手被多个超级 App 围堵是实例）。触发条件：高频 + 特定强风控 App。动作：限速、加随机延迟、单 App 操作频率设上限。
2. **Shizuku 重启失效**：触发条件 = 设备重启。动作：用带 autostart 的维护版，或在 App 内检测 `Shizuku.pingBinder()` 失败时引导重开。
3. **WebView / 自绘界面读不到树**：这是结构性缺陷，不是 bug。动作：必须有视觉兜底，否则该类界面直接判"不支持"。
4. **本地跑 VLM 不可用**：手机本地视觉模型速度退化到不可交互。动作：视觉一律走云端，本地只做文本与结构化判断。
5. **合规红线不变**：天网既有闸门（禁区=群/频道/真人/自己/未知）在手机端同样生效，Shizuku 拿到的是**更高权限**，闸门不能因为"能力变强"而放宽。

## 七、建议的推进顺序（三步，每步独立可验）

1. **第一步 · 通道**：手机 App 内接 Shizuku，先把 `input tap` / `screencap` / `uiautomator dump` 三条打通，与现有 `ui_automation` 的能力对齐（同样的规则匹配，只是执行端从电脑搬到手机）。验收 = 不连电脑也能点开一个指定 App 并读出界面文本。

## 九、2026-11-07 开源路线核查：不 root / 不解锁能到哪一层

| 路线 | 代表项目 | 拿到什么 | 结论 |
|---|---|---|---|
| ADB / shell 共享 | Shizuku、Shizuku+（fork） | shell（uid 2000）：pm / am / dumpsys、截屏、注入输入 | 已接；一次性无线调试配对，重启后看 Shizuku 的 autostart |
| 设备所有者共享 | Dhizuku、OwnDroid | DPM：静默授权 / 卸载、系统限制、重启 | 已接（本 App 自建所有者）；必须无账号时 provision，撤销要恢复出厂 |
| 端侧 ADB 客户端 | LibADB Android（MuntashirAkon） | 手机自己发起无线调试配对，可连另一台手机 | 一机控一机的最短路径；配对与密钥管理复杂，下一步再做 |
| 屏幕镜像控制 | scrcpy / ws-scrcpy、droidVNC-NG | 把另一台的屏幕投过来并注入点击 | 适合准实时操控，带宽高，不解决权限 |
| 张量级算力共享 | llama.cpp RPC、Petals | 按层 / 按张量把推理拆到多机 | 手机不划算：二进制必须严格一致、调度端仍要整模型、实测可能慢数倍 |
| 任务级算力共享 | 本仓 MCP 出站 WebSocket | 一台派任务、另一台执行并回结果 | 推荐：跨机型 / 跨版本兼容，断线可重连 |

结论：

- 「假 root」在无解锁、无 root 前提下就是 **Shizuku（shell）+ 设备所有者（DPM）** 两层，已都在 `tianwang_app` 里，权限矩阵会把两层分开报。
- 手机之间先不要做张量级：llama.cpp RPC 要求同版本二进制，调度端仍要放得下整模型，收益不稳定；先把任务级调度走通（局域网发现 + 直连 + 鉴权）。
- 一机控另一机的最短路径不是 scrcpy，而是「A 手机用 LibADB 连 B 手机无线调试」；scrcpy 只解决画面，不解决权限。

### 9.1 手机直连先走 IPv6，不先绕中继

- 同 Wi-Fi：mDNS 发现后直接连 `fe80::...%wlan0`，一跳；链路本地地址必须带 `%网卡`，否则内核不知道走哪张网卡。
- 跨网络：两端都有全局 IPv6 才可能直连；中继只做地址交换，不搬正文。
- 速度预期：Wi-Fi 6 手机之间 TCP 有效载荷几百 Mbps 是正常的（受 AP、频宽、发热、对端存储影响），不要按云中继的体感设上限。
- 工程细节：`TCP_NODELAY`；64KB 读写缓冲；测速走独立二进制段，不套 Base64/JSON；首帧口令鉴权，口令不进 mDNS TXT。
- 已落工具：`self.lan.status/start/stop/call/speed`；`self.lan.call` 直接调对端 MCP 工具。
- 真机验收顺序：B 机 `self.lan.start` → B 机 `self.lan.status` → A 机 `self.lan.speed` → A 机 `self.lan.call`。
- 失败排查：AP 开了客户端隔离时 mDNS 和直连都会失败；换手机热点或手动填地址再试。

### 9.2 动态 IPv6：对端记名字，本机发布地址

手机拿到的全局 IPv6 是自动分配的，也必然会变：换 Wi-Fi、换运营商、租约到期、隐私地址轮换都会换一个。**把 IP 写死在对端配置里一定会过期**。正确的抽象只有一层：

1. 本机把「当前全局 IPv6」发布到一个稳定域名（DDNS）；
2. 对端只记域名，连接前解析 AAAA，拿到的是当下地址；
3. 地址变了就重新发布，对端无感。

已落：

- `self.ddns.config provider=duckdns domain=<子域> token=<密钥>`：DuckDNS 官方更新接口；
- `self.ddns.config provider=custom url=https://.../{ipv6}?token={token}`：自建更新接口；
- `self.ddns.publish`：立刻发布一次；
- `self.ddns.watch enabled=true`：网络变化 / 全局 IPv6 变化自动发布，另有 10 分钟兜底（隐私地址会轮换）；
- `self.ddns.status`：配置、当前全局 IPv6、上次回执（密钥不回显）；
- `self.dns.resolve name=<域名>`：解析并按「全局 v6 > ULA > 私网 v4 > 公网 v4」排序；
- `self.lan.call host=<域名>`：直接连域名，内部按上面的顺序逐个地址尝试，坏地址不会拖死整次调用。

边界必须说清：

- DDNS 只解决「找得到」，**不解决「进得来」**。运营商/路由器拦入站时仍然走中继，不假装直连成功。
- 全局 IPv6 可能不止一个，其中可能有临时隐私地址；发布的是当前首选地址，轮换后靠自动发布追上。
- DNS 有 TTL 缓存，换地址后对端可能几十秒到几分钟才看到新值；重连逻辑要允许这一段空窗。
- 密钥只存本机 SharedPreferences，status / 审计都不回显；更新接口优先 HTTPS。

真机验收顺序：B 机 `self.ddns.config` → `self.ddns.publish` → 在 A 机 `self.dns.resolve` 看是否解析到 B 的新地址 → A 机 `self.lan.call host=<名字>`。

### 9.3 手机集群：任务级共享，不是张量级

手机之间做张量级推理共享（llama.cpp RPC / Petals 那类）在手机上不划算：二进制要严格一致、协调端仍要放整模型、跨机型常常慢数倍。真正能落地的是**任务级**：

1. 每台手机是一个完整的工具执行节点（自己的权限、自己的模型、自己的界面）；
2. A 只把「这一单」派给最合适的一台，拿到结果就结束；
3. 对端不可用时换一台，但**只对只读操作换机**。

已落：

- `self.peer.add name=<短名> host=<地址或域名> port=<端口> token=<对端口令>`：名册落本机；口令只露头尾；
- `self.peer.list`：电量、充电、亮屏、能力数、最近错误；同时列出 mDNS 发现但未入册的机器；
- `self.peer.probe`：逐台握手，拿 hello 自述（机型 / Android / 工具表 / 电量 / 充电）；
- `self.peer.pick tool=<工具>`：按「充电中 > 电量高 > 最近见到」排序，只按对端有没有这个工具过滤；
- `self.peer.call tool=<工具> args=<JSON>`：按选路结果逐台尝试，回包告诉你「由谁完成、第几个候选」。

两条硬规则（代码里写死，不是提示词）：

- **权限只有一档**：控制方（发起派单的这台）的「允许操作」决定写操作能不能派；执行方只判断自己有没有这个工具，有就接，不再单独设只读开关。LAN 口令就是授权凭证；
- 写操作只派一台：回包丢了不代表没执行，换机重试就是重复点击 / 重复发送。

边界：

- 口令即授权：拿到某台的口令就能调用它全部工具。要收回，`self.lan.start rotate=true` 换口令（已入册的对端要重新填）。
- 每台手机的口令不同，必须逐台入册；名册含口令，只存本机 SharedPreferences。
- 队友离线时 `peer.call` 会给出每台的失败原因，不会假装成功。
- 这是「多机接力」，不是「一台手机算力变强」；跨网络仍受运营商入站策略约束。

真机验收顺序：A 机 `self.peer.add` → `self.peer.list` → `self.peer.probe` → `self.peer.pick tool=self_ui_tap` → `self.peer.call tool=self_status`（只读）→ 再试写操作。

### 9.4 整单目标：控制方只说「做什么」

到这一步，集群的链路才完整：

1. **解析**：`peer.probe` 知道谁在线、谁有哪个工具、谁在充电；
2. **连接**：IPv6 / DDNS 名字直连，不经过中继；
3. **操控**：把一句自然语言目标交给对端，对端用自己的本地模型选工具、执行；
4. **解析结果**：控制方只收最终答复，不关心中间点了哪几下。

已落：

- `self.agent.goal goal=<一句话>`：本机本地模型跑完整单，自己选工具、执行、回最终答复；
- `self.peer.goal goal=<一句话>`：自动选一台最合适的手机，把整单派过去，只回结果；
- `self.peer.call tool=self_agent_goal`：手动指定某台执行整单目标。

三条硬边界（代码写死）：

- **独占模型**：同一台手机同时只跑一个目标，第二个直接拒绝，不排队、不并发把内存打爆；
- **不许递归**：本地模型看不到 `self_agent_goal` / `self_peer_goal` / `self_peer_call`，避免 A→B→A 循环；
- **不许切断回包通道**：看不到 `self_lan_start` / `self_lan_stop` / `self_owner_reboot`。目标把 LAN 停了或把手机重启了，控制方永远等不到回包。

默认超时 5 分钟（上限 10 分钟）；写操作仍然只派一台、失败不换机。

使用：

```text
A 机：
self.peer.goal goal=打开设置，把屏幕亮度调到一半，然后回报当前亮度

B 机：
不需要额外配置；只要有 GGUF 模型和对应工具，就自己跑完回结果
```

边界：目标能不能跑成取决于对端本地模型的能力；这边不做“流式转播”，只回最终答复；对端锁屏/休眠/模型没下载时会明确报错。

真机验收顺序：B 机先 `self.agent.goal goal=看看当前电量` → A 机 `self.peer.goal goal=打开设置并回报当前界面标题` → 再试带写操作的目标。
