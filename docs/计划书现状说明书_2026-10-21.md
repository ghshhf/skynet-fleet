## 四、🔴 下一部分计划书是什么：**X1「专家·技能·连接器」三 Tab**

### 4.1 为什么它是下一段

- X0 是它的**前置**（导航项「专家技能·连接器」本身就是 6 个死链之一，X0 要先把它接上）；
- 它是**整个产品形态的核心**：WorkBuddy 那套「左栏导航 + 专家/技能/连接器三 Tab + 卡片墙」
  是我们要学的骨架，而本仓**缺的不是像素，是「能力/设备/连接器」这套信息架构的显影**；
- 货已经齐了：70 项能力、9 台设备，**只缺把它们摆出来的货架**。

### 4.2 X1 产出规格（已定）

| Tab | 内容 | 数据来源（必须真） | 硬约束 |
|---|---|---|---|
| **技能** | 70 项能力按**能力族**分卡（`pcctl.`14 / `adb.`14 / `host.`8 / `web.`7 / `ai.`4 …） | `/api/caps` | 零硬编码；每卡含能力名、中文说明、`registry.owners()`、副作用档（auto/ask） |
| **连接器** | 9 台设备卡片墙 | `/api/devices` | 每卡必须带**「为什么不能用」**一栏；不可用设备不许显示成正常 |
| **专家** | **能力组合包** = 能力子集 + 人设引用 | `catalog.py` 子集 + `cards/*.json` | 界面上叫「专家」，文档里写清 = 能力子集 + 人设引用（与 WorkBuddy 的「人格专家」同名不同义） |

### 4.3 X1 验收标准（可测）

1. 三 Tab 切换**不重载页面**（纯前端视图切换，零 HTTP 往返，**响应 < 100ms**）；
2. 技能卡数量 = 70（`/api/caps` 的 count），少一张门禁红；
3. 连接器卡探活状态与 `/api/devices` 的 `ok` **逐个一致**，不一致门禁红；
4. 搜框输入 `adb` → 只剩 `adb.` 族 + 名字含 adb 的卡；
5. 一次渲染 ≤ 80 张卡，超了分页，**不许静默截断**。

### 4.4 🔴 语义红线（X1 最容易犯的错）

WorkBuddy 的「连接器 `+`」= **接入外部服务**（QQ邮箱/腾讯文档/企业微信）；
本仓的 `+` = **把设备纳入编队**。
⇒ **只抄图标不抄语义 = 禁止**（否则做出来的是假按钮）。

### 5.3 问题三：**门禁项数在各文档里对不上**

实跑当前是 **52/52**，但文档里散着 47 / 48 / 49 / 50 / 51 / 52 / 「t12 20 项」/「t13 57 断言」等数字。
⇒ **文档里的数字是快照，会过期。** 需要一个「门禁清单自动生成」机制（或每次改门禁后统一回填）。

### 5.4 问题四：**阶段粒度不统一**

- W 线：W0–W7（8 段，每段对应一个可验收的界面能力）
- X 线：X0–X6（7 段，偏产品形态）
- D 线：D0–D5（6 段，偏设备种类）
- 无限智能体：A/B/C（3 段，偏机制）
⇒ 四套编号混在一张路线图上，**同一条线上的不同粒度**。W 线与 X 线的边界（W3 与 X0 都动图形版）**没写清**。

### 5.5 问题五：**验收口径在各书里不统一**

有的段说「真机点一遍、渲染图对比」，有的说「门禁红绿」，有的说「跑一遍看输出」。
⇒ 缺一条统一规则：**每段的验收必须是「可复算的数字」**（门禁项数 / 差异百分比 / 死链数 / 探活数），
而不是「看起来对」。

### 5.6 问题六：**文档没有「状态回填」机制**

各书都有「已落地进度」表，但都是手填 ⇒ 必然过期（见 5.3）。
⇒ 建议：进度表由脚本从 `git log` + 门禁输出生成。

### 5.7 问题七：**设备层扩展计划书的 7 条待确认，3 条是「要买什么 / 哪些是你的」**

（摄像头 20+ 台是谁的、路由器买不买、要不要装 prompt_toolkit/rich）
⇒ 这类**只有用户能答**，且**卡着 D2 整条线**。
