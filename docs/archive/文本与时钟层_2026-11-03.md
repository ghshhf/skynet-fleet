# 文本与时钟基础层（2026-11-03）

> 本文记录天网在 Windows 上反复踩的两类坑，以及为什么最后是自己写一层，而不是直接引一个库。

## 一、为什么会有这一层

翻自己的历史，这两类问题出现的形态几乎一模一样，每次都在事发地点局部修一次：

| 症状 | 真因 | 当时的修法 |
|---|---|---|
| 接力器永不触发 | `tasklist` 是 GBK，`text=True` 解错，异常在后台线程，`stdout` 变 None | 在那一处加 `except` |
| 防火墙检测恒返回 None | `netsh` 同上 | 换了个调用方式 |
| 「训练链起不来」 | `run_chain.bat` 第 14 行注释混了中文，cmd 按 GBK 读整行当命令执行 | 改成全 ASCII |
| 中文报错变乱码 + 行号对不上 | 无 BOM 的 `.ps1`，PowerShell 5.1 按 cp936 解 | 加 BOM |
| 合成出来是静音 | curl 在 GBK 终端传中文，服务端收到乱码 | 改用 Python urllib |
| 传「电路板」返回「处理器」 | curl 用 GBK 发中文，服务端按 UTF-8 解析失败**静默回退默认值** | 在 `_body()` 加三级容错 |

最直接的证据是：**同一个 workaround 被独立写过四遍**，编码尝试顺序有三套不同写法。

```python
netaccel._safe_run : ("utf-8", "gbk", "cp936")
tunnel             : ("gbk", "utf-8", "cp1252")     ← 顺序反了
gw_up._run_text    : (locale, "utf-8", "gbk")
netdiag            : utf-8 → gbk(replace)           ← 只两级
```

`tunnel` 那份是**真 bug**：GBK 的合法区间极宽（首 0x81-0xFE / 次 0x40-0xFE），
任何 UTF-8 中文都能被它「假成功」解出来，所以 `utf-8` 分支永远走不到，
在英文系统上照样乱码。

## 二、实测出来的两个硬事实

全部在本机（Windows 10 + Python 3.12.10）实测，不是查来的。

### 1. 三个时钟，两个常用名字都是错的

| 函数 | 底层 | 分辨率 | 单调 |
|---|---|---|---|
| `time.time()` | `GetSystemTimeAsFileTime()` | 15.625 ms | ✘ |
| `time.monotonic()` | `GetTickCount64()` | 15.625 ms | ✔ |
| `time.perf_counter()` | `QueryPerformanceCounter()` | 100 ns | ✔ |

测同一段约 11 ms 的计算，各跑五次：

```
time          11.02  11.99  11.99  11.02  11.98    ← 精度够，但会被校时改
monotonic     16.00  15.00   0.00  16.00  15.00    ← 测出了 0 ms
perf_counter  11.70  11.69  11.68  11.75  11.83    ← 正确
```

`monotonic` 出现 0 是因为两次读数落在同一个 15.6 ms 时钟节拍里。
**凡是「用 monotonic 量毫秒」的代码，量快操作时都会得到一堆 0 或 15.6 的整数倍。**

顺带解释一个别人的误判：某重试库的作者在 Windows 上看到 `sleep(0.05)` 只睡了 47 ms，
以为是「早醒」，于是把 `Retry-After` 改成 `X * 1.05 + 50ms` 去补偿。
50 ms 在 15.625 ms 网格上就是 46.875 ≈ 47 —— 他补的是一个**测量误差**，不是真实的早醒。

### 2. 默认编码取决于「从哪个终端启动」

```
Git Bash 里：locale.getpreferredencoding(False) == "utf-8"
cmd / 双击 ：同一句返回 "cp936"
```

同一份代码，两种结果。而 PEP 540 的 `PYTHONUTF8` 只在**解释器启动前**生效，
运行期设 `os.environ` 改不了它。

更坏的是解错了不报错：

```
subprocess.run([py, "-c", "写 GBK 中文"], capture_output=True, text=True)
→ returncode = 0
  stdout     = None      ← 不是 ""，是 None
  stderr     = ""
```

解码在 `subprocess` 的后台 `_readerthread` 里做，异常炸在那个线程，**主线程收不到**。
调用方 `r.stdout.strip()` 抛 AttributeError，或者更常见的是
`if "关键字" in (r.stdout or "")` 静默走 false 分支。

## 三、开源项目调研结果（不是没找）

| 项目 | 结论 | 理由 |
|---|---|---|
| `charset-normalizer`（MIT，806★，本机已装） | **用**，但只做兜底 | 统计法在中文 GBK/UTF-8 之间不如确定性规则链稳；只在规则链全失败时调用。没装就跳过 |
| `ftfy`（rspeer，4k★） | **没引** | 本机未装；GitHub 识别许可证为 NOASSERTION。mojibake 修复按它公开的算法思路重写（cp1252 往返 + 五个未定义字节直取） |
| hermes-agent 的修法（Popen 注入 `encoding="utf-8"`） | **没采用** | 它只是把 cp936 的问题换成另一个方向的问题：强制 utf-8 之后，`netsh`/`tasklist` 这些真·GBK 输出照样乱 |
| `agent-deadline`（纯 monotonic Deadline） | 只借鉴 `intersect()` 思路 | 它用 `time.monotonic()`，在 Windows 上就是 15.6 ms 精度，亚秒级超时会不准 |
| `nopanic`（重试/熔断组合库） | 只借鉴纪律 | 「Retry-After 要留余量」这条对；但它对 Windows sleep 的解释是测量误差 |

**共同的盲区**：所有现成方案都假设「用 monotonic 就对了」，没有一家注意到
Windows 上 monotonic 只有 15.6 ms。所以这一层只能自己写。

## 四、做了什么

### `fleet/text.py`

判定链（顺序不能反，理由写在每条注释里）：

```
1. BOM            → 说了算
2. 纯 ASCII       → ascii
3. 零字节分布     → utf-16（只覆盖 ASCII 为主的 UTF-16）
4. 严格 UTF-8     → utf-8
5. 候选评分       → gb18030 / utf-16 按「解出来像不像话」选
6. charset-normalizer 兜底（装了才用）
7. utf-8 + replace（永不抛）
```

第 5 步的评分权重是从误判里改出来的：最初只按「CJK 越多越好」打分，结果
`tasklist` 的 GBK 输出被 utf-16 解成一堆韩文汉字，CJK 密度反而更高，评分压过正确答案。
现在**结构字符（空格/换行/`=`/`:`）权重最高**，韩文和私用区倒扣。

对外接口：

| 函数 | 用途 |
|---|---|
| `sniff(raw)` | 判编码，返回 encoding / method / confident |
| `decode(raw)` | bytes → str，永不抛 |
| `read(path)` / `write(path, s, bom=)` | 读写，写走 `store` 原子写 |
| `run(cmd, ...)` | **`subprocess.run` 的替身**：收 bytes 自己解，stdout/stderr 永不为 None |
| `fix_mojibake(s)` | 修双重编码，只在「明显变好」时采纳 |
| `check_script(path)` | `.bat`/`.ps1` 编码与行尾合规检查 |
| `safe_filename` / `long_path` / `normalize_newline` / `strip_ansi` | Windows 杂项 |

### `fleet/clock.py`

| 函数 | 说明 |
|---|---|
| `now()` | 唯一的计时读数（perf_counter） |
| `wall()` | 墙上时间，**只用于记录时刻，禁止参与判断** |
| `Deadline(seconds)` | 预算，`.left()` 恒 ≥ 0，不受校时影响 |
| `Stopwatch` / `timed(sink)` | 测耗时，支持分阶段 lap |
| `sleep` / `sleep_until` | 分片睡，被打断能续剩余 |
| `fmt_dur` | **小于 1 ms 显示微秒，绝不显示 `0.0ms`** |

## 五、接线范围

- `subprocess` 裸 `text=True`：**32 处 → 0 处**（AST 扫描 263 个 .py 确认）
- 四处各写一遍的 workaround → 统一走 `text.run` / `text.decode`
- 时钟层已建好，调用点迁移是独立一步（见下）

### 明确没做的

`time.time()` 算时间差在全仓还有约 190 处（其中 33 处直接关系超时控制流）。
这一轮**只建层、不批量迁移**——机械替换控制流代码的风险远大于收益，
且时钟层已经有门禁守着，新代码可以用对。迁移按模块分批，每批单独跑门禁。

## 六、门禁 `evals/t75_text_clock.py`

77 项断言，A/B/C 三段：

- **A 能力对**：判定链、`run()` 语义（含「原生 text=True 给 None」的对照组）、
  mojibake 修得回来且不乱修、Deadline 单调、脚本合规
- **B 接线**：AST 扫全仓，**不许再出现裸 `text=True`**（grep 会被多行参数骗过去，必须用 AST）
- **C 回归**：留证据证明「gbk 排在 utf-8 前面」确实会把 UTF-8 解错

## 七、已知限制（如实记）

1. **无 BOM 的纯中文 UTF-16 判不准**。中文 UTF-16 一个零字节都没有，
   而 gb18030 能对它「假成功」。现在的做法是靠评分复核，多数能救回来，
   但样本极短时仍可能判错，此时 `confident=False`。已知编码请直接传 `encoding=`。
2. **日文 Shift-JIS / 俄文 cp1251 等**不在规则链覆盖内，靠 `charset-normalizer` 兜底。
3. `time.sleep(0.001)` 在 Windows 上实际要 1.92 ms，这是系统时钟节拍，本层不假装能修。
4. 时钟层尚未覆盖全仓 190 处墙钟差值，见「五」。
