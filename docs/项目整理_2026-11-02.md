## 一、一句话结论

**8 天里能力表从 121 涨到 404（3.3 倍），但真实可用的增长远小于这个数——因为 404 里 89 个是纯声明空壳、263 个没有门禁碰过。**

规模已经够大，现在的问题不是"还能接多少"，而是**账实不符**：能力表在膨胀，可验证的部分没跟上。下一步该做的是「把账算清」，不是继续往上堆。

## 五、门禁健康度：账没坏，游离已清零

| 项 | 数值（脚本生成，见自动块） |
|---|---|
| `evals/` 文件数 | 见 `_stats.json` 的 `eval_files` |
| `run_selftests.py` 登记条数 | 见 `gates_registered` |
| 游离未登记 | **0**（2026-11-02 晚清账，见下） |
| 抽样实跑 | t62 + t60 + t61 + t55_download → **4/4 PASS，13 秒** |

**两个游离门禁的真相**（比「写了不跑」更值得记）：
`t50_voice_synth.py` 和 `t59_pinhole.py` 不是忘了登记，是**坏了所以没人愿意登记**。
t50 里 `pc_melo` 变量根本没定义，跑到最后一步必抛 `NameError`；
同时它的引擎循环遍历全部引擎去拼 sherpa 参数，而 `indextts2` 是 proot 类引擎、
进去必抛错——脚本自己的注释（"它不能进上面那个循环"）写了，代码却没照做。
**于是它恒红 → 谁都不登记 → 更没人跑 → 一直红。** 这是个死循环，不是疏忽。

修法：定义 `pc_melo`、循环按 `kind` 分流、环境缺模型时 `skip` 而不是 `FAIL`。
修完全绿，登记为 `eval_t50_voice_synth`；t59 因编号被 `eval_t59_groups` 占着，
登记为 `eval_t59b_pinhole`。

**判断：门禁这台机器是健康的、快的（13 秒跑完四个域），问题在"没被写的 255 个能力"。**

## 八、下一步：三个候选

### 候选 A · 账实相符（推荐，1 小时）

1. 补登 2 个游离门禁（t50 / t59）
2. 给 `fleet.catalog` 加一个 `available()` 方法：按设备返回"声明数 / 有实现数 / 依赖在场数"
3. 对外报的数字从"404 个能力"改成"404 声明 / 315 有实现 / N 个此刻真能用"

**理由**：现在所有决策（包括记忆里的数字）都建立在虚高口径上。先把账算清，后面每一步才不会踩空。这也符合「行动经济」——先止损，再进攻。

> **落地情况**：①②③ 用另一种更硬的方式做了——不加新方法，而是让
> `tools/gen_stats.py` 直接读真注册表出四层数（`declared` / `owned` / `gated` / `live`），
> 并写进文档自动块。理由：新加一个 `available()` 只是又一套口径，
> 而「脚本按真注册表算 + 门禁比对」才是断掉漂移的那一刀。

### 候选 B · 统一图景（半天）

README + 总纲 + 实际代码三方对齐，出一份"天网现在是什么"的单一事实源。
**理由**：文档停更 8 天，能力涨了 3.3 倍，新读者（包括未来的我）会被 README 带偏到老架构上。

> **落地情况**：✅ 已做，见 §十。核心不是"把数字改成 404"，是**让数字以后不可能再漂**。

### 候选 C · 继续内化（新域）

在 `lla` / `video` / `email` / `card` 这些薄域里挑一个吸收外部实现。
**理由**：内化这条线已经被验证有效（四个域走通）。但**在账没算清之前继续堆，只会让虚高更严重**。

## 九、我的判断

**先 A 再 B，一周内不碰 C。**

理由：A 的成本是 1 小时、收益是"所有后续决策的数字都准"；B 的成本是半天、收益是"不再有两套说法"。这两件做完，C 才有可靠的起点——否则下个域内化完，能力表变成 450，而真实可用的可能还是 200 出头。

## 十、统一图景（11-02 晚落地）

### 做了什么

**核心不是把 151 改成 404，是让「改写数字」这件事本身变得没必要。**

| # | 动作 | 落点 |
|---|---|---|
| 1 | 统计口径从 AST 计数改成真注册表 import | `tools/gen_stats.py`。旧口径数 `Capability(` 构造器出现次数得 **427**，真注册 **404**——差的 23 个是"写了构造器但没进清单"，数打字次数不是数能力 |
| 2 | 出四层可复现口径 | `declared` / `owned` / `gated` / `live`，每层都写明取值点，`live` 单独标采样时间 |
| 3 | 文档加自动块 | README 与总纲各一块 `<!--STATS:BEGIN-->…<!--STATS:END-->`，内容由 `--write-docs` 生成 |
| 4 | 正文禁写累加绝对值 | 把「能力表 X 加到 Y」这类写法全改成「本轮 +N」 |
| 5 | 建门禁 t63 | 自动块同步 / 无累加链 / 正文引用文件必须存在 / 游离门禁 0 / 四层不自相矛盾 |
| 6 | 修 t54 | 它本来就管「代码 → `_stats.json`」，跟着新字段改，并豁免易变字段 |
| 7 | 清账两个游离门禁 | 见 §五 |
| 8 | 重写总纲 §七 文档索引 | 原来写着「docs 从 76 → 3」，实际已经 7 份，且新加的都没登记 |

### 门禁分工（别重复造轮子）

```
改代码 ──→ tools/gen_stats.py ──→ docs/_stats.json ──→ 自动块（README / 总纲）
             ↑                        ↑                      ↑
             └──── t54 盯这一段 ───────┘      └── t63 盯这段 ┘
```

t54 管「代码 → JSON」，t63 管「JSON → 正文 + 正文引用的东西是否真在」。
一开始差点又写一个门禁去做 t54 已经做的事——**继承项目之前，先看项目里有没有**。

### 反面教材（为什么非要机制不可）

README 里原来有一条能力数累加链：`151 → 160 → 166 → … → 374 → 380 → 384`。
看着挺严谨，实测一 grep 就露馅：**`378 → 382` 排在 `380 → 384` 后面**。
两条支线各自往前加，链断了，断了两头都还标着「能力表」。
这不是谁不认真，是**手写的绝对值必然会被并行的工作流冲散**。
所以现在的规矩是：绝对值只许出现在自动块里，正文只许写「本轮 +N」。

### 还没做的

README 的**叙述部分**（第 15 行往后那几百行）仍然按时间倒序堆叠，是"8 天里每天都加了什么"的流水，
不是"天网现在是什么"的说明书。数字已经不会再漂了，但**要一眼看懂这个系统，
还得有一份按层（L0–L4）而不是按时间组织的总述**。这是下一步，不在本轮范围。
