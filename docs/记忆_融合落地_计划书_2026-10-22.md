# 记忆 · 融合落地计划书（借 MemFlywheel 的骨架，接我们自己的 L3）

> 2026-10-22　状态：**已实现并过门禁**（实现见 `memguard.py`，门禁见 `tools/mem_gate.py`）
> 一句话：**不新造存储，只给现有记忆加「证据闸 + 溯源 + 派生目录」。**

---

## 一、为什么不照搬

天网本来就有记忆，四件套都在：

| 已有 | 文件 | 职责 |
|---|---|---|
| L3 共享上下文 | `memory.py`（sqlite KV + FTS5，中文 LIKE 兜底） | 跨设备同一份记忆，逐条可删 |
| 对话流水 | `journal.py`（append-only，**自增 id**，打码，cap 环切） | 事件落盘，可当证据 |
| 往事唤醒 | `recall.py`（12–72h 窗口、去重、"只引用原文"） | 隔日能提具体事 |
| 未闭环 | `followups.py`（open topic 抽取） | 「上次那事还没完」 |

MemFlywheel 装不进来（只适配 Pi/Hermes/OpenCode/OpenClaw 四个 Node 宿主）。
但它的**骨架**我们确实缺两块：

| MemFlywheel 有 | 我们 | 后果 |
|---|---|---|
| 派生索引（200 行/25KB，先给目录再读正文） | 无，`recall` 直接塞原文 k=3 条 | 记忆一多就只能靠"多塞几条"硬顶 |
| 每条记忆挂 `## Sources` 指回轨迹行号 | 无，`ctx.put` 想写就写 | 编造/记错无从核验 |
| 「无证据只进 pending」 | 无 | 推测会混成事实 |
| dream 去重整理 | 无 | 重复条目只进不出 |

**总纲 Phase B 的验收③原话就是「引用必须是真的（对照 journal 原文，不许编）」——这本来就是我们的欠账，只是没人还。**

## 二、做法：一层闸 + 一张表 + 一个目录

### 2.1 证据闸 `remember()`

```python
mg.remember("her", "game_lastnight", "昨晚那局还没玩完，说到第3关", evidence=[12, 15])
```

- **有 `evidence`**：核验这些 journal id 真的存在 → 写入 L3 正式 ns，并记进 `evidence` 表
- **没 `evidence`**：**不拒绝、也不装正式**——落到 `pending` ns，`digest` 里单独一段标「待核」
- **编造的 id**（journal 里查不到）：直接报错。宁可写不进去，也不许拿假证据充数

### 2.2 溯源表 `evidence(ns, key, jids, verified, ts)`

同一张 sqlite 文件里新开一张表，不动 `memory.py` 的表结构。

`verify()` 回头核对：journal 里那条被 `purge()` 删了（E-7 用户的删除权），
对应记忆就标 `verified=0`，`digest` 里显示「证据已丢」——**记忆不会因为证据没了就消失，但会明确降级。**

### 2.3 派生目录 `digest()`

给对话注入的那段文本，格式对齐 MemFlywheel 的 `MEMORY.md`：

```
- 昨晚那局还没玩完，说到第3关（昨天｜her/game_lastnight｜证据 #12,#15）
- 待核：听说楼下在装修（今天｜pending/decoration｜无证据）
```

硬上限 **40 行 / 6000 字节**（比它的 200 行/25KB 更紧，因为这是**每轮**注入，不是一次性）。
超了按「离昨天近」截断并加标记。同一状态连续生成两次字节必须一致（幂等）。

排序沿用 `recall` 的「离昨天 26h 最近优先」——不另造一套时间观。

## 三、门禁（`tools/mem_gate.py`，10 项，实跑 10/10）

| # | 做什么 | 通过标准 |
|---|---|---|
| 1 | 无证据 remember | 落 `pending`，正式 ns 里查不到 |
| 2 | 有证据 remember | 正式写入，digest 行里带 `#id` |
| 3 | 编造 journal id | 抛错拒绝，L3 里不留痕 |
| 4 | 证据被 purge | `verify()` 标 unverified，digest 显示「证据已丢」 |
| 5 | 造 100 条 | digest 行数 ≤40 且字节 ≤6000（实测 41 行 / 3541 字节，末行是截断标记） |
| 6 | 连跑两次 | 两次 digest 完全一致（幂等） |
| 7 | 两条 val 完全相同 | `dupes()` 能找出来，且**不删** |
| 8 | 待核项 | 不进「往事候选」，但**留在目录**里（人要看得到） |
| 9 | 同 topic 三条流水 | 沉淀成 1 条记忆，证据 = 全部 3 个 id；无 topic 的不沉淀 |
| 10 | 抽取连跑两次 | 条数不涨、证据不变、目录一致 |

## 四、真实数据诊断（2026-10-22 实跑，只读副本）

拿仓库里真实的 `fleet_context.db` / `fleet_journal.db` 跑：

```
流水 journal：187 条事件（task 160 / user 19 / her 7 / see 1）
L3 kv      ：1 条，且是 her/last_thought（她自己的元状态，按设计不进目录）
带 topic 的事件：1 条
```

**两个结论，都不是"记忆层不够用"：**

1. **记忆层的缺口是「最后一跳」**：流水有 187 条，L3 里一条生活记忆都没有。
   `extract()` 补的就是这一跳，但它只能沉淀**有 topic** 的事件——所以真实数据只抽出 1 条。
2. **真正的瓶颈在写流水那一步**：160 条 `task` 事件**没有一条带 topic**。
   这直接解释了「未闭环跟进」为什么一直空转——`followups.extract()` 按 topic 找，
   没有 topic 就永远找不到。**该改的是记流水的地方，不是记忆模块。**

> 所以本次没去动真库：抽取规则的粒度值得先看一眼（`memguard.py --extract` 在副本上跑），
> 但上游补 topic 才是让整条链活过来的前提。

## 五、明确不做（避免范围膨胀）

- **不做向量检索**：总纲 §Phase B 写死了「先关键词 + 时间窗够用」。`memory.py` 已有 FTS5。
- **不做自动 dream**：`dupes()` 只**报**不**删**。合并/压缩要动到用户明确说过的原话，风险高于收益；
  等它跑出一段时间、看到真实重复率再谈自动化。
- **不碰 `recall.py` 的排序与窗口**：那套是照验收标准调过的，只加一条 `pending` 进 `SKIP_NS`。
- **不替代 `followups`**：未闭环是"事"，这里是"记忆"，两者不合并。

---

## 五、和 MemFlywheel 的三处刻意差异

1. **无证据不写正文，只写 pending**。它的子 Agent 可以自由 write；我们的提取必须先有 id。
2. **待核区永不自动转正**。要人（或下一轮带证据的写入）明确升，不靠模型自己觉得"想通了"。
3. **不自动删除/合并**。它靠 dream 自动压缩；我们只报告重复，删除权留给人（呼应 E-7 逐条可删）。
