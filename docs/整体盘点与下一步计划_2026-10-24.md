# 天网（device-fleet）整体盘点与下一步计划

日期：2026-10-24 05:10 · App build 45 · 门禁 67 项 · 设备 14/14 在线
写这份东西的起因：主人报「审批点不了、点基准测试就崩」。修完回头看全局，
发现这两个都不是孤立的 bug，而是同一个病灶的两个症状——
**能力铺得很开，但「最后一公里」没人守**。

---

## 一句话结论

**骨架建完、能力铺完（109 条），但真机闭环还没稳，且失败时普遍不说话。**

三层现状：
- **能力层**：109 条已登记（27 条需审批，82 条其余），注册表/闸门/结果信封这套骨架是完整的。
- **设备层**：14 台设备、14 台在线；手机（红米 25060RK16C）已是真算力节点。
- **闭环层**：聊天/出图/只读探测已通；**「让手机动手」这条链刚修完，但它依赖一条没人看管的隐形链路（adb reverse）**。

今天修的三个 bug 里，有两个的根因都不是「代码写错了」，而是
**「失败了但一句不说」**——这才是当前最大的系统性风险。

## 一、现在到底能干什么

分三档写。**只把真机验过 / 门禁钉住的算「能」**，代码里有但没验过的单独标出。

### A 档：真机验过，可以信

| 能力 | 证据 |
|---|---|
| 手机只读探测（22 个工具） | 昨天实测：17/17 只读工具真拿到数据——中国移动 n41 2524.95MHz、184 个应用、253 进程、42 台局域网设备、12 个 Wi-Fi；蓝牙关着如实回「不可用——ERR bt-off」，不谎报 0 个 |
| 模型工具决策（Qwen3-1.7B） | 决策准确率 27/28 = 96%；问「我用的哪家运营商」给出双卡真数据，并主动说「当前用哪张 dumpsys 没给，不敢猜」——**不编造** |
| 手机算力节点 | Termux llama-server 常驻，Qwen3-1.7B-Q8_0，冷起 4 秒就绪；同包第二问 TTFT 129~281ms |
| 手机本地出图 | sd.cpp + Vulkan，三档（快/标准/精细）、512/768/1024、串行队列、断点续跑；档案里存着实测 1792s/步 那条 |
| 电脑侧 109 条能力 | 注册表在跑，`pcctl.*`（截图/窗口/剪贴板/进程）、`host.*`（点/打字/滚）、`web.*`（12 项）、`card.*`、`job.*`、`artifact.*` 都登记且可用 |
| 记忆与人格包 | 人格 = 记忆的副产物，5 类分片，identity/value 永不被预算裁掉；PC 与手机跑同一份 `memory_pack.py`；实测换包后自称从「大肥鱼」变「设备维护终端」 |
| 手机说话/听写 | 录音→上传识别；播报走系统 TTS，起不来回落电脑合成 |
| 配对一次长期免令牌 | 6 位码换 device_id+secret，电脑重启不用重配；落盘只存 sha256，可撤销 |

### B 档：代码通了，但依赖环境（本轮就栽在这）

| 能力 | 依赖什么，断了的后果 |

## 二、本轮修的三个真事故（都发生在同一天）

| # | 现象 | 根因 | 修法 | 验收 |
|---|---|---|---|---|
| ① | 点「基准测试」必崩 | `activity_device.xml` 里 `btnDevBack` 是 `<TextView>`，Java 却声明 `private Button btnBack;` → `ClassCastException`。**findViewById 是泛型，编译器按声明类型推导、不校验布局，所以编译期零报错** | btnBack 单独声明为 View（它只需要 setOnClickListener） | 真机点：FATAL 数 0，前台 `.DeviceCheckActivity`，页面正常显示 GPU Mali-G925 / 内存 11285MB / 8 核 / 历史基准档案 |
| ② | 审批「点了没反应」 | `worker` 是 **单线程**池，而审批轮询是 `while(...) { sleep(1500) }` 的**长驻循环**，一起跑就把唯一那根线程永久占死 → `sendApproval` 排在无限循环后面永远轮不到 → 30 秒超时 | 加 `urgent` 线程池（2 线程），审批回送/轮询/失效探测全走它；顺手放开 `setCancelable`（不点允许本来就=不执行，锁死只会让人以为卡死） | 代码已改，端到端待复测（见计划 A2） |
| ③ | 弹窗压根不出现 | `ConnectException: Failed to connect to /127.0.0.1:8000`——**adb reverse 掉了**，而轮询的 catch 块是空的，每 1.5 秒 fail 一次、界面一个字没有，副标题「已配对」还是旧的 | 轮询失败打 logcat；连续失败 3 次在界面上说人话（连不上电脑 + 地址 + 怎么恢复），成功后清零 | reverse 补上后手机侧 curl 返回 401（已通到服务端） |

**顺带把①这类坑固化成门禁**：新增 `tools/check_viewcast.py`，扫全部布局建 id→标签表，
比 Java 的 findViewById 目标类型（Button 是 TextView 子类，所以 XML`<Button>`当 TextView
用放行，反过来必崩才报）。已接进 `run_selftests.py`（android_viewcast，秒级离线）。
**注入故障验证过它真会红**（把 btnBack 改回 Button → rc=1 且指出行号），不是永远绿的假门禁。

## 四、还没攻克的（按严重度排，都是**未攻克**）

### P0 —— 不解决就永远会有「玄学 bug」

1. **失败不说话（系统性）**。今天三个 bug 里两个的根因是静默失败。同类还有：
   轮询 catch 空、App 连不上不提示、决策模型挂了只当「无工具面」继续。
   **判据：任何后台循环都必须有心跳日志 + 失败可见。**
2. **审批闭环的环境依赖**。两条 adb 转发（reverse 8000 / forward 18080）没有自愈、
   没有开机自检、没有状态展示。掉了就是「点了没反应」。
3. **决策模型地址硬编码** `127.0.0.1:18080`（`agent_tools.py:28`），无发现、无降级。
4. **门禁覆盖率**：12 个 evals 写完没接（≈415 条断言，纯浪费）、6 个模块自测没接、
   8 个 tools 门禁全游离；**CI 三条流水线一条测试都不跑**，门禁纯靠人手敲。
5. **Android 端几乎裸奔**：零单测、零 UI 测试、零 lint，只有今天加的 1 条静态门禁。

### P1 —— 功能缺口

6. 手机 **LLM/VL 引擎没接**（能下载不能跑，5 个模型是摆设）。
7. 本地 **whisper 未接主链路**（识别仍上传电脑）。
8. **编队控制面 D1**：`shell.exec` / `file.push` / `file.pull` 只有登记，跨机代发没做。
9. `video.gen` 空壳（catalog 登记但无 kind 声明）。
10. `skynet_relay --lan` 无鉴权（注释自认「留给下一版」）。
11. 多轮对话是把历史**折成转写**喂进去（因为十几个免费后端只吃单条 prompt），
    不是真 messages 数组——这是小模型/免费后端的现实约束。

### P2 —— 质量与文档

12. README 数字过期（写 47 项，实际 67 项）；`test_jobs_artifacts.py` 被 README
    称作门禁但根本没接进去——**文档与事实不符**。
13. App 硬编码一堆：签名口令明文 `PASS="tianwang"`、默认地址 `127.0.0.1:8000`、
    `MIN_BYTES=256MB`、能力数口径 87 vs 70 不一致。
14. `MainActivity.java:2058` 三目两支完全相同（冗余/笔误）。

## 六、现在最该记住的一条

**这轮三个 bug，两个是「失败时不说话」造成的。**
能力越多、链路越长，「静默失败」的代价就越大——它不会报错，只会让主人
在某天随手点一下，然后说「点不了」。所以计划里 A 批次（自愈 + 可见 + 复测）
排在补功能前面：先把已经会的东西守稳，再去拿新的。
