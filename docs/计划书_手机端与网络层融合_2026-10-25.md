> 写于 2026-10-25 06:00。依据：当日实测（真机 Redmi K60 已装 `tianwang-next` v0.1-proto）
> + 三个上游仓库当天 HEAD 的 README/源码。

## 一、先把话说清：现在手里到底有什么

### 1.1 两个手机端（产品形态的参照）

| | Operit | pocketpal-ai | 天网 Next |
|---|---|---|---|
| 语言 | Kotlin + Compose | React Native + TS | Kotlin + Compose |
| 星数 | 8952 | 8795 | — |
| 本地模型 | ❌（塞在工具里的旁枝） | ✅ GGUF/llama.cpp | ✅ 已定接口，待接 JNI |
| 云端模型 | ✅ 主路 | ❌ 完全没有 | ✅ 已定接口，待接 SSE |
| 编队/多机 | ❌ | ❌ | ✅ 独有 |
| 界面厚度 | 21 个 feature 模块 | 9 个 screen | 4 个页面（原型） |

**结论**：它们各自瘸一条腿，这是主人当场的原话，不是我的判断。
天网 Next 的取舍点是 **`Model.kt` 里那个 `ModelBackend` 接口**——只要那个 `if (是不是本地)`
永远只出现在 `backendFor()` 一处，加第三个、第四个引擎都不用改 UI。

### 1.2 三个网络层（云端额度的来源）

| | freellmapi | zen-gate | dsh-our-free-model |
|---|---|---|---|
| 语言/形态 | TS 服务 / Docker | Go 桌面托盘 | JS 零依赖插件 |
| 星数 | 40910 | 227 | 41191 |
| 端点 | `:3001/v1` + 统一 Key | 面板可配端口 | 本机 `8326`、独立服务 `18900` |
| 覆盖 | 34 家 635 个免费端点 | OpenCode Zen 车道 + 14 家预设 | 10 个账号渠道 + Kilo + 匿名车道 |
| 局域网 | 需自行暴露 | 面板可配 | **自带中继（0.0.0.0 + 独立 LAN Key）** |
| 特点 | 额度跟踪、按 Key 计用量、自动 failover | 自动注入 Agent 配置、单模型体检、模态路由 | 零依赖、免登录免 Key、说 Anthropic + OpenAI 双协议 |
| 协议 | OpenAI | OpenAI + Anthropic | Chat/Responses + **`/v1/messages`（Anthropic 原生）** |

**关键判断：这三个不是三个系统，是同一种资源的三个实例。**
它们做的事完全一样——**把上游的免费额度，翻译成一个 OpenAI 兼容端点**。
差异只在「上游从哪来」「怎么轮换」「有没有局域网口」。

⇒ 所以融合的正确姿势**不是分别对接三次**，而是抽一层：

```
        ┌──────────── Provider 注册表（一层）────────────┐
        │  id / kind / baseUrl / key / 探测结果 / 模型表 │
        └───────┬──────────┬──────────┬────────────────┘
                │          │          │
           freellmapi   zen-gate    dsh        自付 Key    本地 llama.cpp
```

### 2.1 三个设计决定，以及为什么

**(1) 手机不直连那三家，只连天网路由层。**
理由不是"架构好看"，是三条硬理由：
- 密钥全在 1 号机，**手机丢了不泄露**；
- 手机换网/换 WiFi 不用重配（只记一个天网地址）；
- 三家网关的额度是**共享池**，手机直连就无法统一记账，会互相抢额度。

例外：dsh 自带 LAN 中继、且中继 Key 与本机 Key 互不通用——**离线应急时手机可直连 dsh**，
这是唯一允许的旁路，写进设置页当"应急通道"，默认关。

**(2) 降级链顺序，按"失效概率"从低到高排。**

**为什么本地排第一**：它不依赖任何上游政策，唯一会挂的原因是手机/机器性能。
**为什么自付 Key 排最后**：它是唯一会真花钱的，只在前面全挂时才动。

**(3) 额度按"上游账号"记账，不按 provider 记账。**
freellmapi 的教训：它按 Key 跟踪用量才能不超额。我们三家混用时，
**同一个上游（比如智谱）可能被 dsh 和 zen-gate 同时消耗**——
所以记账的键必须是 `上游厂商 + 账号`，不是 `网关名`。
这一条不做，就会出现"以为还有额度、实际早打满"。

## 三、风险，写在最前面而不是最后面

这三条不是免责声明，是**会让整个方案某天突然失效的现实**：

**R1 · 对抗性方案，随时失效。**
zen-gate 自己的 README 写着：v1.8.0 曾因上游按客户端指纹拦截（一律 403）**退役整条车道**，
v1.9.0 靠对齐官方客户端指纹恢复。这句话的意思是——**上游随时能再关一次**。
⇒ 应对：降级链必须至少有一环不依赖"伪装"，即本地模型或自付 Key。**不能只有白嫖。**

**R2 · 免费池可能记录提示词。**
zen-gate 明说「免费池提示词可能被上游记录，别交机密内容」。
⇒ 应对：`SettingsScreen` 里那个「优先本地」开关不是装饰，是**隐私闸门**。
涉及本机路径、密钥、私人内容的对话，强制本地；网关层只许过"公开可查"的问题。

**R3 · 账号风险。**
这类方案本质是蹭免费车道，可能违反上游 ToS。
⇒ 应对：**只挂小号**，不绑支付方式，不与主账号同设备指纹；一旦某渠道开始 403 就停用，
不反复重试（重试会把账号推到风控前面）。

## 四、分批路线（每批都有可验证的判据）

### P0 · Provider 注册表 + 探测（本机 CLI，先能看见）

- 新增 `fleet/providers.py`：`Provider` 数据类 + 注册表 + `discover()` + `probe()`
- `discover()` 三路并行：**扫候选端口**（3001/8326/18899/18900/8080/8090）、
  **读各自配置文件**（`%APPDATA%\zen-gate\channels\`、`~/.our-free-model`）、**手填**
- `probe()` 打 `/v1/models`，记录：存活 / 首字延迟 / 模型数 / 是否需要 Key / 上次成功时间
- 兼容 `re_llm.py` 已有的 `~/.workbuddy/models.json` 形状，产出同一份文件

**判据**：`python -m fleet.providers` 一条命令列出所有网关，
每行带 `[活/死] 延迟 ms 模型数`，缺哪个能说清缺的原因（不是"不可用"三个字）。

### P1 · 手机端接进来（看得见）

- `ModelsScreen` 的"云端引擎"分组升级为**网关分组**：每个网关一张卡，
  显示 存活灯 / 延迟 / 模型数 / 额度剩余（能拿到的才显示，拿不到就写"未知"）
- 加"应急直连"开关（连 dsh LAN 中继）
- 设置页暴露降级链顺序，可拖动

**判据**：手机上能看见至少 2 个网关的真实状态，并能用其中一个跑通一轮完整对话
（不是假流式，是真 SSE）。

### P2 · 路由与降级（用得起）

- `route(task)`：按 模态需求（图/音/长上下文）+ 降级链 + 当前额度，选一个 provider
- 失败自动换下一个，**响应里标注实际用了谁**（学 zen-gate 的响应头做法）
- 额度记账按 `上游+账号`，落 sqlite，按天聚合

**判据**：手动关掉降级链第一环，同一轮对话不中断，日志能指认"从 A 换到了 B"。
额外：连续 50 轮不同任务，额度记账与上游面板数字对不上时能报警。

### P3 · 随时随地（隧道）

- dsh 的 LAN 中继已有，先复用它验证"手机在外网也能用"
- 再上 `trycloudflare` 隧道（已有 handoff 隧道经验）把天网控制面暴露给手机
- 记住 1 号机是 `0.0.0.0` 还是仅 LAN 的取舍：**默认只绑 LAN**，隧道按需开、带独立 Key

**判据**：手机关掉 WiFi 走 4G，仍能对话；关隧道后 30 秒内手机侧显示"离线"而不是转圈。

### P4 · 工具调用统一（真 Agent）

这一步才轮到"像 Operit"：
- 把天网 149 项能力（`catalog.py` 那份唯一真相）投影成模型可调用的 tool schema
- 工具调用走天网自己的闸门（`tg_mcp.py` + `policy.json` 那套代码级闸门，不靠提示词约束）
- 手机端 `ToolCard` 显示的是真的执行过程，不是 Demo 数据

**判据**：手机上说一句"看下 2 号机的 model 目录"，卡片里出现真的 `node.exec` 与真的目录输出。

**2026-10-25 早，云侧这一半真跑通了**（`fleet/agentloop.py`，门禁 `eval_t40`）：

```
问：这台机器现在的 CPU 和内存怎么样
  → [exec] host.monitor    ✗ 本机未装 psutil（pip install psutil）  ← 如实说原因
  → [exec] pcctl.sysinfo   ✓ Windows 11 / 12 核 / DESKTOP-1BQS174   ← 真数据
  → [exec] host.apps       ✓ 真进程列表 1217 字符                    ← 真结果
  ← zen-gate / glm-5.3-flash-free 收尾：给了 CPU 核数与磁盘，
    **内存查不到就直说查不到**，没拿印象补一个数。
```

三件事在这一轮里同时被验掉：模型**会**用工具表（不是当摆设）、执行层**真**跑了能力、
模型**不编造**（查不到就说查不到）。第三条最值钱——工具闭环最大的风险不是调不动，
是调完空手而归时模型自己编一个像样的答案。

顺带暴露一个真缺口：`host.monitor` 依赖 `psutil`，本机没装 ⇒ 该能力「存在但不可用」。
它按纪律给了原因（不是「不知道」），但想让它活就得装 psutil。

## 五、明确不做什么（防止范围失控）

- **不追求"完全离线可用"**。本地模型是隐私闸门和最后兜底，不是主力——
  手机算力摆在那，4B 在 8G 内存机上就是 6 tok/s 的水平，这一点不能自我欺骗。

### 本轮拍掉的一件事：安卓端在制品（B 路）不进 main

那批在制品（`LlmEngine.java` + `jni/build-llm.sh` + 改动的 5 个 Java）是 **B 路：
llama.cpp 静态链进 `libfleet_llm.so`，引擎内嵌 App，不依赖 Termux**。
它不只是「新增一条路」，它**删掉了 A 路**（`Net.chatLocal`、`Prefs.localBase`、
`DEFAULT_LOCAL` 三处），而 A 路是已出包 build49 真机验证过的。

两条硬事实让它进不了 main：

1. **拿没验证的换掉验证过的**。这台没有 NDK / Android SDK / Gradle，B 路一次都没编过。
   「写了不跑 = 等于没写」是本项目反复复发的病，反过来「跑了才许删旧的」同理。
2. **它是残缺的**：`CMakeLists.txt` 里 `add_library(fleet_llm SHARED llm_jni.cpp)`，
   但 `jni/llm_jni.cpp` **不存在**（全仓 git 历史里也没有）⇒ 现在编必失败。

处理方式：整包提交到 `wip/jni-llm` 分支并推远程（`d70e325`），代码不丢、
那台机器 fetch 即可接手；main 保持 A 路原样。commit message 里留了接手清单
（补 `llm_jni.cpp` 五个 native 符号 → `build-llm.sh` → 真机断网验 → 过了再合 main 并删 A 路）。

### 本轮实测出的两件事（都改了代码，不是笔记）

**(1) 端口读了，Key 没读 = 白探一半。**
`_zen_gate_ports()` 从 `config.json` 取了端口，却让人再去配 `ZENGATE_KEY`——
于是探测显示「活着但要 Key（HTTP 401）」，**模型数永远是 0**。
补 `_find_key_in` 后：zen-gate 变成 `活 / 23 模型 / 16ms`。
（顺带交叉验证：23 这个数与当 v1.9.1 升级后单独验的模型数一致。）

**(2) 降级必须是两级的——这条是真跑出来的。**
原先 `chat()` 只会跨 provider 降级。**真跑一轮**才发现：zen-gate 的 23 个模型
走的是**不同上游车道**，`flint-40b-free`、`mimo-v2.6-flash-free` 相继报
`HTTP 429 FreeUsageLimitError`（那条车道额度打满，不是网关挂了），
第三个 `nemotron-3.5-super-vl-free` 直接成功返回。

⇒ 只会换 provider 的版本，那一轮**必失败**——23 条车道被当成 1 条用。

现改为两级降级，并把 403 与 429 分开对待（对应 R3）：

```
一级 · 同一家内换模型    ← 429 = 这条车道没钱了，别条可能还能用
二级 · 换下一家 provider ← 这家模型全试过，或 403 风控（整家停用不再碰）
```

### 下一步：P4 只剩手机侧那一半（云侧已通）

**云侧这一步本轮做完了**（`fleet/toolschema.py`）。原先判断「投影已经在
`mcp/schema.py` 做过了」——那句只对了一半：MCP 形状有了，**云端两家协议的信封没有**。
同一份能力表有三个出口，信封各不同：

| 出口 | 形状 | 谁管 |
|---|---|---|
| MCP 客户端（IDE/别的机器） | `{name, description, inputSchema}` | `mcp/schema.py`（已有，门禁 t14） |
| OpenAI 兼容（三家网关的 chat 口） | `{"type":"function","function":{name, description, parameters}}` | **本轮新增** |
| Anthropic 原生（dsh 的 `/v1/messages`） | `{name, description, input_schema}` ← snake_case | **本轮新增** |

写错就是请求被拒：`input_schema` 写成 `inputSchema`、或给 Anthropic 套了
`{"type":"function"}` 那层壳，网关直接 400。所以这两种形状必须有测试钉着。

**更重要的是回环**（模型说完怎么读回来）：OpenAI 的 `function.arguments` 是
**JSON 字符串**，Anthropic 的 `tool_use.input` 已经是对象；两边都得还原成
**能力真名**——走 `ToolIndex` 查表，不是把下划线换回点号（那是有损反解，
`a_b` 和 `a.b` 同时存在时会指错）。模型叫错名字时**如实报错回给它**，不静默跳过：
它不知道自己叫错了，跳过只会换个名字再错一次。

安全口径与 `mcp/schema.py` 同一套（不许有第二套）：默认只导出只读的 85 项，
副作用 64 项要显式 `include_unsafe=True` 才给；模型给的参数一律按 Param 表校验
（`"3"` → `3`、缺必填报错回给模型、多余字段丢掉但**说明丢了什么**）；
本模块**不执行任何东西**，解析完交给 `Registry.call`，闸门在那一层（无 gate 即拒绝）。

**剩下的那一半要那台机器**：手机端 `ToolCard` 显示真的执行过程（现在还是 Demo 数据），
以及真跑一轮「云端模型 → 发工具表 → 回调 → `node.exec` → 真目录输出」的闭环。
本机做不了：前者要 Kotlin，后者要手机在场。
