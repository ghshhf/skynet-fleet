# 手机能力升级计划书：万能遥控 × 探测叠加 × 距离感知

> 2026-10-24 · 主人定调：「手机的能力绝不止表面上这么简单。万能遥控不是终点；
> 再叠加一个跟探测监控一样的东西；最重要的是距离——你现在只能报方向，
> 我得靠猜。」本计划书把这三件事工程化，先评审后动手。

---

## 〇、结论前置

主人说的「万能遥控 + 探测监控一叠加」，工程上是一个三段闭环：

```
靠近它 ──→ 认识它 ──→ 指挥它
距离感知     暴露面测绘    任意波形发射
(现在只有     (PC 侧有,     (只能发码库
 方向没有     手机侧没有)     里有的码)
 米数)
```

三段各有一半，缺的一环共同点是**没有把「人走路的位移」和「口袋里的手机」接进去当定位源与探测源**。计划分四步，全部复用现有资产：

| 阶段 | 内容 | 直接回答的问题 | 依赖 | 诚实边界 |
|---|---|---|---|---|
| **P0** | 距离感知引擎（RSSI→米 + 热冷导航 + 步程推算） | 「到底多远？」 | 零新增，数据已在手 | 室内误差 ±3~5m 是物理限制 |
| **P1** | 万能遥控 v2（任意波形透传 + 码库扩充 + 空调状态机） | 「厂商没给的遥控器」 | 零新增 | 本机无学习口，不假装能学 |
| **P2** | 热点叠加编队（开热点→设备自己进来→手机侧组网视角） | 「现场设备怎么进编队」 | 零新增 | 依赖手机热点真起得来 |
| **P3** | 监控探测下放（wall_probe 移植 Termux，边走边扫） | 「出门也能探测」 | 零新增 | 只读止于 DESCRIBE，红线不变 |

四个阶段全部**零新增硬件、零新增依赖**（纯标准库 / 已有 termux-api / 已有 adb 桥），这是先做它们的理由。

## 一、现状资产盘点（真有的，不是计划要有的）

| 资产 | 位置 | 现状 |
|---|---|---|
| RSSI 数据源 | `radio.py` wifi_survey/wifi_link、`nearby.py` bt.scan | WiFi/蓝牙信号强度已在手，`survey.distance_hint()` 只有五档文字（「同一房间/几米内/隔墙」），**没有米数** |
| 运动传感器 | `android_device.sensor_read`（termux-sensor） | 加速度/磁力计/步数计/接近光已在读（`acquire.phone_sense`），但只用于房间状态，没用于定位 |

| 任意波形 | `infrared.py` 脉冲编码 + ir.send | 底层支持任意 pattern 透传，「万能」的硬件条件已具备 |
| 协议逆向 | `fleet/reverse.py` re.ir | NEC 脉冲→协议判据→码库对照已落地（21/21 自测），可扩展到其他协议 |
| 热点 | `creative.hotspot` | on/off + dumpsys 读客户端数，**开完之后没有后续动作** |
| 组网视角 | `nearby.py` / `sweep.py` | 全部是 PC 视角；手机开热点后手机才是网关，视角该换成它 |
| 暴露面测绘 | `tools/wall_probe.py` | RTSP OPTIONS/DESCRIBE + ONVIF 组播 + HTTP banner，PC 侧，只覆盖 192.168.0.x 一条网段 |
| 远程链路 | `fleet/remote_link.py`（L6） | 手机在外网也可被家里电脑操控，野外自治的基础设施已在 |

**手机侧铁律事实（红米 25060RK16C）**：有红外**发射口**，无红外**学习口**（无 IR RX）。所以「万能遥控」的正确路线不是「学」，是**任意波形透传 + 协议逆向重建**——见 P1。

## 二、P0 距离感知引擎（第一枪，直接解决「只能报方向」）

### 2.1 用户痛点的精确描述

> 「探测距离相关的，你现在就不知道距离范围是多远，只能你给我报一个方向，我大概去猜。」

翻译成工程问题：现在 `distance_hint()` 给的是「同一房间/几米内」五档文字，主人要的是**米数 + 「我在靠近还是在远离」**。

### 2.2 四个子能力（按性价比排序）

**a. RSSI → 米（对数距离路径损耗模型）**

```
d = 10 ^ ((A - rssi) / (10 × n))
```

- `A` = 1 米处的参考接收功率（WiFi 实测约 -40~-45dBm，需本机校准）
- `n` = 路径损耗指数：自由空间 2.0，室内实体墙 2.7~4.0（实测标定）
- 校准方法：拿自家路由器，1/2/5/10 米各采 50 次，回归出本机 A 和 n

**b. 热冷导航（实时「更近了/更远了」）**

边走边采 RSSI 序列 → 对最近 N 次采样求斜率 → 播报「正在靠近（约 X 米→Y 米）/ 正在远离 / 原地打转」。这就是主人说的「报一个方向」的升级版：**方向 + 速度 + 米数**。

**c. 步程推算 PDR（给估距加时间维度）**

步数计 × 步长（个人标定）+ 磁力计航向 → 走路轨迹。作用：当 RSSI 因为多径抖动不可信时，PDR 给出「我这 30 秒走了大约 6 米」这个独立参照，两个估计互校。

**d. 多 AP 加权三角定位（有 3+ 个 AP 时）**

三个已知位置 AP 的 RSSI 各自估距 → 加权最小二乘求交点。室内粗定位用，与 a/b/c 互为校验。

### 2.3 诚实边界（写进代码注释，不写进幻觉）

- **单次 RSSI 测距误差可达一倍**：多径衰落让同一距离的 RSSI 抖动 ±5~10dBm。这是物理限制，不是没优化。
- 对策：连续采样 + 中值窗/卡尔曼滤波，**报区间不报单点**（「3~5 米」而不是「4.1 米」）。
- 5GHz 比 2.4GHz 衰减快，同模型要分频段标定。
- 目标设备（摄像头/AP）自己没有位置——RSSI 估距是「无位置设备」的补位方案；手机自己的 GPS（termux-location）是参照系，不替代对目标的估距。

### 2.4 验收标准

1. 已知距离标定：1/2/5/10m 四点，估计值落在 ±30% 区间内 ≥ 80%
2. 热冷盲测：不看屏幕，只听话播，走到目标 AP 前 1 米内停
3. 输出永远带区间和置信说明，无「精确米数」字样

## 三、P1 万能遥控 v2（厂商给啥用啥 → 波形自由）

### 3.1 为什么现在还不够「万能」

现状是码库路线：主人说「小米 电视 开机」→ 查码库 → NEC 编码 → 发射。三个缺口：

1. **码库只有 4 品牌**：没说到的品牌/型号直接报「不支持」
2. **NEC-only**：很多空调/风扇用其他协议（Panasonic/Kaseikyo、Sony SIRC、RC5/RC6、Sharp）
3. **空调是状态机不是开关**：电视按一下 power 是翻转；空调每次发的是**全状态快照**（温度+模式+风速+扫风），现在发一个「开机」键，不知道空调原来什么态，发完什么态不可知

### 3.2 三个升级

**a. 任意波形透传（真正的「万能」底座）**

Android ConsumerIrManager.transmit() 可以在 getCarrierFrequencies() 返回的任意频率区间发任意 pattern。也就是说：**码库里没有的码，不等于发不出去**——只要知道协议结构，就能算出波形发出去。硬件的「万能」条件已具备，缺的是协议覆盖。

**b. 协议逆向重建码库**

复用已有的 `re.ir`（NEC 判据 21/21）扩展协议族：lead 码结构、反码校验、位时序各协议的判定函数。拿不到原遥控器时的兜底：**已知协议 + 参数空间搜索 + 设备响应 = 真值**——发射器可重放任意 pattern，按协议参数网格发过去，哪个码让设备动了，那个就是对的（ bruteforce 协议参数，不是 bruteforce 口令，不碰红线）。

**c. 空调状态机**

本地维护「目标空调」状态（温度±0.5、模式、风速、扫风、电源），每次命令 diff 出新快照再整包发。发之前先报「将把空调设为 26℃ 制冷 中风」，过闸门后发射。这解决「不知道空调什么态」的根本问题。

### 3.3 叠加（与 P0/P3 的合流点）

- P0 报「目标在 3 米内且同房间」才允许发射——省得对着墙按
- P3 探测到「这台是海信空调（banner 自报）」→ 直接建议用哪个码库条目
- 三步闭环：**走近（P0）→ 认出（P3）→ 指挥（P1）**

### 3.4 诚实边界

- 本机无 IR RX，「学习」功能明确不做、不宣传；缺码走协议重建，重建不出如实报「此型号暂无码」
- 红外是直线视距，穿不过墙和柜子——「发射成功」≠ 「设备收到」，以设备实际响应为准
- ir.command 保持 dry_run 默认 + approval=ask 闸门不变

## 四、P2 热点叠加编队（开热点 → 设备自己进来）

### 4.1 现状缺口

`hotspot on` 能把热点开起来，但开完之后没有后续：客户端连进来了不知道，设备进编队靠手动。

### 4.2 升级动作

```
开热点 → 读 DHCP 租约（哪些设备连进来了）
      → 手机侧自动 nearby + sweep（视角从 PC 换成手机这个网关）
      → 哨兵标注「新入网设备」
      → （叠加 L6）手机反连家里电脑 = 野外自治编队
```

关键变化：**现在所有能力都是「设备在我家 LAN 上」的视角；开了热点，任何我带到现场的设备一连进来就进编队**。例：把 RK 板子带到楼道，手机开热点，板子一连，整条能力链（屏幕读取/红外/传感/LLM）本地闭合，不依赖现场有没有外部网络。

### 4.3 诚实边界

- 手机热点能否真正起来依赖 ROM（历史上开失败过，用 WinRT 修法救过 PC 侧热点；手机侧同理：起不来如实报，不重试轰炸）
- 连进来的设备默认只做只读探测，发射/操控类照旧过闸门

## 五、P3 监控探测下放（wall_probe 从 PC 到口袋）

### 5.1 升级动作

`tools/wall_probe.py` 核心逻辑（RTSP OPTIONS/DESCRIBE、ONVIF 组播、HTTP banner）是**纯标准库实现**，和 memory_pack 一样可以 PC/Termux 共用一份代码。移植后新增手机能力 `net.wallprobe`：

- 手机每连一个新 WiFi → 自动探测一轮 → 暴露面记录（有无墙、SDP 能否拿、ONVIF 端点）
- 叠加 P0 热冷导航：**「朝信号强的方向走，找到摄像头，报告它有没有认证墙」**
- 时间戳 + 位置（GPS 若有）落盘，形成「走过之处的暴露面地图」

### 5.2 诚实边界（与 PC 版完全一致，不因换设备放松）

- 只读止于 DESCRIBE；拿到 401/403 立即停
- **不发 SETUP/PLAY、不携带任何凭据、不做任何口令尝试**——刑法 285/286 管的是未授权访问本身，与目标是否违法无关，这条红线不移动
- 探测范围限「我已连接的网络」和「公开广播的设备发现机制」，不指向个人持续追踪

## 六、明确不做清单

| 不做 | 原因 |
|---|---|
| 红外「学习」功能 | 硬件无 RX 口，做不了就不宣传 |
| 任何携带凭据的网络请求 / SETUP/PLAY / 口令爆破 | 刑法 285/286，与目标是否违法无关 |
| 指向个人的持续追踪 | 红线，默认告知 + 过闸门 |
| GPS 替代 RSSI 估距 | 目标设备没 GPS，两者是互补不是替代 |
| 精确到厘米的测距承诺 | 物理不允许，报区间 |
