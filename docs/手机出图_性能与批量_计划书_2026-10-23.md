## 1. 实测基线（2026-10-23 03:20–03:28，真机 K80 至尊版，不是估算）

```
可用后端设备（sd_list_devices 原文）：
  Vulkan0   Mali-G925-Immortalis MC12      ← GPU 找对了，就是 Immortalis-G925
  CPU       CPU

模型：sd15-q8_0.gguf  1,763,578,176 字节（1.64 GiB）
参数：512×512 / 10 步 / cfg 7.0 / Euler A / backend=vulkan / threads=4

模型加载   2112 ms
去噪 10 步  33.2 33.3 33.3 33.3 33.5 33.4 33.3 33.2 33.3 33.2  → 约 33.3 s/步，共 300 s
VAE 解码                                                      → 134 s
总耗时      472.86 s = 7 分 53 秒
产物        512×512 PNG 489,190 字节
```

**对比 CPU 基线（02:49 那次，同模型同参数）**：约 80 s/步。
⇒ **Vulkan 只快了 2.4 倍。** 这台 GPU 本该快一个数量级，所以现在是「有东西拖着」，不是「手机就该这么慢」。

### 已经能排除的一个怀疑

十步耗时是 **33.2 → 33.2，平的**，没有随步数上涨。
⇒ **不是温控降频。** 降频的表现应该越跑越慢。这条省掉了后面很多瞎猜。

## 2. 性能：嫌疑人排序（按"改动成本 / 可能收益"排）

| # | 嫌疑人 | 证据 | 验证动作 | 成本 |
|---|---|---|---|---|
| 1 | **VAE 被推回 CPU** | VAE 单独吃了 **134 s**（总时长 28%）。我在 `sd_jni.cpp` 里写了 `cp.vae_conv_direct = true`，当时注释写的是「省一截中间显存」——在 Vulkan 路径上这很可能把 VAE 卷积踢回 CPU。**是我自己埋的** | 改成 `false` 重跑，对比 VAE 段耗时 | 一行 + 一次重编 |
| 2 | **权重不在 GPU 显存里** | 1.64 GiB 的 q8_0 很可能超出 sd.cpp 判给 GPU 的预算，于是每步搬权重 | 试 `cp.max_vram`（显式给 GiB 预算）和 `cp.eager_load`；看 s/步 是否跳水 | 参数 + 重跑 |
| 3 | **量化档太重** | q8_0 = 1.64 GiB。q5_1 / q4 体积减半 | PC 下 q5_1 推上去重测 | 再下一次模型（PC 侧） |
| 4 | 步数 | 10 步是 UI 默认值，**不是性能问题，是画质主因** | 见 §3 | 零成本 |
| 5 | 少步采样（LCM/Turbo） | 4 步出图，是唯一能拿数量级收益的路 | 需要额外模型/LoRA，见 §5 待拍板 | 要下模型 |

**排查纪律**：一次只改一个变量，每次都记 `s/步` 和 VAE 段耗时，改完拿数据说话。不许同时改三处然后"感觉快了"。

## 3. 画质：主因是步数，不是提示词

主人说「也可能我给的提示词太离谱」。实测下来**不是**。

- SD1.5 的常规出图步数是 **20–25 步**；UI 现在默认 **10 步**。
- Euler A 在 10 步下只够出个大轮廓，细节基本没收敛 —— 这就是「没法看」的来源。
- 512×512 是 SD1.5 的原生分辨率，这个没问题；再往上拉（768/1024）它会更糊。

⇒ 修画质第一条：**默认步数 10 → 20**。代价是时间翻倍，所以**必须先做 §2 的性能排查**，否则 20 步 = 15 分钟一张，更没法用。

## 4. 功能设计

### P1 · 队列 / 批量（`ImageQueue`）

```
ImageJob { id, prompt, neg, size, steps, seed, cfg, backend, mode }
ImageQueue: 单线程 Executor + 内存 ArrayList
```

- **串行**：模型只加载一次（2112ms，不重复付），逐张出结果，每完成一张就落盘 + 刷新列表。
- **批量入口**：一次提交多个 prompt（一行一个），或同一 prompt 出 N 张（不同种子）。
- **可中断**：取消当前 / 清空队列。已出的图不丢。
- **结果落盘**：写到外部私有目录 `files/images/`，带 `jobId + 种子 + 参数` 命名，方便事后回看和 PC 端取。
- **UI**：出图页底部常驻「队列 N 项 · 第 k 张」，进度沿用现有 `推理中 x/y`。

不做并发的理由（实测）：单张 RSS 峰值 2.67GB，机器 `MemTotal` 11.0 GiB，两份必炸；安卓还会杀后台进程。

### P2 · 档位 + 自适应

| 档位 | 步数 | 尺寸 | 说明 |
|---|---|---|---|
| 快速 | 4–8 | 512 | ⚠️ 画质明显下降，UI 上必须写清楚 |
| 标准 | 20 | 512 | 默认 |
| 精细 | 25 | 512 / 768 | 768 只在显存够时可选 |

**自适应输入只认三样实测值**（不许按机型名猜）：
1. `sd_list_devices()` 里有没有 `Vulkan` 行 → 决定后端；
2. `MemTotal`（`/proc/meminfo`）→ 决定能不能上 768；
3. **首张实测 s/步**（跑完写进 SharedPreferences）→ 决定默认档位。

规则（初版）：有 Vulkan 用 Vulkan；`MemTotal < 6 GiB` 或 `s/步 > 20` → 降档并开 `vae_tiling`；无 Vulkan → CPU + 降档。
**自适应结果必须在 UI 上显示依据**（"GPU: Mali-G925 · 33 s/步 → 标准档"），且允许手动覆盖。

## 8. 排查实录（2026-10-23 04:0x–04:3x，全部实测，覆盖前面的估计）

### 8.1 单张图的时间到底花在哪

分段计时（C 端按"进度回调 step 值回退 = 换段"判定）跑出来的实账：

| 段 | 实测 | 说明 |
|---|---|---|
| 段1（686 步回调） | 3.5 s | 不是去噪，是调度/编码一类准备 |
| 段2（= 采样步数） | **34 s/步** | 🔴 真正的去噪，SD1.5 512² 在 Vulkan 上本该 <1 s/步 |
| 段3（140 步回调） | 约 134 s | 🔴 VAE 解码，与上一版测到的 134 s 吻合 |
| **合计（2 步）** | **205.3 s** | 加载 1 s + 去噪 68 s + VAE 134 s |

⇒ **VAE 134 秒是单张图最大的一块**；去噪 34 s/步 意味着 20 步就要 680 秒。
两者都远低于这台 Immortalis-G925 该有的水平（CPU 基线 80 s/步，Vulkan 只快 2.4×）。

### 8.2 `vae_conv_direct` 的 A/B（结论：必须 true）

| 取值 | 行为 | 实测 |
|---|---|---|
| `true` | `conv_direct_for()` 直接 return，**跳过探测** | VAE 134 s |
| `false` | 走 `sd_probe_conv_direct()`，Vulkan 分支逐个 shape 建 probe graph | **探测本身吃 9 分半，2 步的图跑了 12.5 分钟仍未出图** |

原因见 `src/pipeline/diffusion_engine.cpp` 的 `conv_direct_for()`。
⇒ 已改回 `true`，并把实测写进代码注释（含"为什么不能改 false"）。
另注：参数里还有 `conv_direct_mode`（on/off/auto 或分模块），可显式指定以彻底绕开探测，待试。

### 8.3 之前"33 s/步"与这次"去噪 0.2 s"的矛盾 → 已澄清

同一份日志里存在**三段不同分母**的进度回调（686 / 2 / 140）。只记"首末回调跨度"会把跨段
时间当成去噪，算出"74 s/步"这种错数。现在 C 端和 Java 端都用**最后一次 step 回退**作分段点，
并保留"未分段"标注，不拿总时间除步数假装那是 s/步。

### 8.4 新装上的诊断与提速手段

1. **日志回调**（`sd_set_log_callback` → logcat）：sd.cpp/ggml 默认往 stderr 打，
   Android 上根本不进 logcat ⇒ 此前"Vulkan 有没有算子回退 CPU"我们完全看不到，只能猜。
   已在 `JNI_OnLoad` 里最早接上（丢弃 DEBUG，避免刷屏）。
2. **TAESD**（`taesd_path`，9.3 MB 蒸馏解码器）：专治 VAE 那 134 秒。已下载并推到手机，
   有该文件就启用，UI 上标明「TAESD 解码（快，画质略软）」，不静默降级。
3. **SD2.1 Turbo q8_0**（2.32 GB）：少步模型，4~8 步；**必须 cfg=1.0 + LCM 采样**。
   已下载（校验 size 一致）并推到手机。
4. **无人值守基准**：`am start .MainActivity --ez bench true --ei steps N --ei size S`，
   结果全进 logcat（`fleet-dev`）。原因是小米"后台弹出界面"默认关闭，非 LAUNCHER 的新
   Activity 会被直接拦掉（`DeviceCheckActivity` 实测起不来）。

### 8.5 下一步（按收益排序）

1. 跑 Turbo + TAESD 的基准，拿到新的 s/步 与总时间（**唯一能判断值不值的依据**）；
2. 用新接上的 sd.cpp 日志看 Vulkan 有没有算子回退 CPU —— 这是 34 s/步 的根因候选；
3. 视结果考虑 q4 量化（权重减半，测是否带宽受限）或 `conv_direct_mode=on`。

## 9. 修订结论（2026-10-23 05:1x，基于上面全实测，更新 §6 验收闸）

**VAE 修好后，真正的墙是去噪 33 s/步（SD1.5，Vulkan）。** 它只比 CPU 的 80 s/步 快 2.4×，
根因**仍未找到**（权重确认在 GPU 显存、无算子回退 CPU 告警 ⇒ 疑 ggml Vulkan 后端在 Mali 上
本身低效，非软件配置问题）。这条不在我们短期能改的范围内。

⇒ 重算 §6 的 P0 闸「512²/20 步 单张 ≤ 3 分钟」：

| 档位 | 模型 | 步数 | 实测单张 | 过闸？ |
|---|---|---|---|---|
| 快速 | **Turbo** q8_0 | 4~6 | **~80 s（1.3 分钟）** | ✅ |
| 标准 | SD1.5 q8_0 | 20 | **~660 s + VAE 9s ≈ 11 分钟** | 🔴 远超标 |
| 精细 | SD1.5 q8_0 | 28 | **~15 分钟** | 🔴 |

**结论：在本机（Immortalis-G925 + Vulkan 低效），SD1.5 任何档位都过不了 3 分钟闸；
只有 Turbo 快速档达标。** 这直接冲击 §5#4 的拍板（"默认给标准"）——标准档在本机是 11 分钟，
体验比"负担"还差。
