# 违法广告向量研究报告：搜索模块捕获样本的 LLM 拆解（2026-10-24）

> 方法：`tools/ad_harvest.py` 用 18 条**正常用户真会搜的查询**撞搜索模块
> （社保/减肥/直播/贷款/比特币/安卓版本…），保留过滤前的全部原始命中；
> `tools/ad_classify.py` 把 112 条命中批量喂给免费 LLM（Beam 1.0，42.5s，
> 10 批）做定性；域名/标题形状统计全部本地确定性计算。
> **纪律：只采元数据（标题/URL/域名），不抓广告页正文、不点跳转链、不登录。**
> 研究的是「广告从哪个口进来、长什么形状」，不是广告内容本身。

## 一、结论（前置）

1. **违法广告进我们上下文的主端口是「高信誉域名寄生 SEO」**：112 条样本里
   63 条（56%）落在 github.com，LLM 判定的 12 条违法/垃圾**全部**是
   GitHub 寄生仓库。手法：一次性小号批量建仓，仓库名/描述直接写导流词，
   借 GitHub 的搜索引擎权重抢排名。
2. **现有过滤规则对这 12 条全部放行**——因为它们标题里**确实含查询词**
   （这正是 SEO 垃圾的设计目的，「标题与问题无字面重叠」规则失效）。
3. 违法广告按品类分六个端口：GitHub 寄生、假交易所 APK、博彩 App、
   盗版影视、成人内容、TG 镜像。各自的话术与形状见第三节，全部带样本。
4. 搜索模块本身有三个病：Bing RSS **串味**（结果不跟踪查询，已被相关度
   闸门挡住）、DDG 限流（暂时状态，按窗口恢复）、`Hit` **无摘要字段**
   （广告话术最密集的 description 在引擎层就被丢弃）。

## 四、这些端口共通的形状（→ 过滤规则）

1. **品类词 + 入口词组合**：直播/影视/观看/破解/网盘 × 官网/入口/网址/最新网站。
   正常技术页描述软件功能（「集成热门资源站实现离线下载」），导流页堆入口。
2. **标题内嵌裸域名**：`(lyiwush.com)`、`-xxx.com`。
3. **真品牌 +「官方下载」**：交易所品牌词 + APK/下载/安装/教程 = 诈骗前置。
4. **GitHub 仓库名即导流词**：拼音串、品类词、随机后缀 + 描述含品类词。
5. **问号堆砌**（已有规则覆盖）：`due65/version` 96 字 6 问号抢比特币价格排名。

## 五、搜索模块本身的三个病

1. **Bing RSS 串味（已知污染的实锤）**：搜「养老保险查询个人账户」返回
   「Quote of the Day」「快雪时晴帖」——结果完全不跟踪查询，是投给机器的
   串味缓存；返回集里还混着 `bingquiz.com`/`bingquote.com` 这种专蹭 Bing
   关键词的站群。代码里 `Engine("bing", ..., 0.8) # 已知污染` 已有标注，
   zh 桶健康度 426 进 56 活（13%）——是相关度闸门在替它兜底。
   **本轮不修 URL**（加 mkt 实测更坏：python 查询带 mkt 返回 quiz 垃圾），
   只记录：Bing 的产出必须经过相关度闸门才可用。
2. **DDG 限流（暂时）**：连采 18 条查询后归零，之前同查询能出 9 条。
   按窗口滚动恢复，标「待刷新」不删除。
3. **`Hit` 无摘要字段**：skynet 引擎层 `_rss_items` 只抽 (url, title)，
   description 被丢；`Hit.brief()` 只是调试格式化串不是摘要。
   webtool 里 `hit.get("snippet") or hit.get("desc")` 因此永远是空串——
   **广告话术最密集的一段从来没进过管线**。这是下一步模块加固的首修项。

## 六、已落地的加固

`webtool.py` `_junk_reason` 新增形状规则（全部用本轮真机样本做自测向量）：

1. 标题内嵌外部域名（知名站点白名单除外）→ 导流页
2. 真交易所品牌 + 官方 App 下载话术 → 假 App 导流（诈骗前置）
3. GitHub 仓库名是拼音品类词/随机后缀且描述含品类词 → 寄生 SEO
4. 品类词 × 入口词组合 → 导流页（不碰正常技术页：正常页描述功能、
   不堆「官网/入口/网址」；误伤对照 moviecatcher 进自测）
5. 成人内容（标题 + 摘要双查）→ 不进上下文

回归结果：**LLM 判违法的 12 条全部拦下（旧规则全部漏判），LLM 判正常的
87 条零误伤。**自测 55 → 56 项。已提交 skynet-fleet `d6868ae`。

**摘要链路已修复并结案**：skynet 五个引擎（bing RSS / ddg html / searx
JSON / github API / mediawiki）改为返回 `(url, title, desc)` 三元组，
`Hit` 加 `desc` 字段，聚合层按 `DESC_TRUST=160` 合并；包装层
`netforce_skynet.search()` 不再丢摘要，webtool 的 snippet 兜底链第一次
有真数据。已提交 netforce `baf7214`。复采 55 条验证 55/55 带摘要，
正版站（爱奇艺/豆瓣）与寄生仓库的摘要都能正常区分。

## 七、边界与未决

- **未抓任何广告页正文**：品类判定只凭标题/URL/域名字面。落地页内容、
  跳转链、收款方式未验证（也不去验证）。
- **样本偏差**：112 条里 56% 是 GitHub，与「正常搜索的广告构成」有差；
  零命名的 5 条生活服务查询要等 DDG 恢复后补采。
- **LLM 判据的边界**： Beam 对「moviecatcher」这类真开源项目判 normal
  正确（有功能描述、无入口词），说明「功能描述 vs 入口堆砌」的区分线
  在模型侧也成立——这条区分线已固化为规则 4 的判据。
- **站群域名**（bingquiz.com 等）未深挖，留作下一轮样本。
