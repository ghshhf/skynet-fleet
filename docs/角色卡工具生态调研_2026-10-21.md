## 0. 结论先行（12 条）

1. **用户转述里的 CardForge 已经废弃。** `Shizuku-Yume/cardforge` 的 README 第一行就是
   「项目现已迁移至 `Shizuku-Yume/Arcamage`　本仓库废弃」。**继任者 Arcamage 是 MIT、2026-06 仍在活跃提交**，
   比 CardForge 强得多。引用工具时要连迁移关系一起说，否则会指着一个坟。
2. **社区角色卡工具分三类，本仓只该抄第 3 类。**
   - ① **Web GUI 编辑器**（Arcamage / Tavern Card Crafter / aimaker）：给人用鼠标点。
   - ② **CLI 打包器**（`Nya-Foundation/card-forge` Python CLI / `numb747/card-forge` Rust+egui / `tavern-cards-forge` Node）：
     离线 pack/unpack 卡。
   - ③ **给 Agent 用的 skill/方法论包**（`ai4rpg/tavern-cards`）：**这是唯一跟本仓技术路线同构的一类。**
3. **最该看的是用户转述里漏掉的 `ai4rpg/tavern-cards`。**
   它不是「角色卡编辑器」，是**一套 Coding Agent skill 集 + 离线 forge CLI**：
   目录里放 `tavern-design/`（叙事设计）、`tavern-cards/`（写卡流程）、`tavern-ui/`（前端渲染）三个 skill，
   加上 `agents/*.md` 子代理（禁词扫描、长文本大纲提取、MVU 变量结构编写）。
   **它的形态和本仓「一切皆 MCP + 技能装载 + 角色编队」是同构的。** 本仓 `fleet/skills.py` 认的正是
   `SKILL.md` + frontmatter，这套东西装进 `skills/` 就能被本仓直接识别。
4. **它的核心工作流对本仓有直接价值：「解包 → 改一处 → 重打包」是增量改卡的最短路径。**
   本仓现在是「整张 JSON 卡读进来 → 改 → 整张写回」，改一个字段要手写整个 JSON。
   tavern-cards 的做法是 **JSON Patch / 条目级定位**，改一个条目不动别的条目——这正好是本仓缺的能力。
5. **它有一个本仓完全没有的东西：角色卡质量的「机械扫描」。**
   `check-agent` 做禁词扫描，`conversion-agent` 做长文本整理，「评估角色卡质量」是它的正式场景之一。
   本仓 `docs/角色卡生态调研` §7.3 早就建议做「卡的安全体检器」，**社区已经开始做了**——
   这不再是「我们独有的想法」，但**我们做的会比它更严**：它扫禁词，我们该扫**注入模式**（我们能操控本机，风险更高）。
6. **Arcamage 有两个设计值得抄。**
   - ① **Diff 预览 + 确认后应用**（Agent 模式每次修改先给差异对比，用户确认才落盘）。
     本仓有审批闸门（`approval="ask"`）但**没有差异预览**——用户点「执行」前看不到到底要改什么。
     🔴 这是本仓审批体系的真缺口：审批只回答「许不许」，不回答「改成什么」。
   - ② **非破坏式 PNG 导出**（chunk 级写入，不碰像素数据）。本仓 `_png_card_payload()` 已经是这个路子，
     但**没有写回 PNG 的路径**（只读不写）。
7. **Tavern Card Crafter v3 值得抄的是「提示词可编辑可持久化」**，不是它的界面。
   它把 AI 生成用的提示词从硬编码改成用户可编辑的 JSON 模板，支持变量插值、多个 AI provider。
   本仓的对应物是**技能正文**——本仓 `fleet/skills.py` 已经把技能当方法论文档，但**技能正文里的提示词模板**还没有这个概念。
8. **`aimaker`（`altkriz/aimaker`）的形态最轻**：纯客户端单文件、MIT、零后端。
   它的价值不在功能多，而在**证明了「不装 Docker 也能用」是可行的**——
   本仓的桌面版是零构建纯手写 HTML/CSS/JS，**天然比社区这些 Docker + FastAPI + Vite 的栈轻**。
9. **MVU（变量系统）本仓不需要。** MVU 是酒馆的状态栏 + Zod schema + 变量更新正则，
   是为了让角色卡在酒馆前端里「有面板、能变状态」。本仓的人格状态走自己的 `persona.py`（情绪/口癖/黏人），
   **不做酒馆前端兼容 ⇒ MVU 无处安放**。**明确排除。**
10. **EJS / 正则脚本本仓不需要。** 同理，那是酒馆前端渲染卡条目的机制；
    本仓是「卡 → system prompt」的单向注入，**不做模板渲染**。`use_regex` 那种**条目级**正则要支持（规范要求），
    但**卡内容里的 EJS 模板不执行**。明确排除。
11. **本仓已有的调研结论有几条已过期，必须以本次实跑为准。** 见 §4 对照表。
12. **总判断：本仓的缺口不在「编辑界面」，在「增量改卡 + 体检器 + 审批时的差异预览」三件事。**
    角色卡的**可视化编辑器**是社区的红海（Arcamage / Crafter / aimaker 都在做），
    本仓做一个必然不如它们；但**这三件事社区都没做好**，且正好是本仓的强项所在。

## 2. 分类：三类工具，本仓只抄第三类

### 2.1 第 ① 类：Web GUI 编辑器（红海，别进）

| 项目 | 栈 | 形态 | 关键能力 |
|---|---|---|---|
| **Arcamage** | Python 3.11+ / FastAPI / Pydantic v2 / Uvicorn + Alpine.js / Vite / Tailwind / Docker 多阶段 | Web 容器 | 分区编辑、世界书拖拽排序、**Agent 模式（自然语言改卡 + Diff 预览 + 撤销/按条目重试）**、Arcaferry 远程批量拉取、内置 skill 导入导出、**非破坏式 PNG 导出（chunk 级写入）** |
| **Tavern Card Crafter v3** | React + TS + Vite + Electron + Tailwind + shadcn | Web + 桌面 | 从自由文本（小说/百科/设定）**AI 抽取生成结构化卡**、v3 全字段、**提示词模板可编辑可持久化**、实时 JSON + token 估算、多 AI endpoint |
| **aimaker** | 纯客户端单文件 | 浏览器本地 | 极轻量，MIT，零后端 |
| **sillytavern-cardforge** | — | — | MVU / 正则 / EJS / 状态栏 |

**为什么本仓不进这条赛道**：
① 社区已有 4+ 个成熟实现，做 GUI 必输；
② 本仓桌面版是**零构建纯手写 HTML/CSS/JS**（仓库铁律：纯 CPU 文本处理一律本机做、零第三方依赖），
   而上面这些都是 Docker + FastAPI + Vite 的重型栈，**抄进来会破本仓的零依赖铁律**；
③ 本仓的用户是**主人一个人**，不是「酒馆玩家大众」⇒ 通用性 = 复杂度 = 成本，没有回报。

### 2.2 第 ② 类：CLI 打包器（可作参照，暂不进）

- `Nya-Foundation/card-forge`（Python CLI，MIT）、`numb747/card-forge`（Rust + egui，GPL-3.0）
- `tavern-cards-forge`（Node）：**pack / unpack / 自动推导运行时配置 / JSON Patch**

**对本仓的价值**：`unpack → 改 → pack` 的**项目目录化**思路，
它让「改一处」不需要重写整张卡（见 §3.1）。但本仓卡少（6 张）、字段少，
**先不做项目目录化**，只做**字段级 patch**（见 §5 建议 P1）。

### 2.3 第 ③ 类：给 Agent 用的 skill 集（✅ 本仓要抄的就是这类）

**`ai4rpg/tavern-cards` 是唯一一个把「写卡」当成**Agent 方法论**来做的项目。**

它的目录结构（本仓 `fleet/skills.py` 认得就是这个）：

```
tavern-design/    # 叙事设计：项目定位、世界观构思、角色构思、互动与动态需求、创作方向、开场构思
tavern-cards/     # 项目创建与创作规划 → 条目创作 → 配置推导 → 打包输出
tavern-ui/        # 前端：Vue 3 + tavern_helper_template，消息楼层内渲染状态栏与交互表单
agents/           # 子代理：check-agent（禁词扫描）、conversion-agent（长文本大纲提取）、叙事式开场白创作、MVU 变量结构编写
scripts/tavern-cards-forge.mjs   # 离线打包 CLI
assets/cardrc.json               # 工作区配置
```

**它的工作流**（README「适用场景」表原文归纳）：

| 场景 | 流程 |
|---|---|
| 从零创建 | `tavern-design` 叙事设计 → `design-spec.md` → `tavern-cards` 项目创建 → 创作规划 → 条目创作 → 配置推导 → 打包输出 |
| 从材料转化 | 已有设定文档 → 自动提取为故事大纲 → `design-spec.md` → 创作规划 → 条目创作 |
| **修改已有卡** | **解包 → 断点续接 → 定位条目修改 → 重新打包** |
| 局部任务 | 只编写某个条目、调整某段 MVU 变量、修改开场白 |
| **评估卡质量** | **分析结构完整性、配置合理性、写作质量，生成评估报告** |

**「提到角色卡/世界书/SillyTavern 等关键词时 skill 自动触发」**——这正是本仓 `fleet/skills.py` 的行为模型。

🔴 **对本仓的三条直接价值**：
1. **「设计 → 创作 → 配置 → 打包」的分阶段流程**可以变成本仓的一个**写卡技能**，
   教模型按什么顺序填字段（比本仓现在的「裸 JSON」强）。
2. **「评估卡质量」直接对应本仓该做的体检器**（§0 第 5 条）。
3. **「解包 → 断点续接 → 定位条目 → 重打包」是增量改卡的正确形态**（§3.1）。

## 3. 三个具体能力，本仓真的缺

### 3.1 增量改卡（JSON Patch / 条目级定位）

**本仓现状（实跑核实）**：`persona_card.py` 只有 `load_card` / `list_cards` / `set_active`，
**没有任何写回路径**。`cards/` 下的 6 张卡是**纯 JSON 手工维护的**。
改一张卡 = 手写整个 JSON 文件。

**社区的做法**：
- `tavern-cards-forge`：**JSON Patch**（`unpack` → 改目录里的文件 → `pack`）
- Arcamage Agent 模式：**Diff 预览 → 确认 → 应用 → 可撤销 → 可按条目重试**

**本仓该怎么抄**：
不做项目目录化（本仓卡少），只做**字段级 patch**：
```
card.patch(card_name, path="data.personality", value="...")
```
配一个 **diff 预览**（改前/改后两栏），让主人先看再落盘。
🔴 这条和 §3.3 是同一件事的两面。

### 3.2 卡的安全体检器（+ 质量评估）

**本仓现状**：`docs/角色卡生态调研` §0 结论 15 早就建议做「卡的安全体检器」，**至今没做**。
`grep` 全仓无体检器实现。

**社区现状**：`ai4rpg/tavern-cards` 的 `check-agent` 做**禁词扫描**（机械扫描），
「评估角色卡质量」是它的正式场景。

**本仓该做什么（比社区更严）**：
| 检查项 | 社区做的 | 本仓该做的 |
|---|---|---|
| 禁词/敏感词 | ✅ `check-agent` | ✅ 同 |
| 结构完整性 | ✅ 评估报告 | ✅ 同 |
| **字段劫持**（`description` 里写「忽略以上设定」） | ❌ | ✅ **这是本仓的差异化项**——我们能操控本机 |
| **世界书内容注入** | ❌ | ✅ 同上（R6 风险） |
| **越狱载荷识别** | ❌ | ✅ 标记而非拦截 |
| **深度伪装**（整张卡是越狱预设） | ❌ | ✅ 标记 |
| **token 膨胀预警** | ⚠️ 只做估算展示 | ✅ 做成体检项（超阈值报警） |

🔴 **不拦截、只标记**。体检器是**给人看的报告**，不是闸门——
拦截权在人手里（这是本仓「用户绝对中心」的宪法要求）。

### 3.3 审批时的差异预览（Diff 预览）

**本仓现状**：审批闸门做得很严（`approval="ask"` + 弹窗 + 落盘留痕），
但🔴 **用户点「执行」前看不到「到底要改成什么」**。

**Arcamage 有，本仓没有**。这是本仓审批体系的一个真缺口：
> 现在的审批回答的是「**许不许**」，缺的是「**改成什么**」。

**为什么这条重要**：本仓的「一切皆 MCP」意味着**外部 agent 也能调能力**。
一个能力如果会让外部 agent 改文件/改系统，主人看到「要执行 XXX」时其实**无从判断风险**——
因为看不见 diff。⇒ **这是「设备也是 MCP」之后暴露出来的必然问题**，不是锦上添花。

**建议**：审批弹窗里带上 **before/after 摘要**（不需要全量 diff，摘要即可）。
配合 §3.1 的 `card.patch` 一起做。

  `grep card|persona` **零命中**。⇒ 角色卡**不能被 MCP 调、不能被 agent 用能力改**，
  它只是**运行时的人格数据源**。这跟 §3.1「没有写回路径」是同一件事的两面。
- **`cards/` 实有 6 张卡**：`大肥鱼`（人格本体）+ 5 张执行角色卡（研究员/程序员/编辑/批评者/验收者）。
  5 张执行卡的 `description` 长度只有 32~52 字，**`character_book` 全是 0 条**，
  `extensions` 存在（但按上面结论 7，不参与 prompt 拼装）。
  ⇒ **本仓自己的卡极其简单**，「做卡编辑器」对它们毫无价值；
  **真正有价值的是「造新卡」和「体检外来卡」**。

## 6. 明确排除（这些看起来诱人，但本仓不要）

1. **MVU**——酒馆前端的状态栏 + Zod schema。本仓人格状态走自己的 `persona.py`。
2. **EJS / 酒馆宏模板渲染**——本仓是单向注入，卡里的模板不执行。
3. **Docker + FastAPI + Vite 重栈**——破零依赖铁律。
4. **卡库浏览器**——原调研已否（§0 结论 15），本次复核无新理由推翻。
5. **`talkativeness` / `fav` / `world` / `emotions` / `assets` / `creator_notes_multilingual`**——
   原调研已列（单人桌面场景无意义），本次无异议。
