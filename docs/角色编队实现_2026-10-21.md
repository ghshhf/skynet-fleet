## A · 五段式输出契约

### 为什么要

子智能体的自由文本输出是**散文**。父级想用它的「证据」，只能整段读一遍再自己挑，
于是三个问题同时存在：

1. **挑错挑不到** —— 父级没有稳定的取材位置，只能靠猜。
2. **出了问题定位不到** —— 本仓实测旧账：`ag.py pipe` 三角色流水线走通但**中间角色超时**，
   自由文本太长导致慢，慢在哪一段说不清。
3. **可以自由省略** —— 子智能体写「大概都弄好了」，父级无从判断它到底做了什么。

Harness 的做法是把输出钉成五段、顺序固定：

```
SUMMARY:    一段话，你做了什么、发生了什么
CHANGES:    改了哪些文件，各一行说明；只读就写 "None."
EVIDENCE:   path:line-range 引用 + 关键发现，每条一个要点
RISKS:      可能出什么问题 / 父级该复查什么
BLOCKERS:   什么挡住了；干净收尾就写 "None."
```

**父级只机械消费 EVIDENCE 段**作为下一轮的工作集。

### 最容易写反的一处

> **「空段」和「合法的 `None.`」是两回事。**

`None.` 是**明确的**「没有」——Harness 明文允许只读任务的 CHANGES 写 `None.`。
空字符串是**什么都没说**。两者混为一谈 ⇒ 父级把「没说」当成「没有」⇒ **静默丢证据**。

所以 `contract.py` 把这两个判断拆成两个函数：

| 函数 | 判什么 | 典型值 |
|---|---|---|
| `is_blank(text)` | 这一段**什么都没说** | `""`、`"   "` |
| `is_none_marker(text)` | 这一段是**合法的明确否定** | `"None."`、`"无"`、`"N/A"` |

（实现时第一版把这两个写反了，自测当场抓到——正常样本被判失败。已修。）

### API

| 函数 | 作用 |
|---|---|
| `parse(text)` | 解析成 `{段名: 内容}`，找不到任何标题抛 `ContractError` |
| `check(text)` | 返回 `(ok, 原因列表, 解析结果)`，**原因逐条列**（缺哪段、哪段空、哪段重复） |
| `evidence(parsed)` | 取 EVIDENCE 段——父级唯一机械消费的那段 |
| `prompt_block()` | 给模型看的格式条款，**写成合同条款不是建议**（「必须/不许」执行率远高于「请尽量」） |
| `render(parsed)` | 渲染回规范五段文本 |
| `SECTIONS` / `SECTION_HINTS` | 段名与每段语义 |

## B · 角色卡加边界字段

### 抄机制不抄目录

Harness 用 `toolFilter` 显式收窄子级工具权限。本仓**不另起 YAML 目录**——
在已有的 chara_card v3 上加字段（`data.extensions.agent` 是规范留的扩展位，
不破坏 SillyTavern / RisuAI / AIRI 导入）。

### 三个字段

| 字段 | 含义 | 本仓取值 |
|---|---|---|
| `provider` | 这个角色用哪个后端出脑 | 全部 `local-gateway`（`127.0.0.1:8787` 免费端点） |
| `tool_filter` | 能力名白名单（**收窄**用） | 5 个执行角色各配 6–16 项 |
| `max_depth` | 作为父级时允许再往下派几层 | 执行角色全 0（不许派生）；大肥鱼 1 |

外加 `contract: "five-section"` 声明这个角色用五段式答卷。

### 关键语义：`tool_filter` 是**收窄**，不是放宽

- 白名单外的角色**调不到**该能力；
- 白名单为空 = **不额外收窄**（但实际动手权仍在**注册表审批层**，本仓铁律没动）；
- `tool_filter` 里写一个**注册表里不存在的能力名** ⇒ 当场报错，红在加载时而不是跑起来后。

### 6 张角色卡

| 角色 | 定位 | 能力白名单 | 可派层 |
|---|---|---|---|
| **大肥鱼** | 人设卡（主人对话用） | 全部 | 1 |
| **研究员** | 搜集事实与证据，只读 | 16 | 0 |
| **批评者** | 挑毛病，找反例 | 7 | 0 |
| **编辑** | 把产出整理成可读文本 | 6 | 0 |
| **程序员** | 写改代码，只在工作区 | 9 | 0 |
| **验收者** | 独立验收，只信证据 | 11 | 0 |

> 大肥鱼（人设）与 5 个执行角色是**分工不同**的两类卡：
> 前者跟主人说话，后者进角色流水线干活。

### 运行时名册 `fleet/agents/roster.py`

角色卡是静态的，但「现在有哪些角色、谁能干什么」是运行时真相。

- `load_all(known_caps=...)` —— 读全部卡，**逐个校验 `tool_filter` 命中注册表能力**，
  有错就**当场报清楚是哪个角色、哪个能力名**，并把全部问题一次性列完。
- `active_name()` —— 读 `cards/active.json` 指针。
- `summary()` —— 汇总成可展示的表（GUI / CLI 共用）。

## C · 容量闸

### 深度与容量是**两个独立的闸**

| 概念 | 管什么 | 实现 | 默认 |
|---|---|---|---|
| **深度** depth | 角色树能长多高 | `profile.max_depth` / `CapacityGate.max_depth` | 1 |
| **容量** capacity | 同一时刻能铺多宽 | `CapacityGate.capacity` | 4 |

混成一个数就会出现「为了限并发把递归锁死」或「放开递归结果并发也涨」这种错。

### 四条语义（逐条抄自 Harness 官方 README.zh.md）

| # | 语义 | 本仓落点 |
|---|---|---|
| 1 | **根父级不占名额** | 容量只数被激活的子角色；`CapacityGate` 初始 `in_use == 0` |
| 2 | **本地与外部后代共享同一池** | 单个 `CapacityGate` 实例，不分内外 |
| 3 | **创建前预留，完整释放后才归还** | `reserve()` 即占；**等待中 / 有待处理输入 / 正在停止 仍占**（`Lease.state` 状态机） |
| 4 | **容量耗尽 fail-fast，绝不排队** | `reserve()` 立刻抛 `CapacityError`，带「已占 N/M，还差 1 个」 |

第 4 条的官方理由很硬：

> 排队会让「等待后代的父代理」去等「自己占着的名额」，互相死等。

第 3 条是最容易做错的：很多实现「收到回复就还名额」，于是「还在收尾的活」不占额度，
实际并发会超过设定值。本仓用 `Lease` 状态机钉死：

```
reserved ──start()──> running ──stop()──> stopping ──release()──> released
   │                                                  ↑
   └──────────────── release() ─────────────────────┘
```

`stopping` **仍占名额**——它还没真正结束。

### 默认容量为什么是 4 而不是 Harness 的 8

Harness 默认 `maxActiveSubagents = 8`，但那是给 **1M 上下文 + V4** 的桌面机。
本机现实（2026-10-21 实测）：

- 16GB 内存；
- 子智能体全部打**同一个**免费端点（`127.0.0.1:8787`）⇒ 并发上去互相抢额度；
- 同一会话 9 个子智能体的对话记录累计约 **19MB** 上下文。

⇒ **照抄 8 会翻车**。默认 4。并发边界建议：**总并发 ≤ 4，同一端点 ≤ 2**。

### 调容量的语义

- 调**高**：立即生效。
- 调**低**：**不杀已在跑的**，只拒绝新的预留；已占名额超过新上限也不报错。

（与 Harness「调高立即生效、调低只拒绝新接纳」一致。）

## 编排器接入

`orchestrator.py`（111 行 → 155 行）的步可以带两个新字段：

```python
{"id": "s1", "cap": "exec", "node": "n1", "args": {...},
 "role": "研究员",     # 这个步由哪个角色执行（不给 = 不占名额）
 "depth": 1}          # 该角色处在第几层（根编排者 = 0，它直接创建的子角色 = 1）
```

`run_plan(plan, exec_fn, log=None, gate=None)` 的行为：

| 情况 | 行为 |
|---|---|
| 有 `role` + 有 `gate` | 执行前 `reserve()`，**这一步真正结束后** `release()` |
| 有 `role` + **无** `gate` | **报错**，不静默放过（否则容量闸形同虚设） |
| 无 `role` | 不受容量闸约束（普通命令步） |
| 容量满 | **fail-fast 拒绝整份计划**，回滚已完成的步，返回 `rejected_by: "capacity"`；**被拒的计划一步都不执行** |
| 深度超限 | 同样 fail-fast，错误里带「这是第几层」 |

## 门禁

`evals/t13_agent_crew.py`（**全离线**：不连网络、不调真模型，角色执行用假 `exec_fn`），
共 **57 条断言**，钉死五件事：

1. 契约不许被当成摆设——缺段报缺哪段、空段报空、`None.` 判合法；
2. 容量闸 fail-fast 不排队，且错误里带「还差几个」；
3. 名额真正结束后才归还（`stopping` 仍占；重复 `release` 不许把池子放飞）；
4. 深度是独立于容量的第二个闸（深度 0 = 禁止委派，根不占名额）；
5. 角色卡写错能力名当场红（`tool_filter` 全部命中注册表 70 项能力）。

已接进 `run_selftests.py`（`eval_t13_agent_crew`）。
