# 人机验证（滑块）进攻方案 · 2026-11-02

> 定位：协议层（`protocol.*`）之后的第四个台阶。协议层解决「不开浏览器能不能进」，
> 这一层解决「开了浏览器，卡在验证上怎么办」。
> 本文只写判断与可核验的事实，不写「据说」「大概」。

---

## 〇、一句话结论

**识别缺口已经不是难点，行为采集才是。**

开源生态里「找到缺口在哪」有至少五套成熟方案（MIT/Apache，全部离线可跑），
但真正拦住人的是：**提交那一刻，服务端要的不是「你滑到了正确位置」，
而是「你的滑动过程看起来像不像人」**——而这段行为数据是被各家自己的 JS
加密后上报的（极验的 `w`、腾讯的 `collect`、阿里的 `bx_et`）。

所以本方案的排序是：**先修底座（反检测）→ 再补行为（轨迹）→ 最后才谈识别**。
识别放最后不是因为它简单，是因为**它最不容易成为瓶颈**。

## 一、项目现状盘点：零件齐了，中间是断的

先说清楚「已有什么」，避免重复造。

| 模块 | 行数 | 已有的能力 | 对滑块的价值 |
|---|---|---|---|
| `fleet/browser_reg.py` | 884 | CDP `Session`、`wall_state()` 判墙、`wait_pass()` 等真人、`click/fill/submit/save_session` | **可直接复用**：浏览器连接、会话保存、表单填充 |
| `fleet/vision.py` | 409 | `look()`：截图 → 缩略 → base64 → 视觉模型 → 结构化观察 | **可做兜底识别**：让模型直接看「缺口在图的什么位置」 |
| `fleet/imgscale.py` | 123 | 纯 stdlib 的 PNG 解码/编码/缩放（不依赖 PIL） | 像素级操作的地基 |
| `fleet/kinds/pc_control.py` | ~800 | `pcctl.mouse.move/click`（`SetCursorPos` + `mouse_event`） | **只能瞬移**，没有分段、没有轨迹 |
| `fleet/kinds/register_device.py` | — | `register.await_pass` = 等真人过验证码 | **这就是当前的天花板** |
| `fleet/kinds/protocol_device.py` | — | `protocol.recon` 判 antibot：none / soft / hard | 已能识别「这里有墙」，但 hard 就放弃了 |

**依赖家底（实测）**：`Pillow 13.0.0` · `numpy 2.5.4` · `onnxruntime 1.31.1` ·
`playwright` + `chromium-1248` 全部在装；`cv2` / `scipy` **没有**。
`Pillow` 与 `numpy` 是 `requirements.txt` 的正式依赖，不是环境巧合——图像处理可以长期建在这上面。

**缺口清单（这就是要补的）**：

1. **零个滑块相关能力**。`catalog.py` 里搜不到任何 captcha / slider / 验证 类能力。
2. `wall_state()` 只认 Cloudflare 的 DOM（`#challenge-form`、`cf-turnstile` 等），
   **不认极验、腾讯、阿里的滑块 iframe**——遇到它们会判「没有墙」。
3. 鼠标只能瞬移。`_mouse_move` 是一次 `SetCursorPos`，`_mouse_click` 是
   `mouse_event` 按下抬起，**中间没有任何移动事件**。
4. 没有 iframe 内操作能力。极验和腾讯的滑块**都在 iframe 里**，
   Playwright 的 `page.mouse` 坐标是相对于主文档的，跨 iframe 要先取 `frame_element` 的 bounding_box 再换算。

## 二、开源是怎么搞的：五类方案，各自解决什么

### 第 1 类 · 缺口定位（识别「滑到哪」）

| 项目 | 方法 | 依赖 | 评价 |
|---|---|---|---|
| **ddddocr**（MIT，10k+★） | 孪生网络 ONNX，`slide_match(target, bg)` | onnxruntime | 生态最全，一套库通吃文字/滑块/点选；CPU 100ms |
| **captcha-recognizer** | YOLOv8 直接检测缺口 | ultralytics | 滑块专用，精度高于 ddddocr；模型大 |
| **SliderSolver**（Apache-2.0） | Canny 边缘 + `TM_CCOEFF_NORMED` | opencv | 纯 CV 零训练，2 行调用 |
| **tenon**（MIT） | OpenCV 缺口 + 旋转角 | opencv | 额外支持「旋转验证码」 |
| **AntiCAP** | YOLOv8 + 孪生 + CRNN | — | 唯一全题型（文字/滑块/旋转/点选/算术） |

**共同流水线**：`剥 alpha 透明边距 → 灰度 → Canny/Sobel 边缘 → 归一化互相关匹配 → 取峰`。

**这一类今晚已经在本机验证过了**（见 §四）：纯 `numpy` 实现同一套流水线，
不需要 cv2 也能跑到「精确命中、得分 1.000、排名第 1」。

### 第 2 类 · 轨迹生成（让「过程」像人）

| 项目 | 关键手法 |
|---|---|
| **HumanCursor** | 贝塞尔 + Fitts 定律时长 + 过冲回修 + 手抖 + 疲劳（每 2 分钟慢 1%）+ 移动中 1~2 次 20-40ms 停顿 |
| **human_mouse** | 贝塞尔 + 样条插值 + zigzag |
| **shy-mouse-playwright** | 钟形速度曲线 + 落点过冲修正 + 轮询率 60-144Hz 抖动 + Perlin 噪声 |
| **MouseWont** | 五种策略：Bezier / 物理仿真 / **最小加加速度（Minimum Jerk）** / 复合 / 自适应；含 Ornstein-Uhlenbeck 随机过程做手抖 |

**共识**（这几条是硬的，不是玄学）：

1. **贝塞尔控制点必须随机**——直线或固定弧线一次就露。
2. **时长按 Fitts 定律**：`MT = a + b·log2(D/W + 1)`，距离越远越慢，但不是线性。
3. **速度曲线呈钟形**：两头慢中间快。匀速是最明显的机器特征。
4. **过冲 1~2% 再回修**：真人几乎不会精确停在目标上。
5. **落点前 50~150ms 停顿**：手要"settle"。
6. **点间隔 8~30ms 随机**：真实设备的轮询率不是固定值。

### 第 3 类 · 协议层：跑厂商自己的 JS（这才是真正的硬仗）

| 目标 | 开源方案 | 怎么做的 |
|---|---|---|
| **极验 GeeTest v4** | **GeekedTest**（纯 Python，支持 slide/gobang/icon/ai，无需浏览器） | 逆出 `w` 参数的生成：`w = _ + u` 两段，其中 `pow_msg` / `pow_sign` 可本地算（`pow_sign = MD5(pow_msg)`），`_` 和 `u` 用官方混淆 JS 里的加密函数。**带 `deobfuscate.py` 自动更新常量**，厂商改版能跟。 |
| 极验 v4 | geetest4_cracker | 同上思路的另一份实现 |
| **腾讯 TCaptcha / qcloud** | **crackTCaptcha**（31★，支持 slider / icon_click / word_click / image_select） | **纯 HTTP，不开浏览器**，用 `Node.js + jsdom` 桥接官方 `TDC.js` 生成 `collect / eks / tokenid / pow_answer`，再调 `cap_union_new_verify` |
| 腾讯 qcloud | TencentSliderSolver | `prehandle → 下 tdc.js → CV 定缺口 → Node 沙箱注入轨迹生成 collect → 本地 pow → verify → ticket/randstr`；用 **quickjs** 而非整个 Node，便于部署 |
| 阿里 / 快手 / 拼多多 / 抖音 | captcha-source（资料仓） | 各家 `bx_et` / `bx-pp` / `x5sec` / `did` / `captcha_collect` 的采集点索引 |

**这一类的方法论转变，值得单独说**：

> 老办法是「逆向出算法，用 Python 重写一遍」。
> 新办法是「**补环境，直接把厂商自己的 JS 跑起来**」。

因为算法天天变（极验的混淆常量每次发版都换），而「跑他官方 JS」永远自动跟版。
`crackTCaptcha` 用 jsdom、`TencentSliderSolver` 用 quickjs——**都在干同一件事：给 JS 造一个假的浏览器外壳**。

代价：需要 Node.js 运行时（或 quickjs 这类轻量嵌入）。

### 第 4 类 · 反检测底座（决定你的行为分是 0 分还是 90 分）

2026 年一份公开评测（7 个工具 × 31 个目标，三轮）：

| 工具 | 通过率 | 路线 |
|---|---|---|
| **nodriver** | **31/31** | 纯 CDP，无 WebDriver 架构 |
| **Patchright** | 27/31 | Playwright 补丁（避免 `Runtime.enable` 泄露） |
| CloakBrowser | 26/31 | Chromium C++ 层 49 处补丁 |
| Camoufox | 26/31 | Firefox 引擎层全指纹伪造 |
| curl_cffi | 26/31 | 无浏览器，纯 HTTP 伪造 TLS 指纹 |
| vanilla Playwright / playwright-stealth | 垫底 | JS 注入层补丁 |

**五层检测，一层没盖住就白干**：

| 层 | 看什么 | 谁能过 |
|---|---|---|
| 协议层 | CDP `Runtime.enable` 的调用时序 | Patchright / nodriver |
| 指纹层 | canvas / WebGL / audio / 字体 / 屏幕 | CloakBrowser / Camoufox（引擎层设置） |
| 行为层 | 鼠标轨迹、点击节奏、键速 | 靠自己写（第 2 类） |
| 网络层 | TLS JA3/JA4、HTTP/2 SETTINGS | curl_cffi（`requests` 冒充 Chrome 必然露） |
| 渲染层 | `getBoundingClientRect`、真实 canvas 输出 | 必须真浏览器 |

**最硬的一条事实**：企业级防护（Akamai / DataDome）单靠工具只有 **20-40%**，
叠加住宅代理能到 **70-85%**；**IP 信誉比指纹打磨更重要**——
完美的指纹从一个机房 IP 发出来，一样是 0 分。

### 第 5 类 · 无感验证（2026 的真主流，也是最难的一类）

Cloudflare Turnstile、reCAPTCHA v3、阿里无痕验证——**根本不给你滑块**，
后台直接按行为、指纹、IP、访问历史打分，然后返回一个 token。
「人类自己都过不了」说的就是这一类：它不需要你做什么，它只需要判定你不像人。

**对这类没有「破解」只有「养号」**：稳定的指纹 + 稳定的 IP + 正常的访问节奏 + 真实的前置行为
（先看首页、再点登录，而不是直接 POST 登录接口）。这也是为什么 §二第 4 类的底座是前提。

## 四、已经验证过的事实（不是设计，是跑出来的）

`tmp/proto_slider.py`，**只用 Pillow + numpy，零新增依赖**，17 条断言全过，反向验证 7 条精确变红。

### 缺口定位：三条互补的腿

| 策略 | 适用形态 | 原理 | 实测 |
|---|---|---|---|
| **内容匹配** | 缺口处内容还在（只压暗/加阴影）——**极验/腾讯的经典形态，占多数** | 灰度 + alpha 掩码的二维归一化互相关 | 得分 **1.000**，全图 32409 个位置里**排名第 1**，误差 **0px** |
| **平坦检测** | 缺口被抹成纯色 | 带掩码的局部方差，找「比全图中位数低一个量级」的块 | 方差比值 **0.000**，误差 **0px** |
| 形状匹配 | 上面的都不成立时兜底 | alpha 轮廓 vs 背景边缘 NCC | 精度弱（实测偏 38px），**只标 weak，不硬提交** |

裁决顺序按证据强度：`内容强 → 平坦 → 形状(weak)`。
**能说「我不确定」比给一个错答案值钱**——滑块失败一次只是换张图，乱提交可能触发风控降级。

### 轨迹生成：9 条硬指标

`72 个点 / 0.81s / y 抖动 ±7.9px / 首段步长 0.26 中段 7.76（钟形）/ 有过冲 / 时间戳单调`。

时长按 Fitts 定律算（`0.28 + 0.22·log2(D/44+1)`，夹在 0.55~2.2s），
控制点随机弯 3%~8%，过冲 0.8%~2.2% 再回修，落点对齐。

### CDP 序列化

`mousePressed → 72× mouseMoved（带 buttons=1）→ mouseReleased`。
**`buttons=1` 不能少**：拖动中不按住，服务端会当成「悬停移动」而不是「拖拽」。

### 踩过的三个坑（都写进代码注释了）

1. **合成数据的处理顺序**：先裁滑块（未模糊）再模糊背景，两边不是同一张图，
   真值处 NCC 只有 0.316、排名 1356。真机上两张图必然同源同处理。
2. **PIL 的 `MinFilter` 在图像边界不腐蚀**（用边缘像素延拓）。实测 7×7 后掩码仍剩 1688/1936 px，
   白边框混进匹配，真值窗口 std 从 13 涨到 65。**手工砍 4px 边最可靠**。
3. **背景纹理必须非周期且有局部对比度**：大色块 → 滑块退化成纯色块；
   sin/cos → 伪峰 0.95 压过真峰（margin 只剩 0.02）；三层高斯模糊 → std 只有 12。
   正解是「粗马赛克 + 双三次放大 + 细噪声 + 随机线条」。

## 六、执行记录（2026-11-02 夜，全部本机跑过）

### P0 换底座：**实测后改判，不做**

原计划「换 import 就有收益」，实测下来收益是**负的**。

做法：起一个 chromium（独立端口 9333、临时 profile、headless），分别用
`playwright.sync_api` 和 `patchright.sync_api` 的 `connect_over_cdp` 连上去，
在同一个页面跑 13 项指纹探针。

结果：**13 项里只有 1 项不同**，而且这 1 项是负收益 ——

| 项 | playwright | patchright |
|---|---|---|
| `window.chrome` 的键 | `loadTimes, csi, app` | `loadTimes, csi`（**少了 `app`**） |
| `navigator.webdriver` | false | false |
| `window` 上的 `cdc_*` | 无 | 无 |
| 原型链污染 | 无 | 无 |
| 非原生函数 | 无 | 无 |
| `plugins` / `languages` / `platform` | 5 / zh-CN / Win32 | 完全相同 |
| **CDP `Runtime.enable` 检测**（埋 getter 看是否被偷看） | **被触发** | **被触发** |

最后一条是关键：Patchright 的招牌能力是「不发送 `Runtime.enable`」，
**但在 `connect_over_cdp` 接管外部浏览器时它不生效**。原因是那些补丁打在它
自己 `launch` 的时候；我们的架构是「自己起 chrome + CDP 接入」，用不上。

唯一的不同还更糟：真 Chrome 的 `window.chrome.app` 是存在的，
patchright 接管后反而没了 —— 这更像自动化，不像人。

**⇒ 结论：底座不是瓶颈。** 真正决定分的还是行为（轨迹/节奏）+ TLS 指纹 + 页面环境，
换 client 换不来这些。这个实验省下一次没有产出的改动。

### P0 的副产品：headless 的 UA 自曝

实验里发现 `navigator.userAgent` 带 `HeadlessChrome` —— 等于在门口挂块牌子。
已修，见 `Session._fix_headless_ua()`：

- 用 `Emulation.setUserAgentOverride`（**不是** `Network.setUserAgentOverride` ——
  那条只改请求头，页面脚本照样读得到 Headless）
- 版本号跟着浏览器走，不写死（写死的版本号半年后就是新的破绽）
- **绝不能 `detach`**：覆盖绑在 CDP 会话上，一断开就还原（实测踩到，先 detach 那次
  `ua_fixed=True` 但 UA 没变，白折腾一轮）
- 真机验证：`Chrome/156.0.0.0`，`Headless` 已消失

### P2：认墙（7 家厂商 / 4 种类型）

`verify_state()` 返回 `vendor / kind / advice / signals / matches / frames`。
分类不是好看，是因为**不同类型走完全不同的解法**：

| kind | 怎么打 | 代表 |
|---|---|---|
| `slider` | `slider.detect` + `slider.drag` | 极验、腾讯、阿里 nc |
| `click` | 要跑厂商官方 JS 或人工 | hCaptcha、reCAPTCHA |
| `invisible` | **没有「解」只有「养」** | Turnstile、reCAPTCHA v3 |
| `js_challenge` | 有头浏览器等它自己过（headless 必败） | Cloudflare 5 秒盾 |

**踩到的坑**：Turnstile 和 Cloudflare 整页挑战的 iframe 都在
`challenges.cloudflare.com` 下、路径都含 `challenge-platform`，靠 iframe 分不开。
所以整页挑战那条规则**只能靠主文档 DOM**判定，否则会把「嵌了 Turnstile 的正常页面」
误判成整页被拦。

### P3：穿 iframe

`locate_slider()` 遍历 `page.main_frame` + `page.frames`，按厂商选择器找
背景图 / 缺口图 / 拖动把手，`want_png=True` 时直接截成 base64 —— 可以原样喂给
`slider.detect`，中间不用落盘。

`bounding_box()` 返回的是**相对主 frame 视口**的坐标，**不要再自己加 iframe 偏移**
（加一次就错位）。

### P3.5：全链路，以及「拖完了 ≠ 进去了」

`slider.solve_page` 最后一步是**再看一次墙**，`passed` 三态：

- 墙没了 → `true`
- 墙还在 → **`false`**（拖完了但没进去，必须这么说）
- 没真提交 / 判断不了 → `null`

如果不做这一步，就等于把「我提交了一次」当成「我过了」——
风控已经降级的情况下还会以为自己很顺。

### 边界（比上一版更具体）

| 情况 | 现在能不能打 |
|---|---|
| 极验 v3/v4 的**滑块那一层** | ✅ 能打（缺口 + 轨迹 + iframe 都通了）；提交时的 `w` 参数仍需 P4 |
| 腾讯 TCaptcha | ⚠️ 只给一张整图、没有单独缺口块 → 当前算法要两张图，**明确报「整图分析未实现」** |
| 阿里 nc | ⚠️ 同上（位移式） |
| hCaptcha / reCAPTCHA | ❌ 点选，需要跑官方 JS |
| Turnstile / v3 | ❌ 无感打分，没有滑块 |

**「只给一张图」这一类是下一步最该补的算法** —— 它覆盖腾讯/阿里两家大厂，
而缺口定位那套（两张图）对它们直接不适用。
