# 手机 GPU 加速实测结论（Mali-G925 + llama.cpp Vulkan）

日期：2026-10-23　设备：红米 25060RK16C（天玑 9400 级 / mt6991 / 8 核实测 2.4GHz / 11.2GB）
GPU：Mali-G925-Immortalis MC12（Vulkan 1.3.278，`VK_KHR_cooperative_matrix` 支持）

## 一句话结论

**在 upstream llama.cpp 上，这台手机的 GPU 是负收益，不要接。**
纯 CPU 在两个模型上都快过纯 GPU，混合卸载（`-ngl` 部分层）更是崩盘。CPU 调参（`-t 4 -tb 6 -fa on`）才是真正的加速来源，已落进 `scripts/phone/serve.sh`。

## 实测数据（`llama-bench`，同 build 4231b23，4 线程）

### Qwen3-0.6B Q8_0（北极星-V7，604 MiB）

| 配置 | pp512 (t/s) | tg128 (t/s) | 相对 CPU |
|---|---:|---:|---:|
| 纯 CPU（`-dev none -fa on`） | **190.53** | **48.04** | 基准 |
| 纯 GPU（`-ngl 99 -fa on`） | 66.63 | 42.77 | pp −65%、tg −11% |
| 混合 `-ngl 8` | 66.88 | 5.89 | tg −88% |
| 混合 `-ngl 14` | 66.50 | 7.55 | tg −84% |
| 混合 `-ngl 20` | 65.27 | 10.78 | tg −78% |
| `-ngl 0` 但没加 `-dev none` | 66.24 | 3.79 | tg −92%（见坑 1） |

### Qwen3VL-4B-Instruct Q4_K_M（2.32 GiB，4.02B）

| 配置 | pp256 (t/s) | tg64 (t/s) | 相对 CPU |
|---|---:|---:|---:|
| 纯 CPU（`-dev none -fa on`） | **31.81** | **12.12** | 基准 |
| 纯 GPU（`-ngl 99 -fa on`） | 8.22 | 8.28 | pp −74%、tg −32% |
| 纯 GPU（`-ngl 99 -fa off`） | 8.21 | 8.52 | 同上 |
| 纯 GPU（`-ngl 99 -ub 64 -b 128`） | 8.54 | 8.32 | 同上 |

GPU 在所有 fa / ubatch 组合下都卡在 8.2~8.5 t/s 的平台，说明不是参数没调对，是 shader 吞吐上限。

## 为什么 GPU 反而慢

1. **模型太小，吃不满 GPU**。0.6B/4B 在 UMA 上都是带宽活，而天玑这代 CPU 有 i8mm + dotprod + Q4_K repack 内核，Q4_K/Q8_0 的矩阵乘在 CPU 上是高度特化的快路径。upstream `ggml-vulkan` 对 K-quant 是"载入后反量化再算"，还要逐 tile 走 cooperative matrix，反量化开销吃掉了算力优势。
2. **UMA 省不掉同步**。GPU 和 CPU 物理共享 LPDDR5X，但 buffer 是分开的。混合卸载时每一层都要跨边界拷贝 + 隐式同步，所以 `-ngl` 越少越慢（ngl 8 只有 5.9 t/s，ngl 20 才 10.8），完全反直觉但数据一致。
3. **prefill 差距最大**。4B 上 GPU pp 只有 CPU 的 1/4，因为 CPU 用大 batch 打 matmul 时 i8mm 能满血，GPU 侧反量化成了瓶颈。

**要让 Mali 真的有用，得换 ARM 的 llama.cpp 分支（KleidiAI + Mali 特化 shader），upstream 不行。** 这是独立工作量，暂不投入。

## 两个会误判的坑

### 坑 1：`-ngl 0` 不等于纯 CPU

Vulkan build 里就算 `-ngl 0`，Vulkan 后端仍留在调度器里，生成阶段每个 token 同步一次：

```
-ngl 0 -fa on            → pp 66.24  tg 3.79   ← 假的纯 CPU
-ngl 0 -fa on -dev none  → pp 190.53 tg 48.04  ← 真的纯 CPU
```

只加 `-dev none` 才能把 Vulkan 设备整个摘出去。**做 CPU 基线不写 `-dev none`，得到的数会低 12 倍。**

### 坑 2：`-tb` 在 `llama-bench` 里不存在

`-tb`（batch threads）是 `llama-server` 的参数。`llama-bench` 只有 `-t`。传了 `-tb` 会打一大段 usage 然后 **exit code 0**，看起来像"跑完了但没结果"，实际是参数非法。同理 `-fa` 在 `llama-bench` 里只接 `on|off|auto`，`-fa 1` 也非法。

## GPU 路线的环境依赖（如果以后还要试）

App 进程（Termux，`u0_a610`）的链接器命名空间**不含 `/vendor/lib64`**，进不去 Mali 驱动；`adb shell`（`shell` 用户）的命名空间**可以**。所以 Vulkan 只能在 `adb shell` 下跑：

```sh
cd /data/local/tmp/vkllama
export LD_LIBRARY_PATH=/data/local/tmp/vkllama:/vendor/lib64/egl:/vendor/lib64
export LD_PRELOAD=/system/lib64/libvulkan.so   # AOSP loader 有 sphal 权限，能进 /vendor 找 ICD
./llama-bench -m "..." -ngl 99 -t 4 -fa on
```

- 用 Termux 自带的 `libvulkan.so.1`（1.4.365）不行，只认 lavapipe 软件渲染。
- 厂商 `/vendor/lib64/hw/vulkan.mali.so` 是 stub，只导出 `mali_vk_vendor_stub` 和 `vkAcquireImageANDROID`，没有 ICD 入口，拷进沙箱也没用。
- 编 Vulkan 后端要自己造 `glslc` 兼容层（Termux 无 shaderc），见 `tools/phone/glslc-termux`。

**这套东西现在只作研究保留，不进 `serve.sh`、不进 `provision_phone.py`。**
