# 李跳跳（广告跳过）拆解与对「天网工程」的启示

> 来源：用户提供的 `李跳跳测试版_测试版.apk`（1.75MB）。本拆解用于把「规则驱动的 UI 自动化」抽象成天网工程的一个**节点能力**，并解释为什么用户感受到「很多规则已不适用」。

## 一、它是什么

李跳跳是国内一个个人开发者做的**安卓无障碍（AccessibilityService）自动点击器**。它不是 root 工具、不是 Xposed、不改系统——纯靠安卓官方无障碍接口，监听界面变化，找到「跳过 / 关闭 / 跳过广告」这类按钮并自动点掉。

用户痛点切入点很准：国内 App 开屏广告、激励广告、摇一摇跳转，按钮千奇百怪，手动点烦死。李跳跳用「规则」描述每个 App 的跳过按钮长什么样，无障碍服务扫到就点。

## 二、物理结构（从 APK 实测）

| 条目 | 大小 | 说明 |
|---|---|---|
| `classes.dex` | 63 KB | **壳/加载器**，真实逻辑不在这里 |
| `assets/0OO00l111l1l` | 782 KB | **加密的真实 dex**（乱命名规避静态分析） |
| `assets/t86` / `assets/tarm` | 279/222 KB | 加固壳的 native 组件 |
| `assets/o0oooOO0ooOo.dat` | 96 B | 校验/配置 |
| `lib/arm64-v8a/libmmkv.so` | 483 KB | 腾讯 **MMKV** 本地 KV 存储（规则、开关落本地） |
| `res/*` | — | 混淆后的资源（aapt 乱命名 `0N.xml` 等） |

结论：**这是被加固（加壳）过的应用**。classes.dex 只是一层壳，真正的规则匹配引擎在加密 payload 里，没法用简单静态反编译看到规则 JSON 原文。但这不影响理解其架构——李跳跳的机制是公开常识，且与上面证据自洽（MMKV 存规则、无障碍服务做点击、规则集可用户导入）。

## 三、逻辑架构（业界已知 + 与实测自洽）

```
App 界面变化
   │  AccessibilityEvent (WINDOW_CONTENT_CHANGED / WINDOW_STATE_CHANGED)
   ▼
AccessibilityService.onAccessibilityEvent()
   │  rootInActiveWindow → 遍历节点树
   ▼
对当前包名取「规则集」{ text/desc/id 匹配条件 }
   │  命中节点？
   ▼
performAction(AccessibilityNodeInfo.ACTION_CLICK)   ← 自动点掉
```

**规则（核心数据）形态**（社区版通用格式，李跳跳同族）：

```json
[
  {
    "enable": true,
    "appName": "某视频",
    "packageName": "com.xxx.video",
    "activity": "*.SplashActivity",
    "rules": [
      { "name": "跳过广告", "action": "click",
        "text": ["跳过广告","跳过","查看详情"], "desc": [], "id": [] },
      { "name": "X关闭", "action": "click", "clickableId": "img_close" }
    ]
  }
]
```

规则存哪里：用户导入的规则 + App 自带默认集，经 **MMKV** 落本地文件（`/sdcard/Android/data/.../files/`）。

## 四、为什么「很多规则已不适用」——根因不是技术，是**维护分发**

这是用户最该看清的一点。李跳跳的失败不在算法，而在**规则集停更 + 目标 App 持续变形**：

1. **按钮文案漂移**：`跳过广告` → `跳过` → `5秒后跳过` → `逛逛`/`立即领取`。规则写死文案就失配。
2. **图标化关闭**：很多 App 把关闭做成纯图片 X（无 text / 无 contentDescription），无障碍节点树里**根本抓不到文字**，只能靠 view-id 或坐标——而坐标/ id 又常被混淆或随机化。
3. **广告进 WebView / 小程序 / H5**：跨端广告的 DOM 不暴露给安卓无障碍节点树，引擎看不到。
4. **反无障碍检测**：部分 App 探测到有无障碍服务在跑就故意不显示跳过，或弹「检测到风险」阻挠。
5. **新 App / 新广告 SDK 不在静态规则集里**，得人工补规则——而原作者 **2023 年前后因法律风险停止维护**，社区规则源枯竭 → 这是「规则不适用」的**主因**：没人持续供给新鲜规则。

> 一句话：李跳跳是**对的架构 + 错的分发模型**。它能跑，但规则靠一个人/一个小社区手动养，养不动就全过期。

## 五、对天网工程的启示（关键）

把「规则驱动的 UI 自动化」从李跳跳里抽象出来，**正好是一个节点能力**，而且天网工程能补上李跳跳缺的那块：

| 李跳跳的短板 | 天网工程的补法 |
|---|---|
| 规则静态、停更就废 | **共享规则中继**：规则存进 L3 共享上下文 / 中继服务器，任一节点更新、全编队即时生效（社区/你本人维护一条，所有设备受益） |
| 单人维护、易断更 | **多源规则**：从多个仓库/频道拉规则，带版本与回滚 |
| 单设备、各装各的 | **中心下发**：第三原则——手机/Commander 反向推送规则与引擎到 Android 节点，不各端手填 |
| 无远端算力 | 规则匹配本身轻；若需「识图找关闭按钮」（图标无文字时），调**共享算力**节点跑轻量视觉模型 |

→ 抽象成一个通用能力：**`ui_automation`**（无障碍节点树 + 规则匹配 + 可选视觉兜底）。这跟「远程 AI 调用」是同一套思想的两边：
- 弱的 Android 盒子/手机：只跑无障碍引擎 + 规则，遇到「图标无文字」的硬骨头 → 把截图甩给有 AI 的节点识别关闭按钮坐标（见 `rfc/remote-ai-service` 分支）。
- 规则本身由编队共享维护，不再依赖某个作者良心。

## 六、合规边界（必须写清）

- 无障碍自动点击**仅用于本人设备、本人账号下的广告跳过/表单填充**，属「减少自己操作负担」的合法个人自动化。
- 不用于绕过付费、不用于他人设备、不用于任何 App 的服务条款明确禁止的自动化（如刷量、抢票）。
- 本工程只把其**架构**抽象为可选节点能力，默认不启用，需用户在 Android 节点上主动授予无障碍权限才生效。
