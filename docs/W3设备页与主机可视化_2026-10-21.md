# W3 · 设备页与「主机」可视化（2026-10-21）

## 一句话

把 T 版里的盲文点阵，换成**真进度条 / 真图 / 可排序表格**；
同时把一条隐蔽的**假数据**链路挖出来修掉了。

---

## 一、产出

### 后端（`fleet/gui/server.py`）

| 端点 | 作用 | 关键约束 |
|---|---|---|
| `GET /api/host` | 设备页聚合数据：资源 / 进程 / 应用 / 屏幕 | **一切走 `registry.call`**，闸门在服务端，前端绕不过去 |
| `GET /api/shot?id=…` | 把截图发回浏览器 | **登记制**：只能取回服务端自己截过的那几张 |

`/api/host` 返回结构：

```json
{
  "ok": true,
  "device": "host:local",
  "devices": [ /* reg.availability() 原文 */ ],
  "avail":  { /* 目标设备那一行（含 reason） */ },
  "monitor": { "cpu": 36.2, "mem": 77.1, "mem_used": …, "mem_total": …,
               "disk": 29.5, "net_up": 126.8, "net_down": 1046.7,
               "procs": [ {"pid": 15864, "name": "WorkBuddy.exe", "cpu": 327.0} ] },
  "apps":   [ {"pid": 1, "name": "a.exe"} ],
  "screen": { "path": "…", "shot_id": "s1" },
  "notes":  [ "取不到资源快照：本机未装 psutil（pip install psutil）" ]
}
```

**`notes` 是这个端点最重要的设计**：拿不到就写明原因，
**不许给假的 0 或空表格**。界面自己算一套状态就会出现
「界面说在线、实际调不动」的鬼故事（红灯 5）。

### 前端（`ui/index.html` / `ui/app.css` / `ui/app.js`）

右栏新增设备页（296px）：

- **资源条**：CPU / 内存 / 磁盘 / 网络 上下行——真进度条，不是文字；
- **屏幕预览**：真 PNG（不是盲文点阵）；
- **进程表**：可排序（点行头切排序方向），12 个热点进程；
- **原因条**：任何取不到的东西都在这里说清楚为什么。

## 二、🔴 安全：截图端点不是任意文件读取的洞

屏幕预览要显示图，就得把 PNG 发回浏览器。两种做法：

| 做法 | 后果 |
|---|---|
| 甲：前端传路径，后端照着读 | **等于开了一个「读这台机器任意文件」的口子** |
| 乙：后端截图时**登记**一张图，给前端一个 id | 前端只能回取登记过的那几张 |

选**乙**。`FleetServer.register_shot(path)` 发 id、`shot_path(sid)` 回取，
只留最近 16 张。

门禁用**行为断言**钉死（不是看代码）：

| 用例 | 期望 |
|---|---|
| 登记过的 id | 200 + 真 PNG |
| 未登记的 id | 404 |
| `?id=../../../../etc/passwd` | **404**（路径穿越被挡） |
| 缺 id / 空 id | 400（说清楚要什么） |
| 无 token | 401 |

## 三、🔴 挖出来并修掉的假数据：进程 CPU 整列是 0

**现象**：第一版跑起来，进程表 CPU 列**全是 0%**。

**根因**：`psutil` 的 `process_iter(cpu_percent=…)` **第一次调用恒返回 0.0**
——它需要两次采样之间的间隔来算差值。原代码只采一次。

实测：

```
--- 第一次采样 ---
0  System Idle Process  0.0
15864 WorkBuddy.exe      0.0
--- sleep 0.5 再采 ---
0  System Idle Process  682.7
15864 WorkBuddy.exe      97.1
```

**为什么这是最坏的一种假**：0% 是一个**看起来完全合理的数**。
没有真值的界面不会报错、不会空、不会红——它只是安静地骗你。

**修法**：先 `p.cpu_percent(None)` 打时间戳 → 隔 0.3s → 再采真值。

### 附带挖出来的第二个假：`System Idle Process` 的 CPU 是 713%

`System Idle Process` 的 `cpu_percent` 表达的是「**CPU 有多闲**」，
不是「某个程序在烧 CPU」。多核下它会超过 100。

排进「占用最高的进程」榜，界面就显示了一个**没有意义的数**，
还把真正的热点挤下去（真热点本来能排进前 12 的，被它挤掉）。

**修法**：排除 `System Idle Process` / `System` / `Registry` /
`Memory Compression` / `Secure System`。

> 门禁 t5 补了三条（AST 静态扫 + 源码常量检查）：
> 进程 CPU 要采样两次、先调 `cpu_percent(None)` 打时间戳、排除 Idle 进程。
