## 〇、一句话结论

**DeepSeek Harness 的「无限智能体」不是一个「能开很多个」的额度，而是一套「怎么把智能体组织起来」的架构。**
它的核心不是数量，是三件事：**①一切皆插件（能力可插拔）②深度与容量两个独立的闸 ③每个子智能体必须交一份固定格式的答卷。**

而本仓（设备编队）**已经有这套架构的三个零件**：
`orchestrator.py`（编排+回滚）、`registry.py`（能力唯一真相+闸门）、远程 5 角色智能体线。
⇒ **本仓不需要「申请更多额度」，需要的是把已有零件按 Harness 的纪律接上。**

## 二、值得抄的四个机制（这是「无限」真正的骨架）

### 2.1 深度与容量是**两个独立的闸**，不能混用

Harness 用两项**独立**配置管子智能体树：

| 配置 | 管什么 | 默认 | 语义 |
|---|---|---|---|
| `maxDepth` | 树能长**多高** | **1**（只允许直接子级） | 递归深度策略；深度 0 = 禁止委派 |
| `maxActiveSubagents` | 同一时刻能铺**多宽** | **8** | 一棵 Activation 树里「在线 + 正在创建」的子级总数 |

**四个容易被想当然的细节**（官方 README.zh.md 原文级）：

1. **根父级不占名额**；本地与外部后代**共享同一个容量池**。
2. **容量在创建前预留，完整释放后才归还**。⇒ 「等待中的」「有待处理收件箱的」「正在停止的」**仍占名额**。
3. **容量耗尽不排队**，直接返回 `ACTIVATION_LIMIT_REACHED`。
   官方理由：**避免「等待后代的父代理又等待自己占用的名额」互相死等。**
4. **调高上限对已有树立即生效**（每次新建/冷恢复前重读）；**调低则驻留子代理继续跑**，只是拒绝新接纳。

> **🔴 这一条是本仓最该抄的**：我们的「多智能体并行」如果也做限流，
> **限流必须 fail-fast（立刻拒绝），绝不能排队**——排队 = 父等子、子等父 = 死锁。

### 2.2 「无限」靠的是**插件化**，不是靠额度

| Harness 的做法 | 本仓对应 |
|---|---|
| 一切皆插件，配置文件组合替换 | `fleet/catalog.py` 能力清单（全仓唯一真相）+ `registry.register_all()` |
| 插件用 `cordis.patch.yml` 声明依赖与配置 | 本仓**没有等价的插件声明层**（🔴 缺口） |
| 具名子智能体库（`~/.dsh/subagents/*.yaml`，热重载） | 本仓**没有具名角色库**（🔴 缺口，但远程 5 角色是雏形） |
| 角色可配 `provider` / `model` / `persona` / `toolFilter` / `maxDepth` / `backgroundMode` | 本仓 `cards/*.json` 只有 `persona`，**没有 toolFilter / 模型路由 / 深度策略**（🔴 缺口） |

### 2.3 上下文继承 **≠** 工具权限继承（最容易想当然的一条）

> 官方原文：子级由父级创建，**子级拿到的是全新的扁平工具 Scope**。父级当时的工具视图、
> `restrict()` 结果和工具权限**不会自动导入子级**。Fork 带走的是已完成对话历史，
> **不会顺便复制父级的工具限制**。需要收窄子级工具时，**应在委派配置中显式设置 `toolFilter`**。

**⇒ 本仓的对应铁律**：子智能体的能力边界**必须显式写死**，绝不能「继承父级的」。
这跟本仓已有的「恒定维契约」「能力唯一真相」是同一个价值观：**边界要显式，不要靠继承蒙混过关**。

### 2.4 子智能体必须交**固定格式的答卷**

Harness 的子智能体输出契约是**五段式，顺序固定**：

```
SUMMARY:    一段话，你做了什么、发生了什么
CHANGES:    改了哪些文件，各一行说明；只读就写 "None."
EVIDENCE:   path:line-range 引用 + 关键发现，每条一个要点
RISKS:      可能出什么问题 / 父级该复查什么
BLOCKERS:   什么挡住了；干净收尾就写 "None."
```

**为什么值得抄**：父级**只读 EVIDENCE 作为下一轮的工作集**。
⇒ 这把「子智能体说什么」从「散文」变成「**父级能机械消费的结构**」。
这正是本仓一直吃亏的地方：远程角色智能体的输出是**自由文本**，`ag.py pipe` 走通过但中间角色会超时——
**自由文本没法定位是哪一步出的问题**。

## 三、你说的「4 个」：**实测不成立**（这条必须先纠正）

我把你机器上的证据全查了一遍：

| # | 查了什么 | 结果 |
|---|---|---|
| 1 | 本机 `settings.json` 全文递归找 `agent/max/limit/concurrent/team/sub` 键 | **零个**本地可配置的上限键 |
| 2 | `app.asar` 里搜 `MAX_AGENT` / `maxSubagent` / `maxTeamMembers` / `memberLimit` 等常量 | 只找到 **`memberLimit` / `memberCapacityMax`**，且来自**服务端响应**（`ownerPlan` / `personalTier`）⇒ **套餐下发，不是本地常量** |
| 3 | 本机 `app.asar` 里搜硬编码的 `>= 4` 之类成员数判断 | 无 |
| 4 | 本次会话的子智能体记录 | `~/.workbuddy/projects/d/<sid>/subagents/` 下 **9 个 agent jsonl**，累计约 **19MB** |
| 5 | WorkBuddy 运行日志按分钟统计并发请求 | `logs/2026-10-21/__85bdf88….log`：**08:00–08:02 三分钟内 16 次并发 `Sending request: agent=general-purpose`**；全日 `agent=cli` 341 次 + `agent=general-purpose` 174 次 |

**⇒ 结论**：
1. **「4 个」不是本机的硬上限。** 同类子智能体**实测并发过 9 个**（3 分钟内 16 次请求，全部打同一个免费端点 `http://127.0.0.1:8787/v1/chat/completions`）。
2. **你在界面上找不到「提高限制」的开关，是因为那个上限在服务端**（`memberLimit` 随套餐下发），
   本地 `settings.json` 里本来就没有这个键——**找不到是正常的，不是你漏看了**。
3. **但「4 个」这个印象不是空穴来风**：它来自 **DeepSeek Harness 自己的默认值 `maxActiveSubagents = 8`**、
   以及 TUI 侧的 `max_concurrent` 默认 10 / 硬顶 20。**你大概是在别处看到的那组数。**

**⇒ 关于「一下搞太多」**（你话里没说完的那半句，我按最保守的方式理解）：
**并行数不是越高越好，本机实测踩过坑**：
- 9 个子智能体打**同一个**免费端点 ⇒ 该端点是**共享额度**（`ofm-` 网关 / 免 key 云脑），并发上去会互相抢；
- 本机 16GB 内存 + 前面那 9 份 jsonl 累计 19MB 上下文，说明**上下文成本是叠加的**；
- 仓库里已有铁律：**「多 agent 同目录并行时绝不 `git add -a`」**——本仓已经因为多 agent 并行踩过两次坑（`git add` 卷进别人在途改动、`git stash` 弄丢文件）。

⇒ **本仓的答案不是「开更多」，是「按 DeepSeek 的两条纪律管住」**：
**深度锁 1（不许套娃）、容量按额度定、满了 fail-fast 不排队。**

## 四、本仓落地方案（分三步，每步可验收）

### A 步 · 角色编队：从「自由文本」到「五段式答卷」

**做什么**：给远程 5 角色（researcher / critic / editor / coder / validator）**加输出契约**，
与 `ag.py pipe` 的三角色流水线对齐。

| 角色 | 五段式里的重点 |
|---|---|
| researcher | EVIDENCE 必须是 **URL + 日期 + 具体数字**，缺就说「未找到公开来源」 |
| critic | RISKS 段必须列出**至少一条**反驳（不许「没什么问题」） |
| editor | CHANGES 段列出改动文件清单 |
| coder | CHANGES 段给文件+行号；BLOCKERS 段写清卡在哪 |
| validator | EVIDENCE 段给**命令与输出**（可重放） |

**验收**：
1. 每个角色返回答卷**五段齐全且顺序固定**（缺段 = 失败，不是「大概齐」）。
2. `ag.py pipe` 的**中间角色不再超时**——超时根因是自由文本太长导致慢，超时要能定位到**哪一段**。
3. 父级能**只取 EVIDENCE 段**喂下一轮（机械消费，不靠人读）。

**为什么先做这一步**：它是纯格式约束，**不改架构、不改模型、不加额度**，却能立刻把「并行跑一堆智能体」的
**收益变得可测量**。而且它直接治本仓旧账（`pipe` 中间超时定位不了）。

### B 步 · 具名角色库 + 显式工具边界

**做什么**：抄 `dsh-subagent-library` 的**具名角色库**形态，但**不抄它的 YAML 目录**——
本仓已有 `cards/*.json`（SillyTavern chara_card v3 格式），**在角色卡里加三段**：

| 新字段 | 对应 Harness | 作用 |
|---|---|---|
| `provider` / `model` | `provider` / `model` | 这个角色走哪个脑（远程云脑 / 本地网关 / 别的节点） |
| `tool_filter` | `toolFilter` | **显式**的能力边界（allow/deny）——**绝不继承父级** |
| `max_depth` | `maxDepth` | 这个角色**能不能再往下派活**（锁 1 = 不能） |

**验收**：
1. 角色卡里 `tool_filter.deny` 列出的能力，**真调一次被拒**（不是文档说说）。
2. `max_depth=1` 的角色**调不动 `delegate` 类能力**。
3. 角色卡改动**热生效**（不重启服务）——对齐 Harness 的热重载。

**🔴 明确不做**：不抄 `~/.dsh/subagents/` 目录结构，不引 YAML 依赖。
**chara_card 是本仓已有的、且有生态价值的格式**（`docs/角色卡生态调研_2026-10-21.md` 有 15 条结论），
**在它上面加字段，好过另起一套**。

### C 步 · 容量闸 + 扇出编排（把「无限」变成「有序无限」）

**做什么**：在 `orchestrator.py`（已有：拓扑排序 + 失败逆序回滚，111 行）上加**容量闸**，
严格照 Harness 的四条语义：

| 语义 | 本仓实现要求 |
|---|---|
| 深度 1 | 角色默认不许再往下派活（防套娃） |
| 容量共享池 | 所有角色共用一个名额池，根编排器不占名额 |
| **预留-释放** | 名额在**派活前**预留，**任务真正结束**才归还（不是「收到回复」就还） |
| **满则 fail-fast** | 满了**立刻返回**「容量已满 + 缺多少」，**不排队** |

**验收**：
1. 派活超过容量 ⇒ **立刻**报「容量已满」（不许出现「排队中」字样）。
2. 一个角色卡住时，**它的名额仍被占着**（模拟：派一个必超时的任务，再看还能派几个）。
3. 名额在**任务结束**（不是收到首字节）后归还。
4. 深度超限 ⇒ 拒绝，错误信息写明「这是第几层」。

**🔴 为什么不做「排队」**：Harness 官方理由直接抄——
**排队会让「等待后代的父代理」去等「自己占着的名额」，互相死等。**

| # | 不做 | 原因 |

| 1 | **不装 DeepSeek Harness** | 它是 Node/TS 栈，本仓是 Python 栈；我们要的是**机制**不是产品。且 v0.1 预览版 |
